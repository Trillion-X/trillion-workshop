# tools/run-sql-in-my-database/

The PostgreSQL kit's own tool (tools/keep-a-postgres-database-on-a-computer runs the database; this tool talks to it). It names no person's database or vault name.

Runs one SQL statement, as written, in a person's own Postgres-wire database and answers `{ columns, rows, row_count }` or the database's own error text, for an AI that has no shell (a phone or web chat). It runs the role recipes that make, grant and take away a kind of login.

| Name | Signature / Shape | Role |
|------|-------------------|------|
| `runSql` | `({ connection, roleConnection?, ticket?, heldValue?, input, connect? }) => Promise<{ columns, rows, row_count }>` | Runs the request as the connection's login and always closes the connection; with `ticket`, the statement's transaction first claims the use the engine signed. |

## Design

- **One statement** is the protocol's rule: every statement is a named prepared statement (extended query protocol), and the server refuses text holding more than one command (`cannot insert multiple commands into a prepared statement`). No parser here.
- **Read-only** is the login's rule. credential_name is the vault name the person saved a connection under (the row lists none: the engine mounts the value held under the name the run gives), a login that may write or one that may only read; the second is a role granted SELECT only. The tool has no read-only flag.
- **Role recipes.** A read role exists only when a recipe makes one; no computer makes it by default. The owner login runs the recipe (it needs CREATEROLE, given by `tools/start-a-computer` `set-up-postgres-role.sh` with `PG_MAKES_ROLES=yes`), every statement filled by the server's `format()` and all of them in one transaction, unless the recipe says `in_one_transaction: false`: Postgres makes and drops a database only outside a transaction block, so `own-database` runs its statements one by one on one connection. It makes the role and database the held role connection names, closed to every other login (the operator's too); the operator takes the right to act for the new role only for the statements that need it, and gives it back. A standing login takes its role and password from the held connection named by `role_credential_name` (descriptor 4) and is never answered; a minted one gets a made-up password and `VALID UNTIL`, and its connection is answered once. A login for someone else takes `recipe.password_verifier` and `recipe.role`: the SCRAM-SHA-256 verifier they made from a password only they keep (`do-work/make-a-login-verifier.mjs`), which Postgres stores unchanged as the role's password, so neither this computer nor any answer ever holds their password; nothing but the role is answered. `drop` revokes what `create` granted and drops the role.
- **Per-login limits.** A recipe's `limits` rows are the limits a create may set (`connection_limit`, `statement_timeout_ms`), each one `ALTER ROLE` statement filled by the server's `format()` with a whole number checked above zero, run only when the caller gives it. No number is chosen here: the caller passes what the computer's measured capacity allows. A standing login's password must be at least 43 characters (32 random bytes as base64url), and a minted one is 32 random bytes.
- **Nothing runs past the run.** The engine kills the run's process at its row's ceiling (`invoke.max_run_ms`, 300000: at most the wake runner's long_run_after_ms, so its runs are never queued one at a time as long runs; at 600000, from 11:05 AM CST Nov 21 2026, every wake-started run-sql waited behind one other for minutes), but a statement already sent runs on in the database unless the database is told when to stop. So every connection lowers `statement_timeout` and `idle_in_transaction_session_timeout` to what is left of the run (`timeLimitOf`): the time the call asks in `statement_timeout_ms`, or `read-data/time-limits.json` `default_ms` (120000) when it asks none, never past the ceiling, less `margin_ms` and the time the run has used; a shorter limit the login already holds stays. The server then ends the statement or the open transaction itself. Why: a Media library query ran about 50 minutes twice from 4:37 AM CST Nov 21 2026 after its run had ended, and stalled every files call until it was cancelled by hand at 5:28 AM.
- **No added layer.** No shape, list name or record type: the SQL goes through as written. The tool makes no table and names none: a list is a table the person's AI makes in the database's own language.
- **Reach.** The process runs sandboxed with internet:true, so it reaches the network only through the run's own loopback proxy (HTTPS_PROXY). Each connection is one CONNECT tunnel to the host and port the connection string names (do-work/through-the-run-proxy.mjs), and the engine opens it only to a host every value the run holds may go to (the vault entry's `hosts`). The database's own TLS runs inside the tunnel, checked against its name (`sslmode=verify-full`). The row names no local port and no host.
- **Declared use.** `use: { purpose, surface }` with `database` is bound by the engine, not by this tool: the row's database item says `under_use`, so the engine opens the database with its reader login (the database's name and the item's `under_use.held_suffix`, `<database>-reader-connection`; its own login is the item's `held_suffix`, `<database>-connection`; the engine reads these names from this row, not from code), a login the role recipe `may-read-under-row-rules` gives SELECT on the public schema and nothing else: it cannot get round the row rules, change a table, make one or read the use binding) instead of the owner's, and hands a ticket of the use on descriptor 5, signed with the database's use key (the database's name and `under_use.key_suffix`, `<database>-use-key`), which never leaves the engine (the engine's `src/tool_runs/tools/use_ticket.rs`). The statement's own transaction claims the ticket first (`BEGIN`, `SELECT * FROM use_binding.claim_use($1)`, the statement, `COMMIT`; `ROLLBACK` on error): the database checks the HMAC and the ticket's end and binds the use to that transaction once, and the row rules read it through `use_binding.run_purpose()` and `run_surface()`; no setting the statement may SET is read. A use with no ticket (a `credential_name` call, or a direct caller) is refused before anything is sent. A statement without `use` is the owner's own work and runs as before; on a table whose row security is forced, the database reads it under its own `use_settings` row `purpose_when_unstated`. The workflow engine sets `use` for a recipe step from the step's `config.context.use` (workflow-core `step_executor.rs`, `bind_declared_use`), over any use the step's input carried. `test/use-tickets.test.mjs` proves it on a real server.
- The connection string is never in the request, argv, a file or the environment, and no answer or error holds it.

## Dependencies

**Depends on:** `pg` 8.23.1 (MIT), the engine's `credential_mounts`, its run proxy and `packages` rows.

**Depended on by:** nothing in the Workshop imports it; a person's AI calls it, or uses the database directly.

## How a workflow step runs under a use (the contract)

A step that reads a pursuit's rows under a use never handles a ticket. The recipe step declares the use, and the engine does the rest:

1. **Declare it in the step** (the recipe row's `definition`): `config.name` is `tool:run-sql-in-my-database`, `config.input` has `database` (the pursuit's database, e.g. `ethos_for_who_runs_it`) and `sql`, and `config.context.use` is `{"purpose": "...", "surface": "..."}`. Two text values, no others.
2. **The engine signs the ticket** (`src/tool_runs/tools/use_ticket.rs` in trillion-rust). It makes a ticket for each run: `hex(payload).hex(HMAC-SHA256(<database>-use-key, hex(payload)))`, where payload is `{"nonce": 16 random bytes as hex, "purpose", "surface", "until": the run's deadline in Unix ms}`. The use key is read from the vault inside the engine and never leaves it.
3. **The tool presents it** (`do-work/run-sql.mjs`). The run gets the reader login (`<database>-reader-connection`) and the ticket on descriptor 5. The statement runs as `BEGIN; SELECT * FROM use_binding.claim_use($1); <your sql>; COMMIT`. The claim binds the use to that one transaction, once per nonce; `use_binding.run_purpose()` and `run_surface()` read it, and the row rules read those.
4. **Nothing else.** The step's SQL is ordinary SQL with no claim call. A statement with no ticket is refused before it is sent, and `set_config` cannot change the use (the test `a run cannot SET its purpose and be believed` proves it).

Example, the shape `clip-examiner` (purpose `manage`) and `daily-formats` (purpose `publish`, surface `social/instagram`) use:

    config.name: "tool:run-sql-in-my-database"
    config.context.use: {"purpose": "publish", "surface": "social/instagram"}
    config.input: {"database": "ethos_for_who_runs_it", "sql": "select id from public.recording_moment order by id"}

Claims and their counts: `select count(*) from use_binding.claims` lists one row per claimed use (nonce, purpose, surface, claimed_by, until), read by the owner. A pursuit's default for a run with no claim is `use_settings.purpose_when_unstated`; `none` reads nothing.
