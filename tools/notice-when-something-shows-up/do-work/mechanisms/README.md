# notice-when-something-shows-up/do-work/mechanisms

One leaf per way of waiting. Each leaf knows nothing about any other leaf, any source, any app, or anything that reacts. A leaf never writes to the log and never dispatches; it hands each transition to its caller. Adding a way to wait is adding one leaf here plus one waiter descriptor row, and it edits nothing else.

## Files

| File | Purpose |
|---|---|
| `elapsed-time.mjs` | Wait for a stretch of time to pass. Contributes `iso_time`, `epoch_ms`, `counter`, `every`, which is exactly the clock record. |
| `due-time.mjs` | Wait for what timed-action (`tools/run-work-later-or-on-a-repeat` `whenToWake`) says is due: its schedules and one-off actions, given as its own rows. Contributes `schedule_id`, `start`, `end`, `record_id`, `operation`; each occurrence is told under its own key, and only the last proof per schedule is kept. |
| `filesystem-volume-attachment.mjs` | Wait for a storage volume to become reachable or stop being reachable under a declared attachment place. Identity is read from the volume's own identity file (`.fseventsd/fseventsd-uuid`), so no child process is spawned and it runs under leaf containment. Reports everything currently present on start. A listing or watch the process is forbidden to make throws, so the emitter records it as a fact. |
| `inbound-http-delivery.mjs` | Wait for something delivered over the network on a declared host and port, bounded by a body byte ceiling. Answers 503 when the fact could not be written so the sender retries. |
| `postgres-connection.mjs` | Not a mechanism: how the noticer opens a Postgres connection, through the run's proxy (HTTPS_PROXY, run-sql-in-my-database's tunnel) when the engine names one. `row-changes.mjs` reads its watched database this way and says `clientOptions` on for `due-time.mjs` and `source-rows.mjs`; `../kept-places.mjs` reads the database `places_in` names this way without loading the row-changes leaf. |
| `row-changes.mjs` | One person's own choice for a Postgres store (not a shared default; the example rendering is in workflow:tell-me-when-something-changes's kit). Wait for rows to change in a Postgres database: reads the database's own change table (row_changes, written by one trigger function in the same transaction as each change) in commit order, only transactions older than every one still running, so nothing is skipped or told twice; LISTEN on its channel wakes it early, and it reads again every `look_again_seconds` anyway. Contributes `database`, `table_name`, `op`, `at`, `before`, `after`, `txid`, `position`; each change is told under `<database>:<txid>:<position>`. Its connection is a descriptor (`connection_fd`). It names no table of the person's. When the run's input `conditions_from` names the database it reads, a change is told only if some wake that hears its kind has a match the change meets, or some workflow's fires_when condition (that database's workflow_recipes rows, or an installed recipe's) could keep it, judged by tool:choose-the-workflows-that-fire; the rest pass without a fact (the place moves on, the change stays in the change table for a replay), a condition that cannot be judged keeps every change told, and each pass says how many it told and did not tell. |
| `signed-service-calls.mjs` | Wait for a service to call over HTTPS and check that it really sent the call by its waiter row's `verify` (which header parts, the signed text, the hash, hex or base64, an optional secret prefix and the replay window), then report each change its `shape` row reads from the call: `where`, `place`, `change` (added, changed or removed), `at`, `key` (the service's own id), `before`, `after`. Names no service: a payment service's `t=,v1=` header and the standard webhook headers are two rows over the same code. A waiter's `verify` may name a rule in `signing-rules.json` (`stripe-signature`, `standard-webhooks`, `twilio-request-signature`) instead of giving its own. An unsigned, forged or stale call is answered 401 and told to nobody; a change the engine did not take is answered 503 so the service sends it again. The signing secret is read from `secret_fd`. |
| `service-lists.mjs` | Read a list a service keeps every `look_again_seconds` by its waiter row's `request` (url and headers, with `{credential}` from `credential_fd`) and `shape` (where the list, each thing's key, place and time sit, and the next page), compare with the last read's fingerprints, and report each thing added or changed, and removed when the row says the list is whole. For a service that cannot call out, and for a computer that slept: what changed meanwhile is still in the list. The first read tells nothing unless `tell_what_is_there_at_first`. Same fact fields as `signed-service-calls.mjs`, and `kinds`: the row's `shape.kinds` rules (`{change?, has?, lacks?, kinds}`, each that holds over the whole thing adds its kinds) label the change with the kinds the person's workflows' fires_when read, as JSON text, because only this read holds the whole thing; `shape.carry` (paths, or names to paths) makes `after` only the values its readers need, under the names they read, so a thing larger than one fact field still carries them. |
| `source-rows.mjs` | Many lists a service keeps, held as rows of a table in the person's database (its `table`, read with the connection on `connection_fd`), one waiter and one session for all of them: each row holds a `service-lists.mjs` waiter's settings (request and shape), its own kept fingerprints, when it was read and when it is due; each pass reads the rows that are due, oldest due first, at most `most_reads_per_minute` a minute, tells what differs exactly as `service-lists.mjs` does, and writes each row back with its new place and next due time. Adding a list is adding a row: no switch, wake copy or session of its own. A row whose list cannot be read says why in `last_said` and is read again when due; a refused tell leaves the row's place where it was. What reads cost is capped each day by the person's budget row (`cost.budget_table`, `cost.budget_id`, `daily_cost`), else by what the service says is left (`cost.balance_request`, `cost.balance_path`), never a number in code. `list_group` lets one table hold lists read with different keys, one waiter each. Same fact fields as `service-lists.mjs`. |
| `whatsapp-linked-device.mjs` | Wait for WhatsApp to push a message to a linked device of the person's account, and report it at once: added, changed (an edit) or removed (a delete), from a person or a group, whatever it carries (words, a voice note, a photo, a video, a document). The socket is the WhatsApp connection's own (`bring-in-new-items-from-this-computer/computer/connections/whatsapp.mjs`, through its `observe` hook), never a second one; its linked session lives in the waiter's own folder (`folder`, inside the run's kept folder). Same fact fields as `service-lists.mjs`, with `by` (the sender) in place of `before`: `key` is `<chat>/<message id>` for the message, its edit and its delete; `after` is JSON text `{chat, chat_name, group, words, media: [{kind, identity, seconds, ...}], reply_to}` within 1,000 bytes (long words cut and marked `words_cut`; media by WhatsApp's own identity of its bytes, never the bytes); `kinds` is the row's `kinds` (default `["seed"]`). Older messages (history sync, messages queued while away) are told only from `history_since` on. Each phone code for linking is told at place `link` until the person enters one. Its connection goes through the run's proxy (`HTTPS_PROXY`) as a CONNECT tunnel (`proxyAgent`). |
| `imessage-chat-database.mjs` | Wait for Messages to write an iMessage or text message into the person's own Mac's Messages database, and report it at once: added, changed (an edit) or removed (an unsend), from a person or a group, its words (the text column, or the attributedBody the iMessage connection decodes) and its attachments by guid, never their bytes. It watches the database and its -wal file, each on its own (a folder watch failed in a Mac sandbox), and reads once per burst of writes; nothing is read on a timer. Read only: it opens the database read-only for each read and never sends. Its state is the last message row and the newest edit and unsend times read, so a restart tells nothing twice; `history_since` tells older messages from a time on. A refused database (no Full Disk Access) is told once at place "access" with the setting to change. It runs in tool:notice-messages-on-this-mac, the noticer's program with the read-messages capability, on the person's Mac. |
| `files-someone-finished-putting-here.mjs` | Wait for somebody outside to FINISH putting a unit in a declared place. Completeness is the completion note and nothing else, so a unit still arriving has no note and does not exist to this leaf; there is no timer and no size comparison. The note carries the identity, so a large original is never read to learn what it is, and a note field invented later travels verbatim into `observed_identity` with no edit here. A note that will not parse, or whose declared length disagrees with the bytes beside it, is reported as a REFUSED note rather than skipped. The place is the WRITER'S private volume, read without taking its lease: the start action declares `readable_private_volumes` and binds `BITFIELD_HANDOVER_PLACE` to the resolved root (`architect` `352f9b79`), so the row names an environment key and never a host path. An unresolvable place THROWS and an absent place is an error, because a `.` fallback would watch an empty ephemeral directory forever while looking healthy. |

## The leaf contract

| Export | Shape | Role |
|---|---|---|
| `MECHANISM_REF` | `package::notice-when-something-shows-up::mechanism::<leaf>` | The identity the emitter compares against the row's declared reference. |
| `describeMechanism()` | `{mechanism_ref, detail_fields, conditions}` | Declared identity plus the payload fields this leaf contributes; may not name an arrival field. |
| `readSettings(settings)` | pure | The row's `mechanism_settings` with declared fallbacks. |
| `watchForTransitions(settings, {onTransition, signal, nextSequence, state, keepState, folder, ...injected})` | resident | Returns only when the signal fires; calls `onTransition({condition, observed_identity, detail})` per event. Every host touch is injectable for tests, including `environment`. |

## Dependencies
