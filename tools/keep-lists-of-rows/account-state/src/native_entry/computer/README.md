# The computer entry's own parts

`../computer.rs` starts the engine as a computer from one config file. The files here are its parts:

| File | What it does |
| --- | --- |
| `settings.json` | The computer entry's numbers and file names (config, key and receipt limits, stop poll, forwarder timings, the copy files) |
| `account_create.rs` | `POST /accounts/create`, loopback only: a sign-in program on this machine (the Better Auth Workshop tool's user-create hook) makes a person's account here, with no sign-in of its own; it is made, landed and served as a skipped account is started. Sign-up itself is the Better Auth tool's (Nov 13 2026) |
| `join.rs` | Adding a computer to an account: `computer id`, `send-secrets-key`, `take-copy`, `join` |
| `join_itself.rs` | A computer named in an account's computers row starts holding the account by itself, with no operator step: a proven message for an account it does not hold makes it ask the sender (`Message::Holding`) for the ids and, when it may answer, the account stores' rows; it makes the folder (receipt last) and joins (`Copies::joining`) from stamp 0. A sign-up with `default_places` tells the others at once (`tell_copy_keepers`) |
| `hosted.rs` | `computer adopt-hosting-app-account COMPUTER_CONFIG STATE_FOLDER`: takes an account folder the hosting app holds, reading its `trillion-vault-root` Keychain item read only and sealing the secrets key to this computer's id; refused while another process holds the folder's lock |
| `hosting.rs` | The hosting app's engine (`native-serve`) as a computer of its own one account: the same `Computer` with the computer key the app keeps (`../parent_kept.rs` `ParentKept::computer_key`), its session to the forwarder (`places:relay`, `places:http`, the account's calls), its copies once the row names voters, and a hand-over of its writer turn when the app's host lifetime ends. The app's engine also gives its account the app's browser workspace as its Home (`ComputerAccount::set_home`, `Computer::set_home`): a visit to `/a/<address>/` with a session opens it (`forward`); a computer made from a config carries no web client yet, and every visit there, like a visit with no session, goes to the Sign-in & security page `Computer::hosting_at` makes the same composition from a state folder with no app window (`tests/hosting_app_computer.rs`) |
| `releases.rs`, `releases.json` | Following a signed engine release feed: the computer reads the feed every `release_check_every_ms`, takes the newest release for its own build target above its own sequence and signed by a listed key, waits its own spread, downloads over verified TLS, checks length and BLAKE3, unpacks to `<releases>/<commit>`, switches `<releases>/current`, hands its writer turns over, stops, and starts the new `current` in its own place (`newer_current`; exit code 0 where it cannot); a copy older than `current` starts `current` the same way at start |
| `installations.rs`, `installations.json`, `installations/tests.rs` | A published installation at the account's computer: `/a/<address>/installations/<id>/<path>` (where the forwarder carries a request for another origin) answered GET or HEAD from the account's own files under `/installations/<id>/`, only when the account's origins list (`/installations/origins.json`, written by the Workshop's `tools/publish-a-site-at-its-own-address`) names it; the list signed by the account's key is the origins row `computer.rs` `tell_origins` hands the forwarder when it changes and on each new session (the port of old trillion src/public-app-host.mjs:1456-1503) |
| `releases_tests.rs` | The feed's rules with no network: signature, content, ordering, spread, the switch, which copy starts `current` |

The release this binary is (commit, sequence, target) comes from build.rs (`TRILLION_RELEASE_COMMIT`,
`TRILLION_RELEASE_SEQUENCE`); `trillion-local release` prints it. The feed format is the one the Workshop's release
publisher writes. Nothing here names a machine kind or a vendor.
