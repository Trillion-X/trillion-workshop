# parts/record-log

The record store every person's data lives in: whole root records (`{ id, type, value }`) whose truth is an append-only log of envelopes, one log row per write, with the records, their type lists and the field indexes the host declares kept as keys of packed pages (log-structured, from the envelope-log engine shape: group commit, a projection kept in memory, boot as written pages plus the log rows after them).

## Key Types / Functions

Forward and reverse `range()` reads select the newest key before opening its value, as `walk()` does. Superseded large values are neither fetched nor parsed; a winning tombstone hides older values. Key bounds, result limits and ordering apply before any unselected value is opened. `test/kept-runs-range-winner.test.mjs` checks cold persisted reads and memtable winners.

Resident membership filters and an unfinished merge's filter share the `filter_bytes` cap on every write-out as well as cold open. A fresh write-out lets go of the oldest optional resident filters before allocating its newest one; the earlier filters stay on disk. A filter larger than the available cap is omitted, and exact page reads still preserve values, tombstones and missing keys. `held()` reports `filter_bytes` and `merge_filter_bytes` separately, each run's filter as `resident`, `blocks`, `stored` (kept but not held) or `none`, and `filter_fill` (the run being filled and its next page). A run with no filter and more than one page is filled after every merge and build is done, `fill_pages` pages a call, saving its blocks every `fill_save_pages` pages so a restart continues from the last save; it is marked filtered only once every page is read (`test/kept-runs-fill-filter.test.mjs`). `test/kept-runs-filter-memory.test.mjs` checks repeated warm flushes, omitted filters, an active merge reservation, cold reopen and a rolled-back write-out.

## Why This Design?

A Durable Object's SQLite bills every row written ($1 a million), and every index entry is a row. The decomposed store (`parts/eeaf`) wrote a row for every value, link and list member of a record plus a log row for each, about 104 rows for one overheard sentence and 313 for a decision. Here a write is one log row, and the records and index entries reach SQLite only as packed pages, about one row for each 64 KB written out. Reads come from memory, and memory is bounded by bytes, never by the size of the store, so a Durable Object's 128 MB is never outgrown.

## Invariants

1. The log is the truth: the keys are a projection rebuilt from the written pages plus the log rows after the position they cover, and every write first checks the log ends where the projection thinks it does.
2. One write is one transaction and one log row (several parts of one row only past 512K characters).
3. Memory is bounded by bytes: memtable (at most `memtable_hold` times `memtable_bytes`), page cache, shared-object cache, resident records (`slot_bytes`).
4. Index declarations are DATA from the host; the module names no product, record kind or field.
5. A record's value is kept at its id key (`i|id` = `[type, seq, value, stamps]`; a removed record leaves `[null, null, null, stamps]` so a change made before the removal never brings it back), so a read by id that misses memory costs one page; records written before keep `[type, seq]` there and their value at `r|type|seq|id` until they are next written, and both are read.
6. A failed statement marks the projection stale and every call first rebuilds a stale projection, so nothing is answered or written from memory a failure (or a rebuild cut off partway) left ahead of or behind the log; a rebuild also lets go of every cached page and big value and the merge filter, because a rolled-back write-out hands its run numbers and refs out again. Proven by seeded faults at every statement (`test/store-crash-recovery.test.mjs`).

7. Every envelope written carries what it replaced (`was` and `added` for changed fields, `prior` for a whole value or a removal), in the same log row: that is what undo, earlier reads, layers and copies compare against, and a change from elsewhere is applied only where this store still holds what it replaced.
8. The checksum is order-free and moved one field at a time; equal stores have equal roots whatever order their writes came in, and the one kept with the pages always equals the one worked out from every record (`test/record-copies.test.mjs`).
9. Copies merge by stamps (`record-stamps.mjs`), so any number of copies that have met the same changes hold the same state whatever order and however often the changes crossed, with clocks that disagree, through lost and replayed answers and restarts (`test/record-gauntlet.test.mjs`: three copies; a device lost and replaced; the leader losing everything and rebuilt from its kept history, `src/record-history.mjs` `restoreRecordHistory`; records and kept history changed on the way, refused); the checksum counts the stamps too, so copies holding equal values from different writes are repaired to one state (a bucket repair merges the leader's records by their stamps and sends back what the copy holds later or the leader no longer holds at all, so a leader that lost its storage is filled again instead of emptying its copies; only what the leader would not take, by its own rule on what a copy may change, is made exactly the leader's, `{ exact }`, or let go, `{ purge }`; records that do not add up to the leader's bucket sums are refused with nothing taken). Changes without stamps (written before them) settle the same way without a leader (`byContent` from the same two values on both sides), and every version a conflict met stays readable in a `kept-apart` record beside the record, whose fields only grow; the cases a root-synced engine is held to (both moved, one change costs the same at any size, a thousand writes cross as the records they touched, a stale peer never wins, the loser kept, a second fork keeps the first, no fork where nobody contested, bootstrap through the same exchange, the same exchange twice changes nothing, removed against edited) pass in `test/record-sync-vectors.test.mjs`.

10. The EEAF data model is kept, not dropped: EEAF is the model and the log is the storage. Every record written keeps `k|type|property|kind` for each value kind each property of its type holds (a type's properties, known the first time data uses them, as `type_properties` was) and one `p|participant|holder|role|ordinal` per thing a kind with parts holds (`participation` and `interaction_set_members`), in the same memtable and pages as the records, so the model costs no row beyond the pages (`scripts/measure-record-speed.mjs` `model_workload`, 2026-10-09: 5 251 writes of list rows, arrivals and moments, 292 page rows beyond the log without the model, 350 with it; the decomposed tables wrote about 104 rows for one sentence). Declaring records are read from the pages before the log after them is replayed, so every replayed record is keyed by the kind it was written under. Records kept before the model are walked as idle work (`model_build_v2`): the kinds with parts first, each over its own type list, so what holds a thing is known soon after a deploy (`holdersOf` `complete`), and a kind whose parts change is walked again; then every record once for its properties' value kinds (`model` `complete`); a holder is answered only while the record it names still holds the thing (`test/record-model.test.mjs`).
