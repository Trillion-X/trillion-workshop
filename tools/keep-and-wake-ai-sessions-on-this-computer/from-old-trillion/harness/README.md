# harness/

Client programs that run next to an AI agent's harness (a terminal coding agent, a headless job), on that agent's own computer: the helper that makes sessions reachable, the optional hooks, and the programs that wrapped a person's AI before Trillion reached every AI through its MCP. What runs on the person's computer to reach what only it can (Contacts, iMessage, WhatsApp, Notes, Mail, screenshots) is in `computer/`, and the helper starts its reader as one of its handlers. Like `extension/` and `ios/`, nothing here is part of the hosted service at app.gettrillion.ai.

## Complete local setup

`setup.mjs` and `setup.json` are the executable local part of `start_setup`'s `install.harness_setup`. The workspace build publishes that pair through its existing `/workspace/` asset route. The account's setup answer contains their actual download URLs and the commands for each supported host. Keep the downloaded pair in the stable folder named by the manifest; the host's installed commands continue to use it.

The installer uses the existing, signature-checked Trillion Mac app's carried harness and Node runtime. An explicitly supplied source checkout must be clean and match `--source-commit <full SHA>`. It does not download a native payload or choose an alternative AI. At present the complete local suite supports Claude Code and Codex on macOS because its existing account-key owner is macOS Keychain. A cloud-only or unsupported host receives an explicit pending report and continues through account setup's applicable capabilities.

| Action | Result |
| --- | --- |
| `--action inspect --harness <id>` | Reads payload, host config, host trust when available, hook execution observations, the existing account key and AI choice, and the app-owned helper. It changes no settings. |
| `--action apply --harness <id>` | Merges seven hook definitions into the selected host, retaining other hooks, permissions and settings. Each changed config receives a private backup and readback; a repeated application has no duplicate hooks or needless write. |
| `--action apply --harness codex --trust-hooks` | After separate review and authority, asks Codex for each exact definition's current hash and uses its own `config/batchWrite` trust operation. It trusts only matching, enabled installer hooks, then reads the host again. Explicitly disabled and managed controls remain in force. |
| `--action remove --harness <id>` | Removes the exact Trillion definitions without requiring the payload to load, so it also works after a damaged or removed app. Other settings remain. Run the kept script with an available Node runtime if the app's runtime is gone. |
| `--action mcp-inspect\|mcp-preview --client <ids>` | Reads each named AI app's own config (rows in `setup.json` `mcp_registration`; ids are `src/ai-clients.json` clients) and says whether Trillion's MCP entry is `absent`, `registered`, `outdated`, `custom` (the same name pointing elsewhere, the person's own), `blocked` or `not_installed`. Preview adds each file's exact changed lines and a BLAKE3 `review_hash` of the whole plan. Neither writes. Claude Code and Codex use the installed app's local stdio bridge, which reads the app-owned door address for every call and returns an error if that door is unavailable. |
| `--action mcp-register --client <ids> [--reviewed <review_hash>]` | The person's explicit action, and the only road that writes an MCP entry into another AI's config (`mcp-registration.mjs`). Per app: `registered`, `updated`, `already_registered`, `custom` (left), `blocked` or `not_installed` (nothing created). With `--reviewed`, a plan that changed since the preview writes nothing. Other keys and non-transport fields are kept; a migration removes only its named old transport fields. Earlier bytes are backed up. An entry is not a signed-in connection: each result names that app's `sign_in`. |
| `--action mcp-unregister --client <ids>` | Takes only Trillion's own entry out (`removed` or `already_absent`); a custom entry is left. |

`--mcp-url` accepts HTTPS, or HTTP at the literal loopback host `127.0.0.1` or `[::1]` for rows that use HTTP transport. Claude Code and Codex use the installed app bridge and reject a fixed `--mcp-url`; the bridge reads the account key from the existing Keychain owner and sends it to the local door over loopback. Addresses containing user information and remote cleartext HTTP are refused. Registration does not prove that an AI client can use the selected account; verify a real round trip separately. Tests use temporary Claude Code and Codex config files, never the person's installed configuration.

The seven definitions register sessions, take in the current prompt, show unseen decisions, require a decision before file changes, consult Trillion before ending a turn, keep the completed transcript, and sweep missed transcript messages. The manifest supplies their event, timeout and command arguments. The decision matchers come from the existing decision hook's own tool inventory. Config writes use the current documented `timeout` field for both hosts; Codex's `hooks/list` returns the interpreted `timeoutSec`, which the installer compares with that definition. The primary host references and Codex trust implementation are linked in `setup.json`.

Every configured command runs this same setup program as a narrow dispatcher. It forwards the real hook's output and exit status unchanged and records only the event, definition hash, time and exit code. A script edit invalidates its old observation. The returned configuration hook and its matching `ran-*` check both expose the current `definition_hash`; this hash includes the local paths and payload bytes, so a server can compare the reported values but cannot recompute it without that local input. An exit-zero process proves only that local execution; the existing recorder deliberately exits zero even when the account cannot yet accept a write, so account setup must still verify actual message intake, connection, source health and work delivery. A configuration file, a published agent or a running process alone never proves that complete loop.

The JSON report distinguishes `ready`, `pending`, `unknown`, `missing`, `blocked` and `unsupported` checks, with exit 0 for ready local checks, 2 for remaining work and 1 for an installer error. Inspect the individual checks. The Mac app already owns the helper and its recurring intake and recovery handlers. Setup does not create a second LaunchAgent, choose a background AI, launch work, read personal files or grant operating-system permissions. Native notifications, account authorization and iPhone widget placement retain their existing owners and require their own observed results.

`test/harness-setup.test.mjs` covers create/update/remove, repeated installation, broken-payload removal, config preservation, conflict and symlink refusal, pinned-source and signature checks, exact Codex trust, policy-output forwarding, evidence invalidation and duplicate-helper detection. `test/harness-setup-publication.test.mjs` resolves every setup URL to bytes produced by the same copier the workspace build calls and checks those inputs remain in the deployment source gate.

## The trillion command

`trillion.mjs` is a command any AI with a shell runs (Claude Code, Codex, Cursor, Gemini CLI, opencode, a script) to see the person's AIs and their AI jobs, run their Workshop tools and hand and take work, without an MCP connection of its own. Every command is one call of the engine's one MCP tool, `run_resource_operation {address, method, request_key, input}` (`trillion.json` `engine`), at the account's door, so the checks and authority are the engine's own. The request key rides on every retry, so a retried call is answered as the first one was.

The door is the Mac app's local door when this computer has one (`local-door.mjs`: the app `mac_app` names, its `computer-reader.json` adoption file and the port in its private descriptor), else the public origin; `--origin` or `TRILLION_ORIGIN` name a door. A sign-in made by `login` is used at the public origin, where it was made.

| Command | Engine call |
| --- | --- |
| `trillion whoami` | MCP `initialize`; the account is `result._meta["ai.gettrillion/account"].account_id`. Prints this AI's `ai` record id, its facts and the door |
| `trillion who [--all]` | `tools:run` of `tool:see-my-ais` (each AI's stored value, `live`, `seen_at` and how many jobs it holds), then one `tools:run` of `tool:evaluate-a-formula` with the formula title field of the person's list `list:ais` (`who.ai_list`) over the AIs shown. Groups them by owner (the record's `owner`, else the account the door answers for; yours first), then one line per name with its ready chats beneath; shows the AIs seen within `who.seen_within_days` (every chat with `--all`) and says how many it hid. With no `list:ais`, or one whose title is not a formula, it says so and names nothing; an AI's own `label` is never shown |
| `trillion publish [--dry-run]` | `@own-records` `records:read` of this AI's `ai` record, then `records:write` of it with `expected` the value read (null when new): the facts (`owner` from the door's account, `agent_id`, `app`, `model`, `provider`, `computer`, `harness`, `where`, `working_on`) and `live.seen_at` now; a person's cells (nickname, order, can) are kept. A write refused because the record changed meanwhile is read and made again |
| `trillion send any "JOB"` / `trillion send AI "JOB"` (`--wait SECONDS`, `--priority`, `--outcome`, `--label`, `--key`) | `tool:hand-a-job-to-an-ai {as, job, to, priority, outcome, label, key}`; `key` is the request key unless given, so sending again answers `already-there`. `--wait` reads it with `tool:see-ai-work {id}` until it is finished |
| `trillion work [ID]` (`--status`, `--to`, `--from`, `--taker`, `--limit`), `trillion events ID` | `tool:see-ai-work`, newest first; `records:history` of one job |
| `trillion take [ID] [--mine]` | `tool:take-an-ai-job {as, id, only_mine}`; the job taken is kept in `~/.trillion/cli/held.json` so it is moved as the id that took it. A job another AI took first is shown, never tried again |
| `trillion finish ID "RESULT"`, `fail ID "WHY"`, `stuck ID "WORDS"` / `--clear`, `release ID [--because]`, `withdraw ID --reason`, `remove ID` | `tool:change-an-ai-job {as, id, action, ...}` with the action `work.actions` names. `moved: false` with reason `changed` means another AI moved it first: the job is shown as it now is |
| `trillion serve -- COMMAND ARGS` / `--ag-ui URL` | writes this AI's record, then takes with `tool:take-an-ai-job`; each job runs COMMAND with the job on standard input (`TRILLION_JOB_ID`, `TRILLION_AGENT` set), or an AG-UI agent, and is finished with its output, given back with its error, or said stuck, each with `tool:change-an-ai-job`. It writes its record again every `contact_seconds` |
| `trillion tools`, `trillion call TOOL JSON` | `@workshop-tools` `tools:list`, every page (a pager that repeats a page is refused), and `tools:run {tool, input}` |
| `trillion op ADDRESS METHOD JSON` | any `run_resource_operation` |
| `trillion login` / `logout` | the public origin's own sign-in: `/oauth/register`, `/authorize` with PKCE, `/oauth/token` |
| `trillion setup [--harness claude-code,codex,cursor]` | login when there is no credential, then copies the program to `~/.trillion/cli/program`, links `~/.local/bin/trillion`, and writes `trillion-skill.md` as `skills/trillion-cli/SKILL.md` for each app present |

AI ids are `ai` record ids (`ai:<agent id>`; `ai:` may be left off on the command line) and job ids are `ai-job:<key>`. The agent id is `--as`, else `TRILLION_AGENT`, else built from the first `agents` row in `trillion.json` whose variable is set: `{app}-{session}-on-{computer}` when that app names its chat session (`session_env`), else `{app}-on-{computer}`. A job taken under the computer id before sessions had their own id is still moved as that id (held.json names it).

This AI's record carries facts only: `app` (the `agents` row), `model` (the row's `model_env`, else the setting its `model_config` names in the app's own config file), `provider` (from the model's family in `model_families`, else the row's), `computer` (the system's own computer name with its duplicate counter removed), `where` (repository and branch, never a path) and `working_on` (the title of the job it holds). No name is built or written here: an AI's name is the person's `list:ais` name formula (a nickname, else app · model · computer), worked out by the formula engine when read.

The credential is the account's existing key: the Keychain item `trillion-agent-work-key` the Mac app keeps, or `~/.trillion/cli/key` (0600) without a Keychain, or `TRILLION_KEY`. With none, `login` registers the program as an OAuth client, opens `/authorize` with PKCE (S256) and a loopback `127.0.0.1` callback, exchanges the code and keeps the sign-in (access and refresh tokens) in the Keychain item `trillion-cli-sign-in` (written with `security -i` on standard input) or `~/.trillion/cli/sign-in.json` (0600); it is renewed at `/oauth/token` before it ends. `logout` ends and removes only a sign-in this program made; the Mac app's key is left on and the answer says where to turn it off. A refusal names the door: 401 is that door refusing this credential (at the public door, a key is told it works at this computer's local door), 404 is a route the door does not serve; only a computer with no credential, or a sign-in that ended, is told to log in. Setup never replaces a file it did not make.

`test/trillion-cli.test.mjs` covers the arguments of every command and the work tool input each makes, the agent id, the record's facts (no name, no path or secret, a person's cells kept), the conditioned write and its retry, the key and sign-in stores, the door choice, whoami from `initialize`, the pager, `who` named by the list's formula in one call and its refusal with no list, send/work/take/finish against a stand-in door including a job another AI moved first, `--wait`, serve's finish, give-back and stuck, the PKCE sign-in against a stand-in server, logout's refusal of the Mac app's key, and setup's idempotent writes and refusals.

## Dependencies

**Depends on:** `src/agent-delivery.mjs` (signature check); the hosted routes `/mcp/api/agents/publish`, `/agents/presence`, `/agents/capacity`, `/handoffs/take`, `/handoffs/finish`, `/handoffs/read`, `/agents/events` reached with a personal key.
`drain-owed-decisions.mjs` depends on the hosted MCP tools `list_decisions`, `export_decision` and `start_decision` (through `trillionCaller`), on `decide-before-building.mjs` for the owed file, the server and the down answers, and is started by `wake-sessions.mjs` from its `handlers` row.
`decisions-since.mjs` depends on the hosted route `/mcp/api/notices/unseen` (`src/notices.mjs` through `src/person-store.mjs`), on `record-every-message.json` for which harnesses are recorded, and the macOS `security` command for the key.
`keep-written-files.mjs` depends on the hosted route `/mcp/api/namespace/write` (`src/file-tools.mjs`, the write_file route) and the macOS `security` command for the key.
`record-every-message.mjs` depends on the hosted routes `/mcp/api/inbound` and `/mcp/api/messages` (`src/inbound.mjs`, `src/messages.mjs` through `src/person-store.mjs`) and the macOS `security` command for the key.
`work-consumer.mjs` depends on the hosted routes `/mcp/api/live` (WebSocket), `/mcp/api/agents/publish`, `/agents/capacity`, `/activation/bind` and `/activation/waiting` reached with a personal key, the macOS `security` command for the key, and each host's own command (`codex queue`, `claude --bg --resume`, `claude agents --json`).
`trillion.mjs` depends on the engine's one MCP tool `run_resource_operation` (its `@own-records` records operations and `@workshop-tools` tools operations), the Workshop work tools (trillion-workshop `tools/hand-work-to-ais`) and `tool:evaluate-a-formula` (`tools/formulas`), the person's `list:ais`, MCP `initialize`, the public origin's `/oauth/register`, `/authorize` and `/oauth/token`, the Mac app's local door declaration (`local-door.mjs`), and on Node's built-ins only, so `setup` can copy it out of the checkout.
**Depended on by:** the distributed-tool work (it registers its run command with `--on tool.run.requested=...`); any agent harness that wants to wake on work instead of polling; the live proof `scripts/prove-agent-delivery.mjs`.

Historical transcript backfills (`--transcript` and `--sweep --all-history`) use the private chat archive road. They preserve the existing complete conversation identity and source message IDs, and do not create arrivals, replay old requests or finish old handoffs. If that archive route is unavailable, the cursor stays resumable; there is no fallback to the live person-message road. Normal prompt and turn-end hooks retain their existing behavior.
