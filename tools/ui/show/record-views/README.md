# record-views

A CRM-style view over any set of records, shaped like Twenty CRM's record views: one toolbar row (the caller's title and search, view switch, Group by, Filter, Sort, Saved views, Fields), rule filters, and table, board and gallery views of the same records.

View choice, grouping, column order, visibility, widths, density, alignment and frozen columns use the person's workspace records under each `preferenceKey`. A browser's older local choice remains the initial fallback until the person changes it. The account record is restored on another device with the workspace's normal `/work/api/records` read.

The public `@trillion/ui` barrel exports the generic preference seam: `keepRecordViewPreferencesIn({use, write})`. The signed-in workspace installs its reactive account owner before drawing lists. An isolated saved screen has no such owner by default and must install its own adapter using its declared named requests; without that, preference writes intentionally reject. `RecordViews` itself is not currently exported from that barrel. Named requests currently cannot express the workspace records read's `?label=...` query directly, so the screen needs an authorized endpoint that supports its preference reads and writes. Rejected preference writes are caught and shown in the shared view's configuration error area.

## Group order

- Groups and board columns appear in the order the grouping field lists its `values` DATA, then any undeclared value alphabetically (`groupComparator`, one comparator for both, so they cannot disagree).

## Toolbar

- `count={false}` leaves out the count beside the title, for a view that already shows its whole window (a calendar's week); `detailLevels={null}` leaves out the zoom pair.
- Group by, Filter, Sort, Saved views and Fields are one shared `ExpandableTabs` bar (`mode="action"`): an icon each, the word appears on hover or while a tool is in use (a chosen grouping shows as its detail, a filter as its count). Each opens a shared `ActionMenu`; fields hover open their submenus (buckets, directions, values). The bar is one rounded surface (`../twenty/record-table.css`).
- Rule chips sit on their own row under the bar, only while rules exist or the builder is open.
- Every row has a ⋯ when the caller passes `rowActions` or says what each record is (`aboutRecord` or `shareRecord`): the menu then offers every row for that thing (Share, Ask your AI, and the rest), so a list with no row actions of its own still shares one row.

## Appearance

- Styles live in `../twenty/record-table.css` (Twenty's rules) with tokens from `../twenty/theme-*.css`.
- Every class drawn here has a rule in a stylesheet the workspace loads (the looks in `scripts/workspace-looks.json`, `coss-workspace.css`, `../twenty/record-table.css`, `src/workspace/workspace.css`) or is a name a tour or test reads to find the element; `test/record-views-classes-have-looks.test.mjs` fails on an orphan. The quote excerpt's rule is in `screen-look/show/navigation-preview.css`. A gallery card with no picture pads its words and keeps the checkbox and menu together at the end of the title line.
- The toolbar row has no background or divider of its own. It gets the pane's glass surface only while it is pinned over scrolled content (`data-pinned="true"`, set from an IntersectionObserver on a zero-height marker).
- Each rule or group chip in the view bar has its own remove control; "Clear all" lives in the rule builder (`../rule-filter`).
- Gallery selection and hover rings are an inset `::after` layer, so a selected card keeps the same gap as the others.
- Hovering a gallery, table or board record opens the same Base UI PreviewCard with its media, name, first three useful facts and an Open button when the caller offers `onOpen`. Fields marked `preview: true` take priority; remaining visible columns stay available behind Details. Empty values are omitted. Marking one field never hides the other visible fields. Appearance: `screen-look/show/navigation-preview.css`.
- The card's select box and menu are one square size at one inset from their corners, from screen-look tokens `--record-card-control-size`, `--record-card-control-inset`, `--record-card-control-radius`, `--record-card-control-surface` (the look's popover glass), `--record-card-control-border` and `--record-card-control-shadow` (`screen-look/show/coss-workspace.css`). A card's picture made of words (`MediaPreview` `text-snippet`, `markdown-snippet`) starts its words below them (`--media-preview-overlay-top`, `twenty/record-table.css`), so a control never sits on what the card says.

## Dependencies

View options use ExpandableTabs' stable icon mode. Current grouping and sorting
remain in each control's accessible name and shared hover label, with applied
controls pinned. Opening a tool or choosing a group cannot expand its text,
rewrap the toolbar and move an open menu away from the pointer.

## Windowing, timeline and reveal

- Table rows, board cards and gallery rows are drawn only where they are on screen (`windowing.ts`); twenty thousand records cost what sixty cost. The count, sort, shift-ranges and ⌘A still use every record because none of them read drawn elements.
- `timeline: {fieldId, levels, level?, onLevelChange?}` lays the gallery out as a photo-library timeline while no Group by is chosen: square tiles sized by the level's `tile_px`, headings from the level's calendar stretch. Pinch (ctrl-wheel or WebKit gesture events), ⌘+ / ⌘− and the Zoom buttons step one level, keeping the record under the pointer where it was, and scale the grid from the old size to the new.
- `detailLevels` (default `detail-levels.json`; `null` turns it off) is semantic zoom for a gallery that is not a timeline and for a board: a trackpad pinch (ctrl-wheel, WebKit gesture events), two fingers on a touch screen, ⌘+ / ⌘− and the Zoom buttons step one level, so zooming out shows more, smaller cards that each say less and zooming in fewer that say more. The card under the fingers stays where it was while the grid scales into its new size; the level is kept with the list's other view choices (`detail`), and the gallery and board carry it as `data-detail`. Both draw cards through `RecordCardBody`, whose `detail` sets how many fields follow the name.
- `reveal: {id, nonce}` selects a record, scrolls it into the middle of its place in the run and marks it for a moment (`data-revealed`).
- `selected` is followed after mount: a caller that changes the selection (its own Select all) re-renders with the new list.
- A timeline tile stays within a quarter above its level's `tile_px`: a narrow gallery takes as many columns as that needs (two on a phone), so a tile never grows to the gallery's width.
- A board card leaves out the field the board is grouped by (its column already says it); each card value sits in its own `record-views-card-field` box.
- Appearance for all three (gap, inset, tile minimum, reveal ring) lives in `../twenty/record-table.css`, read by the component from custom properties.

## Column header menu, marks, counts, sheet, canvas and focus

The whole header cell opens the column's menu (Twenty's record table): a 32px row, the field's `icon` left of its name, a small arrow at the right end of the sorted column, a 200px menu opening below the cell, a 10px resize zone with a 2px accent line while dragging. Every row is derived from what the field can do and where the column sits; a row that cannot apply is never offered.

| Group | Rows | Offered when |
|-------|------|--------------|
| sort | Sort ascending, Sort descending (checked when current) | `sortable !== false` |
| view | Filter by this; Group by this / Stop grouping (checked) | `filterable` with a `ruleKind` and rule operators; `groupable` |
| layout | Freeze up to here / Unfreeze; Align (submenu Left, Center, Right, current checked and shown as hint); Reset width | always; always; only after the width was changed |
| move | Move left, Move right | not the identifying (first) column; Move left not on the column right after it; Move right not on the last |
| hide | Hide | not the identifying column |

Align, frozen count, order, widths, hidden fields and density are kept per view in one stored record under `preferenceKey`. Frozen columns are `position: sticky` from `--record-views-frozen-left`; the last casts a shadow once the table has scrolled sideways. "Filter by this" writes into this list's own level of the focus chain.

| `RecordViewsOptions.statusField` | `string` | The field whose value is each record's state where a view draws one (default the field whose role is `status`, else the first whose values carry a tone): on Draw a card's live badge takes that value's words and tone and pulses while the value says `working`. |
| `RecordViewsOptions.adds` | `RecordAdds` `{label, placeholder?, search(words) => RecordAddRow[], add(kind, at?) => Promise<{id}>}` | What the list adds by kind where a view offers adding (the board's Add on Draw: searched as the person types, added where they look). Without it a list that keeps changes adds a new record named by the words typed (the Draw row's `add_label`, `add_placeholder`, `new_label`). |
| `RecordViewContext.links` / `.statusField` / `.adds` | as the options | Handed to every view drawn with React, so a design offered to every list reads the list's own lines, states and adds. |

Counts beside a name are chips (`Badge`): the view bar title's count, a value's count beside its chip, group heading counts (the shared `DisclosureHeading`), board column counts. A grouped heading reads `<field label>: <value>`; a value chip's hover says what the count is ("6 items have Kind: Key. Press to show only these"). Group by starts with None, checked while nothing groups. Table and board rows open the same hover card as a gallery card; with no field marked `preview`, the card shows the record's own shown fields. A field marked `preview: 'heading'` sits beside the card's name, shrinking (its words cut short) or moving under the name so the name always keeps room to read; one whose value says the same as the name is left out.

Views every list offers beside the caller's own (when it offers more than one): Board (where a field groups), Sheet and Changelog, then the designed views (`designs/`: Chat, Feed, Inbox, Guide, Swipe, Calendar, Matrix, Sprints, Document, Carousel, and Draw, the one canvas, id `canvas`: the list on the real board, `src/workspace/draw-design.tsx`) and visual-database's views, each where the list's fields fill it. A view the caller only names (an id with no render, such as `canvas`) is drawn by the part that offers that id. The Document (the records top to bottom, each a numbered heading with its words under it, written in place where the list keeps changes) is the `document` designed view. Their tests are `test/record-views.test.mjs` in this repository (a real browser, with the formula engine deciding every filter).

## A saved view that says how it is drawn

A saved view (`SavedRecordView`) may carry `display: { as, settings? }` (`SavedViewDisplay`): `as` is the id of any view the list offers (the built-in views, a view an every-list part registers such as the chart), `settings` is that view's own choices as plain JSON. Nothing in `record-views.tsx` names a view or reads `settings`.

- Applying a saved view whose `display.as` is offered for this list's fields switches to that view (`applySavedView`).
- `readOnly` on the `render` context means the page only shows the list (a public share): a view draws what it is given and offers no control that would change it. `src/workspace/shared-list-views.tsx` passes it with no `write`.
- While a saved view is open, a caller view's `render` context carries `settings` (the open view's `display.settings` when it is drawn as this view) and `saveSettings(next)`, which writes `next` back to that saved view through the same `onUpdateSavedView` the app uses for any change to a saved view, and shows it at once. With no saved view open both are absent and the view keeps its choices where it always did (a view that needs the fallback reads its own preference).
- `display` is kept and checked by `trillion-workshop/tools/keep-lists-of-rows/read-data/saved-view-engine.mjs` (`normalizeSavedView`), so an AI sets it with `save_list_view` and reads it with `read_list_view`.

## Current-value projection and editing

A caller can supply `derivedReadProjection` with `project` and a pending-row projection. Calculations finish before normal filtering and sorting; stale replies cannot replace newer inputs. Pending or refused calculations are visible states. Under unchanged filters, refresh retains only row identities still supplied by the current owner so editors keep their drafts. Calculated cells are withheld while pending. Record arrays keep stable identities between accepted replies, including time/multiple-sort projection.

Cell edits await the real owner, suppress duplicate Enter/blur saves and retain failed drafts for retry. Markdown notes use the shared NotesDocument and the existing kept Coss popover/phone sheet. Active editing suppresses the row's HoverPreview; single-copy rows retain their React identity through regrouping. Narrow tables derive effective pinning from the existing measured viewport and field widths, preserving the person's stored freeze choice.

Caller views can declare `ownsEmpty` to receive a zero-row result while keeping their own empty-state controls mounted. `RecordViewContext.sections` carries the same section tree the owner computed for the current groups and configuration time zone; callers adapt that tree instead of implementing another grouping policy. `RecordViewContext.sort` carries primary and secondary keys, allowing specialized interactions such as reordering to respect the active shared sort.

Caller views stay mounted while derived/configuration values refresh or fail. The shared read notice reports pending/refused state; current-row admission and calculated-cell withholding still apply. This preserves caller controls and drafts without admitting old-owner rows.

`defaultRules` supplies a first-use filter after explicit configuration/initial rules and persisted node rules. Use it for a screen default; keep `initialRules` for an explicitly requested starting rule. Async account hydration retains newer local edits and clears through the host filter owner.

A record that appears after the list was drawn (an AI or another device added it) is marked for a moment in the table, board and gallery (`arrivals.ts`, policy in `arrivals.json`): at most a few at once, never the first draw or a change of filter, and its duration is the Screen Look's `--motion-arrival`, so a person who asked for less motion gets none. A board column folds to a narrow rail with its fold button, and the folded columns are kept with the list's other view preferences (`collapsedColumns`; words in `board-words.json`). While a list loads, its placeholder takes the shape of the view it last showed (`loading-layout.ts`, shapes in `loading-layouts.json`: table, board, gallery; any other view uses the caller's own).
