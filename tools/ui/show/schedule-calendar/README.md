# schedule-calendar

A calendar things are dragged onto: a month board or day lanes of hours, a header to move back, forward and to today,
and a tray for the things with no time yet. Composes the shared `calendar-grid` and `hour-grid`.

## Key Types / Functions

`selectableIds`, `selectedIds` and `onSelectionChange` expose explicit caller-owned multi-selection through the shared Checkbox on month cards, timed pills, all-day banners and tray items. `selectionDisabled` locks those controls while the caller is carrying out a batch action, and `selectionBar` hosts the caller's shared `BulkSelectBar`. Items outside `selectableIds` have no batch checkbox; the calendar does not infer selection gestures or own selection state.

`registerVerb` makes the calendar's keyboard the caller's one keymap (`src/workspace/keymap.json`, scopes `calendar` and `calendar-event`): the calendar names what it can do now (`calendar-shift`, `calendar-sideways`, `calendar-today`, `calendar-view`, `calendar-cycle-view`, `calendar-rolling`, `calendar-all-day`, `calendar-zoom`, `calendar-date-picker`, `calendar-shortcuts`, `calendar-new-now`, `calendar-focus-upcoming`, `calendar-focus-neighbor`, `calendar-open`, `calendar-move`) and the caller binds keys to those names; `calendar-action` runs the caller's `contextActions` (the same actions as the right-click menu); a thing it cannot do now has no verb, so its key goes on to the page. The calendar adds no key listener. `shortcutGroups` is the shortcuts sheet (the `calendar-shortcuts` verb opens it), drawn by the caller from the keymap rows in the person's own keys, and `shortcutKeys` are the keys of the header's arrows and Today for their tooltips. Other props: `format` (`{ dateLocale, hour12 }`), `zoneGutters` (+ `gutterHeading`), `onHourHeightChange` (+ range and `zoomStepPx`), `onRollingChange` (a view that says `rolling` starts on the anchor day, a week beginning today), `onDuplicate` (an Option-drop), `sections` (the header's first crumb). Command- or Control-click picks an item for the caller's batch selection instead of opening it. The header is a breadcrumb: section, month (a menu of months) and week ("W24", the shared `DatePicker` with `todayTone="calendar"`); the arrows say the span they move by ("Go to previous week") with their keys in the tooltip.

## Invariants

- Generic: no product words; every visible word is the caller's, month, weekday and hour names are the browser's locale (Intl).
- Only a movable thing can be picked up; a drop outside a day, a lane or the tray changes nothing; a drop that lands where the thing already is reports nothing.
- Days are local date keys, never UTC instants, so a day never slips across a zone or a clock change (tested in `test/schedule-calendar-placement.test.mjs` over both US clock changes).
- Anatomy: Buffer's publishing calendar and Cofounder's month board with its unscheduled list (Mobbin screens e018b95f, cc48070c).
- Date navigation: the calendar header opens the shared `DatePicker` in place over the visible schedule, following Amie screenshot review #152. The picker remains anchored to its trigger; choosing any day, including a day in the adjacent month, reports that exact day key via `onAnchorChange`. `chooseDate` supplies the trigger and popup accessible name when needed. The shared picker owns keyboard movement and close/focus return.
- Selection: `selectedId` is a caller-controlled identity, never inferred from a title. The same selected state reaches month cards, timed hour pills, all-day banners and checked task rows; selected controls expose `aria-pressed` for assistive technology.
- Persistent tray panels keep drafts and pending interaction state mounted while caller-owned tab choices change the visible pane.
- Hour lanes report pointer- or keyboard-selected snapped times. Caller-authorized movable timed items can preview and report duration resizing; all-day and read-only items cannot use the handle. Existing drag/drop remains the move path.
- Whole-day items may supply `dayEnd` as an exclusive date key. In hour views, the shared calendar clips the span to visible columns and draws one stacked banner across them; missing or invalid ends occupy only the start day. The caller still owns the provider's source dates and writes.
- Optional working-hours shading leaves items and their interaction available outside the chosen interval. Optional weekend hiding affects displayed columns only; date arithmetic and navigation still cover the full view.
- Planner proposals are bounded to 200 tasks, 3,000 busy events and 60 days. The caller must pass real local work-hour data; tasks and provider event records remain untouched until the caller explicitly applies a proposal.
- Interaction reference review: Amie's documented calendar and existing day/week capture comments in `HourGrid.tsx`, plus 21st.dev Inbox Calendar component 8088 (captured at `proof/amie-rebuild-2026-10-12/21st-inbox-calendar.json`) for quick-selection hierarchy. No registry code was copied. No Mobbin screen was used for these interaction changes.

## Ownership

Shared calendar controls own rendering and preference interactions. Appearance uses Screen Look tokens and its calendar stylesheet. The Trillion workspace adapter supplies copy, source data and navigation callbacks; service connections owns provider-declared discovery and exact-account binding.

`CalendarControls.colorOptions` receives the caller's existing palette. Source colors use the exact `calendar.color_key`, so two accounts with the same calendar name remain independent. A default requires a connected, writable source with create capability and a matching current account/calendar incarnation. Loading disables account/default changes; stale saved selections remain visible for recovery.

`ScheduleCalendar.contextActions` uses the shared `NodeActionPack` over `{ family: 'schedule-calendar-item', parts: { id } }`. The same exact item id reaches month cards, timed pills, all-day banners and unplaced rows. The shared menu owns presentation; the caller supplies actions and permission checks and performs writes.

`selectableIds`, `selectedIds`, `onSelectionChange` and `selectionDisabled` support controlled selection of exact records through the existing licensed Coss Checkbox. Omit `selectableIds` to keep normal event cards free of selection controls. The caller owns entry and exit from selection mode and supplies its `selectionBar`; the component does not infer a reference application's selection gesture. Timed pills, all-day banners and month cards share the same identities.

`CalendarControls.presentation="sources-menu"` reuses the same visibility, connection status and connect controls as full settings in the licensed Coss Popover. Its trigger uses caller-owned source tones and counts only readable, connected, visible sources. Palette dots and popup geometry belong to the existing Screen Look stylesheet.

`choicePresentation="menu"` reuses the pinned MIT Coss Select source (`parts/ui/show/coss/ui/select.tsx`, provenance and license recorded in `parts/ui/show/coss/README.md`) for a compact calendar-view dropdown. It preserves the controlled choice values, caller labels, and `onChoiceChange`; no reference implementation or new appearance CSS is copied. The default segmented presentation and its placement remain unchanged for existing callers.

## Calendar workspace anatomy

`trayItems` lets the caller show a selected collection in the side pane, including timed records outside the current grid. Omitting it retains the unscheduled-items default. Every row keeps the same identity for selection, context actions and drag/drop; the component owns no filter or task store. Trillion supplies All, Inbox and Today choices from its Lists-backed task records.

The shared calendar uses a fluid seven-day grid by default; callers may explicitly set `minDayWidthPx` for horizontal scrolling. The unplaced-items pane sits to the left on wide containers. Optional `trayHeader`, `trayContent` and `headerContent` slots accept caller-owned shared components for actions and details. `headerPosition="grid"` keeps calendar navigation with the grid while tray controls remain in `trayHeader`; it does not create a second navigation row. On narrow containers, the tray/detail pane retains its existing DOM reordering and the grid header travels with the grid. The grid body keeps its own scroll viewport, so hour scrolling and initial positioning remain intact. An open detail pane moves above the grid on narrow containers and scrolls within its bound. Weekday labels and day markers are caller-localized, with current-day emphasis; an explicit all-day label keeps that strip visible even when empty. Appearance stays in Screen Look and uses its light/dark tokens. Reference: installed Amie’s task/calendar split, documented July 19 week/day references, and 21st.dev Inbox Calendar 8088 for task-row hierarchy. No proprietary or registry implementation is copied.

For a populated dark week view, the supplied Amie screenshot #86 provides the composition reference: the task pane takes about 23% of the content width, compact task rows sit beside a continuous seven-day hour grid, and short event blocks keep their duration instead of expanding to a half-hour minimum. `ScheduleCalendar` retains caller-owned navigation and selection; Screen Look owns the task-row and event appearance.

`traySide="start"` or `traySide="end"` is caller-owned layout data for the wide pane. Screen Look uses the same `data-tray-side` value to align the pane divider; compact containers keep the existing content-driven order.

The optional checklist state (`ScheduleItem.checked`, `checkDisabled`) and `onCheckedChange` callback let the same tray expose completion without taking ownership of tasks. Labels come from `words.checkItem`; the shared Coss checkbox is separate from the row’s open button. Title and secondary details wrap inside the tray, and Screen Look owns the circular treatment and completed-title appearance. The consuming app serializes each task’s write and keeps the item unchanged until persistence succeeds.

The calendar adapter composes existing shared Tabs with `TabsContent.keepMounted`: task and email drafts and pending-send state survive switching panels. Inactive content stays hidden and occupies no layout space. The adapter supplies `trayDetailOpen` only for meaningful open content, so a mounted but inactive Mail pane does not displace tasks or lead the compact grid.

`showHeader={false}` lets an embedding screen provide its own navigation. The Trillion calendar uses the shared navigation with `headerPosition="grid"`; its task pane places the existing RecordViews search and view switch once, and keeps them available when search has no results. Trillion's `/calendar?settings_only=true` route uses the existing `CalendarControls` in place and does not mount the grid or task/mail tray.

`ScheduleItem.parentId` groups related tray records beneath their actual parent, preserving sibling order. Iterative traversal retains orphaned or cyclic caller records. Storage validation stays with the caller; Screen Look bounds indentation so long chains remain readable.

## Inline tray details

`trayItemDetail: { id, content }` expands caller-owned content inside the matching tray record. Use the exact ScheduleItem ID, including the caller's namespace. A detail for a record outside the current tray stays caller-owned and can use `trayContent`. Fields, writes and navigation remain with the caller; the shared calendar supplies placement. Screen Look styles the expanded row.

`trayGroups` supplies ordered headings for caller-owned `groupId` values; a heading may carry `count`, a fold press (`toggleLabel`, folding its records), an add press (`addLabel` with `onAdd`, shown on hover and focus) and `empty` to show with no record under it. `trayMarkedIds` marks several tray records as a set (a record pressed with Command, Control or Shift reports `onOpen(id, { additive, range })`), `trayFocusedId` draws and scrolls to the record keys act on (focus follows when it was already inside the tray) (the keys that act on it are rows of the one keymap, not a handler here). Nested items stay with their root group; missing and cyclic relationships remain visible. `trayAfterItems` hosts a retained adjacent collection after task rows, so mail or other sources can join the list without a second calendar or duplicate state.

## Named preferred times

`WeeklyAvailability` edits named weekly templates with independently available weekdays and sorted intervals for breaks. Drafts stay local until Save, including the deletion of the final template. The caller owns the selected default and persistence. Schedule names and times remain readable in each Select; narrow containers show one weekday per row.

`ScheduleCalendar.workingIntervalsForDay` passes each day’s availability to HourGrid. An empty interval list shades the whole day; omitted intervals use the existing legacy hours. The planner accepts the same `{ days: [...] }` shape and admits only sorted, nonoverlapping integer-minute intervals. A task must fit within one interval. Calendar settings loads its saved preferences before first paint so reopening retains the selected template.
