# Watch the service itself

`tool:read-service-usage` reads fresh provider counter samples for one exact connected account and inclusive UTC dates. The producer adapts the immutable `askProvider` slice in `source-baselines/`, using the current connection owner’s `read_usage` DATA and the HTTP owner’s renderer and executor. It mounts the selected account and token on private pipes. Missing, invalid and refused counters remain unread; an empty sample list is not zero usage, a complete period total, a price or an invoice.

`tool:keep-service-usage-watches` keeps each watch in the account’s existing records owner, at kind `service-watch` and id `service-watch:<watch_id>`. Configure, pause and delete require the exact prior snapshot (`expected`, or null for a new watch); configuration replies and the saved consumer expose current snapshots, including opaque root identity when the records owner supplies it. Delete reads back absence and refuses a root that still holds an unresolved original call. Configure with the current snapshot edits or resumes a paused watch. Each run processes at most one due watch. Every successful stage reads its actual admitted root before building the next CAS, so Native’s wake-cause metadata remains part of the exact prior state. The descriptor’s five-minute repeat uses the existing Native wake owner and budget; a Workshop wake starts off until its existing switch grants it standing rights. The package does not turn it on or create a second scheduler.

A due run conditionally claims the root, calls the fresh reader through the current records door’s nested-run grant, saves an immutable candidate in the same root, then conditionally publishes its reading and next due time. Provider unread is retained explicitly. A candidate survives a cold process and reconstructs the exact original declared final key and body. A fresh wake uses only the protected original-result read and never replays that write: Native currently stamps the new wake cause, so original-context recovery is not yet proved. A claim whose candidate is unavailable stays unresolved and makes no new provider call: Native nested keys include the original parent run, and another wake cannot safely impersonate it. These cross-wake original-context and claimed-phase recovery boundaries remain open; it is not reported as complete automatic recovery. Lost write replies use the existing records door’s protected original-result readback; an unavailable or refused original stays unresolved and is returned unchanged.

`tool:read-saved-service-watches` reads these account-owned states without contacting a provider. It is distinct from the old saved service-wide `tool:read-service-watch` identity, which is preserved in the inert migration evidence rather than repurposed.
