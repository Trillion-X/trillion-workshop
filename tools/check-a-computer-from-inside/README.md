# Check a computer from inside

`tool:check-a-computer-from-inside` reads one of the person's computers from another computer, over SSH as its administrator: how full each disk is, and whether each engine the computer's row runs holds the person it must hold. It is the inside half of `tools/check-a-computer-from-outside`, which logs in to nothing and so cannot see either.

Why: on Nov 23 2026 the always-on computer filled its disk, its engine came back holding no person, and every signed-in call to it was refused for a day. Nothing noticed, because nothing read the disk or the engine from anywhere else.

## What it reads and what it does

| Part | How |
|------|-----|
| Disks | `df -P -T -B1`; memory and image filesystems (settings.json `disk.skip_types`) are left out. A disk at or past `warn_used_pct` (85) is `disk-filling` (warn), at or past `alert_used_pct` (92) `disk-nearly-full` (alert). |
| Engines | Each unit of the row's `runs.units` that declares an engine's ready check: a loopback listen address (its slots' `health_listen`, its own `health_listen` or `settings.listen`) and a persons folder (`settings.persons`), whatever program it runs. The listen addresses are asked `/readyz`; the most persons any answering slot holds is the engine's. An engine that runs in a container names `ready_in_container`: the container's name, or `{compose_project, service}` to find it by its compose labels (which outlive a recreated or renamed container), and is asked inside that container's network (`nsenter -t <its process> -n`, with the computer's own `curl`). No address answering is `engine-not-answering` (alert). |
| Persons owed | The persons the engine's `settings.local_agents` name. An engine that holds none of them is held again by `POST /persons/add {"person": ...}` on its `settings.agent_socket`, run as the engine's own user (`runuser`), the only road the engine adds a person on; then it is read again. `engine-held-no-person` is a warning when it holds them now, an alert when not. An engine whose row names no person (a computer that only passes requests) may hold none. |
| Wake books | For each engine whose row names a local agent (`settings.local_agents`): its wake book, read by `wake:list` on its agent socket as the SSH login (the socket admits a caller by its OS user; the row's local agent is root), page by page (`after`, at most settings.json `wakes.most_pages`). A due-time wake is one that hears facts of `due-time`; a teller is a wake of `tool:notice-when-something-shows-up` whose id is `keep-noticing` or starts with `keep-noticing/`; a wake counts only when it is switched on and its switch stands. An engine with a due-time wake and no teller is `due-time-wakes-without-a-teller` (alert), naming the wakes: nothing tells their occurrences (Nov 25 2026, 6:40 AM CST: the Elestio engine held a due-time wake with no teller and a 6:45 school tick was missed, nothing said). A book that could not be read (the socket refused the caller, a page did not answer, no list came back) is `wake-book-not-read` (warn), never read as no due-time wakes. An engine whose row names no local agent holds no one (a meeting point) and is not read. `read_wake_books: false` skips it. |
| Due times told | Was each due occurrence told? For each switched-on due-time wake of an engine's book (`do-work/due-times-told.mjs`): its own cadence, local window, zone and clock-change rule are the schedules it asks to be watched (`on.fact.watch.schedules`), and when an occurrence is expected is timed-action's alone (`whenToWake`). Told is the wake's own `mark.fired_ms`, never `kind_last_told`, which is one fact for the whole kind (any other wake's would hide this one's missed tick). Asked from the later of its last fire and its switch time (`switch_history`), so a wake switched on after an occurrence began is not late. An occurrence is late once its start plus its own window plus `told.grace_seconds` (120) passed, and the wake has not fired since: `due-time-not-told` (alert, one finding naming the wakes). With neither a fire nor a switch time known a wake is not judged, said in `not_judged`; a one-off, a wake of another kind and one not standing are not judged. It catches a missing teller and a teller that is on but stuck or broken, which the strict check above misses; when no teller is on the strict finding says why and this one is left out. |
| This computer (`here: true`) | The computer the run is on, with no SSH: the row's records right lists the wakes that hear `due-time` on the run's own door (the descriptor on fd 3), every page. A run's right lists only the wakes that hear a kind of fact, never the tellers (they hear nothing), so only the symptom check, `due-time-not-told`, is made here (about `this-computer`; the computer is named as the door says). A door that refuses is `wake-book-not-read`. |
| Person folders | Each folder in the engine's `settings.persons` folder: its size (`du -sb`) and its `persons.largest_files` (5) largest files (`find -printf`, sorted). A reading, not a finding: the caller keeps it each run to see what grows (an engine's tool-run records, its builds). Only read. |
| Units | Every other unit of the row's `runs.units` (a service, a timer, a path; a unit run in slots is read as its engine): `systemctl show -p LoadState -p ActiveState -p Result`. A unit whose last run did not end in `success` is `unit-failed` (alert): a base backup that failed (Nov 24 2026: the 6 PM CST backup failed while the database was down and nothing told anyone). A timer or path that is loaded but not active is `unit-not-running` (alert); a unit the computer does not have is `unit-missing` (warn). Only read. |
| The row as read now | What is checked is only what the caller's `runs.units` names, so a call with no units list is answered `checked: false` (it would otherwise check nothing and answer green), and so is one that does not give `row_read_at` (when the row was read, in the same read as its runs) or whose `row_read_at` is more than settings.json `row.max_age_seconds` (300) before the check (a copy of a row read 44 minutes earlier named five units another apply had removed, Nov 25 2026). The answer gives `units_asked` (every unit asked of systemd) and `row_read_at`. |
| Not answering | An SSH failure is `unreachable` (alert). An address that is not an IPv4 address or a DNS name, or a missing host key, is answered `checked: false` with why, and no finding. |
| `pretend` | `{disks: {mount: percent}, engines: {unit: persons}, units: {unit: result}, wake_books: {unit: [wake, ...] or {refused: why}}, unreachable: true}` replaces what was read, so a caller sees those findings without making them. Each finding they make says `pretend: true`; a pretended engine is never asked to hold anyone. |

`hold_again: false` only tells an empty engine. Nothing else on the computer is changed.

## Keys and network

The administrator key is the held value `server-administration-ssh-key`, mounted as a 0600 file at the path the row's last argument names; it reaches only the hosts its vault entry names. The host key is pinned from the input (`host_key`), never learned on first use. SSH goes through the run's own proxy with `tools/administer-a-rented-host` (`administrationArguments`, `proxied`, `heldKeyFile`), packed beside this tool at `/opt/administer-a-rented-host`. Every value written into a remote command (listen address, unit, user, socket, person) is checked against its shape first.

## Source and checks

`do-work/check-from-inside.mjs` (Node's own `child_process` and the system `ssh`; no package). `test/check-from-inside.test.mjs` answers each script with a made-up computer (192.0.2.x): a disk under, at 86% and at 93%; an empty engine held again, one that stays empty, a pretended one, one with `hold_again: false`; an engine that owes no one; an engine that does not answer; a computer with no engine; one that does not answer; one with no usable address or host key; no units list, a row read too long ago and a row read just now with a unit the computer lacks; person folders measured with their largest files by a script that writes nothing; refused shapes; and the row's argv, key mount and packed helper. Run `node --test tools/check-a-computer-from-inside/test/check-from-inside.test.mjs`.

`workflow:check-every-computer-from-inside` (a row of the person's own `workflow_recipes`) runs it for every computer row every fifteen minutes, keeps each reading in `computer_readings` and tells each finding as a notice.
