# tools/use-your-tools-from-a-shell/

The `{cli}` command: any AI that can run a shell (Claude Code, Codex, Cursor, Gemini CLI, opencode, a script) sees the person's AIs and their tasks, gives, takes and hands on tasks, lists and runs Workshop tools and runs any engine operation, with no MCP connection of its own. Moved from an older repository (moved-from.json names where) with the files it installs beside itself (record:library:rea:F-0829, F-0183).

- **One road.** Every command is ONE call of the engine's one MCP tool, `do_one_thing_in_my_account {address, method, request_key, input}`, over MCP JSON-RPC at the account's door: the site's Mac app's local door when this computer has one (`local-door.mjs` reads the loopback port from the app's own declaration on every call), else the public origin. The only other addresses are the origin's own sign-in (OAuth with PKCE to a loopback redirect). The engine and `tools/hand-work-to-ais` decide; nothing here decides, stores or routes work.
- **Task moves are the task rows' own.** A task command reads the records its move needs (run-a-task-move.mjs: the tasks, the records named as assignees, a finish's acceptance target), runs the task row (`tools/plan-tasks-and-todo-lists`, packed under `packs/`) over them, and applies the writes the row answers, each conditioned on the value it was read at. When the person's own database keeps the tasks as table rows, `--store NAME` on any task command names the connection saved for it (kept for the next command, `tasks.store` in command.json), and each read and conditioned write is one statement run by the SQL tool (run-a-task-move.mjs `tasksIn`). Rows otherwise live in the person's own store and are reached there, in that store's own language. `{cli} publish [HELD_JSON]` answers this AI's own `ai` record as one `keep` row conditioned (`expected`) on the value the store holds now, handed in; `{cli} who --list FILE` names the AIs by the `list:ais` formula of the list handed in (without it they are shown unnamed). `{cli} schedule` lists and switches (`schedule on TOOL WAKE_ID --input FILE` hands the wake the person's own JSON object, at most 64 KiB, `-` for standard input, which it gives every run it starts under the row's own fields) the wakes the tool rows declare at the engine's wake owner (`wake:list`, `wake:switch`) and cancels one admitted run (`tools:cancel`); a wake is made, changed or removed in its row's `wakes` list. `--pin ID` on `op` and `schedule` (repeated, or a comma list, at most 64, each checked against `engine.pins`) sends the call's `pins` in the order given, beside method and input; with no `--pin` the call is sent as before.
- **The credential** is the account's existing key (the Mac app's Keychain item, else a 0600 file, else `{CLI}_KEY`) or the sign-in `login` kept. It is read into memory only and sent as a bearer token to the door; never printed, put on a command line or logged.
- **Every call carries one request key**, reused on every retry, so a retry is answered as the first call was.
- **It follows the Workshop copy.** The installed command in `~/.{cli}/cli/program` follows the Workshop copy this computer's engine reads where it stands, the place its product settings name (`install.follow` in `command.json`; nothing is installed): each run it finds that copy and runs it instead of itself, so a Workshop update reaches every command at once. `{cli} setup` run from a newer Workshop copy also rewrites each installed file that changed, and those files stay as the fallback when no Workshop copy is found. `{cli} update` says so.
- **Login is one plain journey.** `{cli} login` holds the person at this computer's engine (`POST /persons/add`) before it asks who they are, because a main-built engine serves no one it has not been told to hold; a kept sign-in the engine refuses makes login sign in again, never fail. The person reads one line (`You're signed in to <site> as <email>.`, the email being the pass's own claim), or one line saying what happened and the one thing to do. Every such sentence is a row of `command.json` `words`, and `test/command-words-are-plain.test.mjs` fails on any that holds a word, address, port or id from `tools/better-auth-official/pages/plain-words.json` (the one list the sign-in pages' words are checked against too). Technical lines (the address, the status, the engine's code) are `words.details` and print only with `--verbose`. The loopback callback sends the browser to the sign-in tool's own `/sign-in/done?result=done|old|failed`, which owns the look and the words.
- **Each engine is its own connection.** `{cli} login` with no address signs in at the site this command was installed from: the site's install line (`curl -fsSL <site>/cli/install | sh`, do-work/install.sh) writes that site's origin to the site file (`site_file` in the state folder), so the person types only `{cli} login`, and no site's address is kept in this shared tool. `--origin` names another engine, which gets its own sign-in. A kept sign-in or key the engine refuses, for any reason, never blocks a new sign-in: one browser sign-in is made at the site, and a new one refused too is said with the engine's reason. No sentence a person reads names an app or a Mac.
- **A computer with its own engine is reachable through its site.** After `login`, a computer whose computer config names where its engine listens is carried to the site's meeting point (`command.json` `carry`): the carrier packed from `tools/carry-a-computer-to-a-meeting-point` is installed under this computer's init row, its key is made once by the way row and kept where the sign-in is kept, and it reads that key through `{cli} carrier-key` (descriptor 3 only). It asks the site's meeting point with `{cli} op` for its port, certificate, ssh port and host key, so nothing about the meeting point is kept here. `test/command-carry.test.mjs`.
- **Settings are DATA** (`command.json`): the door, the work table, every refusal's words and every place written. A new AI app is one `skills` row and one `agents` row.
- **It names no product.** A site's own pages come from `do-work/write-site-pages.mjs ORIGIN PAGES_FOLDER SITE_FILE`: `cli/client.json` (this program's OAuth client), `cli/install` (the install line) and `cli/program/` (every `install.files` file and `files.txt`), filled with the site's origin and its site row's `name` and `cli` (the same row its sign-in pages wear). The install line writes them to the site file, and the command fills every `{site_name}`, `{cli}` and `{CLI}` (its command in capitals) in what a person reads, the folders it keeps (`~/.{cli}/cli`) and the environment names it reads (`{CLI}_KEY`, `{CLI}_ORIGIN`, `{CLI}_AGENT`) from them (`siteOf`, `speakFor`). With no site file it speaks for the name it was run by.

The local door itself (the Mac app's loopback server, its bind interface and how it checks the bearer) is the Mac app's and the engine's, not this folder's: this folder is the client.

## Routes (`need`)

`{cli} call TOOL JSON` sends the tool's run template `need` (the row's invoke block, read from tools:list with `tool`) as the `need` of the engine's one call tool, passed through untouched. A tool whose row needs nothing sends no route, so the engine's envelope is what it was. Pins (the person's computer order) are not sent yet: the CLI keeps no person settings, so there is no road to read them from.

## Replaying recorded writes

When an account's rows must be brought back (a restore from an older copy), the AIs' own transcripts on this computer hold every row they wrote. `records replay-from-transcripts --since TIME` reads each transcript file changed since TIME (subagent transcripts included) and keeps every `records:write` call (the name the older door gave its write, matched here as data) whose own result proves it succeeded:

- an MCP `do_one_thing_in_my_account` call (a tool_use row and its tool_result row, or one completed McpToolCall item);
- a shell `op @own-records records:write ARG`, read with the command's own argument parser, where ARG is literal text, a heredoc, a here-string, piped `echo`/`printf`/`cat FILE`, or a FILE the transcript itself wrote (Write, Edit, `cat > FILE <<'EOF'`) or that is unchanged on disk since the call answered.

Input built at run time (jq, a variable, a loop) is listed as unresolved, never guessed. The newest write of each record id wins by the time of its call; a null value is a removal; `expected` is dropped; a record whose newest value looks like a credential is listed by id only and never kept. It writes `summary.json`, `records.jsonl`, `conflicts.jsonl`, `skipped.jsonl` and `credential-like.json` (readable only by the user) into a new folder under `replay-inventory` beside the command's state folder, and sends nothing. Nothing is written back from here: whoever restores the rows keeps `records.jsonl` in the person's own store, in that store's own language.
