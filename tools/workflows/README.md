# workflows

For a committed publication, `node tools/workflows/do-work/publish-tool-catalog.mjs TOOLS_FOLDER --git-ref COMMIT` reads only that exact Git tree. It includes listed row sources and leaves working files unchanged. Without `--git-ref`, it reads the working folder as before.

Shared playbooks that any person's AI can follow step by step. Each playbook is a row of the person's list of workflows (its steps are rows of their list of workflow steps); the public ones are published into `published/` and made into `recipes/workflows.json`; the workflow engine that runs them is arriving here from `crates/workflow-engine` in the main Trillion repository.

## Keeping the tool catalog current

`published/tools.json` is derived from every folder's `tool-rows.json`, so any tool that lands makes it stale. It is therefore regenerated as part of the push, not by each tool's author: on the exact tip it is about to push, the pusher runs, from the repository root,

```
node tools/workflows/do-work/publish-tool-catalog.mjs tools
```

and, when `git status` shows `tools/workflows/published/tools.json` changed, commits that file alone as the last commit of the push. `test/tool-catalog.test.mjs` then holds that tip to the file (it fails when the committed file is not what the rows make), so a lane's own commits never need to touch it. The same holds for `recipes/workflows.json`, which comes from the two published workflow files (`node tools/workflows/do-work/rebuild-recipes.mjs`, `--check` to verify).

## Recipe shape

A recipe in `recipes/workflows.json` is `{ payload }` in `records`. The payload is a `workflow-recipe` row: `kind`, `id` (`workflow:` then lowercase words and dashes), `label`, `job`, `source` (where the playbook came from and which of its parts were not adopted, and why), `input_schema` (a JSON Schema with `"type": "object"`), and `steps`. Each step has `id`, `title`, `do` (what to do, naming the exact tool, address or screen and the exact input), `submit` (a JSON Schema for what the step hands back) and `checks` (rules that must hold before the step counts as done; the kinds are the rows of `recipe-check-kinds.json`).

A recipe names no person, product, keyword or subreddit of its own: those are inputs.

A method's shape (four sentences, sent on Saturday, the five rubric dimensions) is held by the step schemas. Every choice that belongs to the person is an input with the method's value as its default, or a row of the tool it runs: the finder's source row (`source_row`), the pacing row (`pacing` / `pacing_row`), which addresses to keep (`address_patterns`), `min_score` and `stalled_days`. ## When a recipe runs by itself

A recipe may carry `wakes`: the causes that start a run of it, each exactly the engine's wake declaration `{ id, on, budget, input }`, the field the engine reads from every Workshop row (a listed recipe row included), and `produces`, one line saying what a run makes that could be shared. A Workshop row's wake is off for every account until the person switches it on (`wake:switch`); a person may also declare their own wake, with their own input and time zone, as a `wake-declaration` record in their own records naming the recipe id as its tool. One malformed item refuses every Workshop row's wakes, so every wake is checked here before it ships. `on` names one cause: `record` (a record of a kind, or under an id prefix, changes in `own-records`), `time` (`at_ms` once, or `every_ms` from `from_ms`, optionally in an IANA `zone` that keeps the wall-clock time; without a zone, epoch 0 was a Thursday 00:00 UTC, so a Monday 09:00 UTC weekly wake is `from_ms` 378000000), `arrival` (from a `source`) or `host_event` (a kind the computer reports, with `match` on its fields). `budget` is drawn from the person's ledger per firing. `input.start_at` is the step a woken run starts at; a later start step reads the earlier steps' outputs of the person's last run of the recipe.

| File | Purpose |
|------|---------|
| `recipe-wake-causes.json` | What the engine's wake primitive takes, as DATA: one row per cause with its fields and shapes, the resources a record wake may watch, the host event kinds and their fields, the least budget a run needs and the ledgers, each read from the engine file it names at the commit it names. A new cause is a new row. |
| `read-data/wake-problems.mjs` | `wakeProblems(wakes, { stepIds, inputFields })`: every problem with a recipe's wakes list, judged only by the rows of `recipe-wake-causes.json`; `recipeProblems` calls it and also refuses a wake without `produces`. |
| `test/recipe-wakes.test.mjs` | Every cause accepted when well formed; a start step that is not a step, an input field the recipe does not take, a time with both or neither of `at_ms`/`every_ms`, `from_ms` or `zone` without `every_ms`, a zone the time zone database does not know, an unknown cause, field or key, an unwatched resource, a host event field its kind does not report, a budget below a run's least or above its ledger, a repeated id and a missing `produces` are refused; a cause added only as a DATA row is accepted; every shipped wake together fits the engine's cap. |

A recipe row has no `invoke` of its own: `source:workflow-recipes` names `invoke_with: "tool:start-a-recipe-run"`, so the engine runs every recipe row as that tool, with `input.row` set to the recipe's id and the switch's grant being that tool's rights. A recipe's steps are work for the person's AI, so the starter does none of them: it writes one record of kind `ai-job`, id `ai-job:<recipe id>:<request key>`, holding `status: "waiting"`, the recipe id and label, its steps, the input it was started with and the wake cause. The AI that next connects to the person's records lists waiting `ai-job` records, does the oldest and writes `status: "done"` with its result. A wake's request key is its cause key, so a firing that comes again finds its job and writes nothing.

## The checklist gate

A person's checklist is a JSON document `{ delivery_stages, default_delivery_stage, publish_phase, after_phase, stages: [{ id, checks: [{ id, check, routes, verify, must, per_option?, rule_id?, advisory_passes_at? }] }] }`. A piece is a folder with a header block of `key: value` tags; its items are the files the piece's globs find. The gate lists every required check of the chosen stages that applies to the piece (by route against the header tags, per-file media and the flags an item's own files prove) and has no current passing row, per item for a per-item check. Output is JSON; exit 0 passed, 1 open or failed, 2 unreadable.

Rows are lines in the piece's answers file: `{ check_id, option_id, answer, evidence, by, at, definition_pin, file_pins, check_pin }`. `definition_pin` is the BLAKE3 of the stable canonical JSON for that exact checklist definition; missing or changed definition pins require a fresh answer. `file_pins` is the BLAKE3 of the files judged; a row on other bytes is stale. A check a checker or gate answers counts only on that checker's own row with the reviewed `check_pin`, never on a person's row. `definition_pin` and machine `check_pin` bind independent things: the criterion and the checker code/rules. An `advisory` answer passes only at the delivery stages its check lists. A failed judgment rule on an item that rebuilds a picked item waits for the person's ruling and does not block.

The schema (JSON, `--schema`) names everything: `checklist`, `lock`, `piece` (header file and tag fields, answers file, record file, `on_first_gate` command, per-piece `config` and its defaults), `answers` (words, minimum evidence), `items` (folder patterns, media suffixes, lanes, rounds and moments, rebuild key, ruling words, proven flags, watch folders), `checkers` (answerer name, report keys and check-to-rule mapping, reviewed pins, `current_pins_command`, the sweep), `gates` (answerer name and the files that pin each), `runs` (the command per run mode; it prints as its last line `{ rows: [{ gate, answer, evidence }] }`, `{ problem }` or `{ not_measured }`), `audit` and `checklist_source` (the regular expressions that read the person's checklist text). Any value may be a `$ref`. A section a command needs and the schema lacks is refused by name.

## Dependencies

**Depends on:** `recipe-check-kinds.json` (read once when the validator loads) and the Node standard library. Kept as code: the five field shapes a row may name (`path`, `list`, `words`, `count`, `catalog`), because a new shape is a new test on a JSON value; the recipe and definition structure (`PIN`, step id patterns, actor-policy keys, `ask` and `check` step kinds), which is the engine's own closed format, not something a person extends; the recipes' steps name the tools the steps name (`tool:read-a-page-in-my-browser`, `tool:tell-the-person`), which the host offers.

**Depended on by:** nothing yet; the workflow engine will read `recipes/workflows.json` once it moves here. The list of workflows and the list of workflow steps are the person's rows in their account; the published files here are their public view, so every account gets the public workflows through the Workshop.

**The gate depends on:** python3 and BLAKE3 (the `blake3` Python module, else the `b3sum` command; without either a file identity is refused). A native computer run uses the Python module so it needs no child program; the direct command-line fallback can also use `b3sum`. The read-only native entry point invokes this same consumer, keeps criteria and checker pins unchanged, and does not write its lock, first-record file or pin cache. The writable entry point requires a separate `change-a-folder` grant. It runs the commands the person's schema names (`current_pins_command`, the sweep's `batch_command`, `runs.*.command`, `on_first_gate`) only in the modes that request them; a read-only gate skips `on_first_gate`. **Depended on by:** the person's own checklist, schema and pieces, which stay with the person; the Workshop holds none.

### Apply a library row through the same gate

An optional schema section `library_checks` connects captured advice to this checklist. It names `sources: [{ file, path?, fields: { id, statement, sources }, citation: { text, locators: [fields] } }]` and `applications: { file, path? }`. Files may be JSON arrays (or a dotted `path` to an array), or JSONL. Each application names `source_id`, a unique check `id`, `disposition` (`apply`, `held`, `not-applicable`), and `because`, with `assessed_source_identity` bound to the current canonical row's BLAKE3. A stale or absent applicability assessment cannot silently keep a row not-applicable. An applied or held row also names an existing checklist `stage`, a scoped `check`, its `verify` evidence and `routes`; `per_option` is optional. An applied row needs `support: { status: "supported", assessment, source_identity, source_indices: [0] }`, bound to the same current row and citing its source indexes. A missing, uncertain, unsupported or stale assessment, or a citation with no quotation and locator in the declared fields, holds the check. Quote presence and quote-match scores never establish support by themselves. A held row names `held_until` and cannot pass until its application is resolved. These rows are required checks of the existing gate, not another checker.

The source statement, citations, application reason and BLAKE3 identity of the complete current source row are part of the check definition. A changed source or application invalidates an earlier answer. Library advice is not automatically an instruction: unselected rows are reported in `library_coverage.unassessed`; applied, held and not-applicable rows are distinct. Removing an application removes its derived check without rewriting the base checklist or answer history. A malformed, missing or duplicate selected source is refused. The caller still verifies whether the source supports the claim and whether the observed application worked.

A gate reports `library_evaluation.evaluated` and each `not_evaluated` id with its reason, separately from definition counts in `library_coverage`. Set `library_checks.required_checks` to the check ids the current run must actually evaluate. A stage, route or item-scope mismatch then fails the gate instead of claiming the intended applications passed.

## Native checklist tools

### Resume source assessments for actual work

The existing gate CLI and native read/write-grant adapters also accept `library-pending --limit 8 [--source-id ID]`, `library-assess --json FILE`, and `library-remove --json FILE`. Pending is read-only. Assess and remove require the write-grant tool; `--read-only` also refuses both in the shared consumer. No workflow run, queue or global Library Done status is created.

Set `library_checks.context` to `{id, purpose, targets: [file paths]}`. Target bytes and this context DATA form its BLAKE3 pin. Application rows have `context_id` and `assessed_context_identity` alongside their existing source pin. Other contexts and legacy rows are retained. Changed targets hold existing applied checks and reopen exclusions. Changed sources reopen dispositions. The pending result has total counts, a bounded batch and bounded held ids; held assessments stay unresolved without blocking the next unassessed source. Removing an assessment reopens that source. Keep `required_checks` configured: removal cannot turn a missing intended check into a pass.

An assessment submission is `{context_identity, by, judgments: [...]}`. Each judgment contains the existing application fields, `assessed_source_identity`, the pending row's `prior_identity`, and `review: {assessment, evidence}` recording the continuous source context read and its locator. The consumer refuses changed source, target or same-context assessment reads, validates the proposed merged DATA through the actual gate composer, preserves unrelated rows, writes atomically and reads back. Equal retries do not duplicate rows. Removal uses the same submission envelope with judgments `{source_id, prior_identity, because}`; it removes only that context's matching assessment, and retries safely. Cooperating application writers lock the application directory. This is not atomic CAS against arbitrary source-file editors or remote account edits; fresh reads and final pin checks bound the observation rather than guaranteeing an external transaction.

Sources may select existing grouped import rows with `row_groups: "commands.input.records"`, filter exact fields with `where`, and omit authoritative override ids using `exclude_ids`. With `citation.row: true`, the source row itself supplies the quote and locator fields. This reads an existing imported snapshot directly instead of copying it into another store.

Offline source pins do not prove live account freshness. Before any application or gate claim, fetch every assessed source (including prior assessments) from its current account owner and preserve genuine readback. A source spec can require `live_snapshot: {file, at: "read_at", records: "records", max_age_seconds: 300, source_record_path?}`. The receipt contains an aware timestamp and exact full records. Missing, expired, future-dated or different records hold applications and reopen exclusions; new judgments are refused. This local comparison does not authenticate the receipt's author or perform the connector read. The caller owns that real operation and must refresh the actual source snapshot when a live edit differs. A passing shape check is never account freshness proof.

`tool:gate-a-piece-against-a-checklist` runs the existing checklist CLI through `do-work/native_checklist_gate.py` with a read-folder grant. It accepts inspection commands, retains current criterion and file pins, and writes no lock file, first-record file or pin cache. `tool:record-checklist-gate-changes` uses the same consumer with a separate change-folder grant for answer and report writes. The library and schema stay inside the granted folder. Commands are parsed as arguments, never shell text. Python BLAKE3 is required in the native runtime; inability to calculate an identity refuses the check.
