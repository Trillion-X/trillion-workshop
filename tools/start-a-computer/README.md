# Start a computer

Rent a Linux machine through a provider description the person supplies, or adopt a machine they already run over SSH, and make it run what its own computer row says: set it up, build each program from source on the machine itself, write the files the row renders, start what changed and read back its health page and monthly price. There is no release, no release feed and no copied program. Provider credentials arrive on private pipes, never in argv, a lease or an answer.

What a computer runs is its own row, a `record:computer`: its `address`, `name`, `os` and `arch`, and `runs`, the units, Caddy, set-up (`machine`), `unmanaged`, `absent` and `absent_users` it runs. A request hands the row in (`computer_row`, read by the caller from their own data; this tool reads no store), or names it as a file beside it (`computer_row_file`, resolved against the request file): the row is that file's JSON. A backup's `destination` in it is the path of the storage row's file, resolved against the computer row's file and read there.

## A program built from source on the computer

A unit whose row names `source` runs a program built from that source on the computer itself: `repository` (the git address the computer fetches from; any host, the address is the row's), `commit` (a full commit id), `build` (the argv run in the tree), `output` (the file the build makes) and `environment` (the `NAME=value` lines the build runs with: the toolchain's `PATH`, `HOME`, and its target and cache folders). Each `{field}` in `output` and `environment` is the unit's own value (`{builds}`, `{state}`) or the `{commit}` built (an engine's TRILLION_RELEASE_COMMIT, which it reports). A private repository names `credential`, the vault name of an SSH key that may read it, and `host_keys`, its host's known_hosts lines: the apply hands the vault's value (descriptor 5) only on the build's standard input, into an ssh-agent for that one fetch, and the fetch accepts no other host key. The program is the unit's `program` (a door's `door_file`) and lives in the unit's `builds` folder: `differences` reports a `current` that is not the row's commit, and `apply` has the computer fetch that commit into the copy it keeps at `builds/repository` (only what the copy lacks), build it as the unit's user (do-work/build-from-source.sh, one build at a time per builds folder), put the program at `builds/<commit>/<program>`, move `current` to it with one rename and restart the unit. A commit already built there is only made `current`. No source is copied from the computer that runs the apply. A target folder kept in `builds` is reused by the next commit. The toolchain is a download of the row's `machine` (below) with an `install` argv. The engine's unit uses `template: serve-computer`: it serves its computer config (`settings` written as JSON at `settings_file`; trillion-rust src/native_entry/computer.rs), its `key_file` is made once by set-up as 32 random bytes in one base64 line, and its `folders` (the persons folder) are made for its user; `serve` creates none of them.

## Keeping a program running on any kind of computer

`read-data/init-rows.json` holds one row per init system (launchd user agent and system daemon, systemd user and system unit, a Windows startup task, a Quadlet container): the file's path and text (a file of `read-data/unit-templates`), and the steps that unload and load it. `do-work/install-init.mjs` (`selectInit`, `renderInit`, `installInit`, `removeInit`) picks the row whose `match` holds for what a computer is and whose `scope` is asked for, writes the file, unloads what the label already ran (a refusal the row's `absent` matches means nothing ran), waits until the init system no longer knows it, and loads the new one. No operating system or init system is named in code; a new one is a new row, and a row nothing has proved says so in `proved_on`. Rendering shares `do-work/fill-fields.mjs` with a computer row's own units. `tools/carry-a-computer-to-a-meeting-point` is its first caller.

## Requests and commands

Run `node tools/start-a-computer/do-work/start-a-computer.mjs OPERATION ...`. Operations are `price REQUEST`, `rent REQUEST`, `start REQUEST`, `apply REQUEST`, `differences REQUEST`, `status LEASE`, `unit LEASE REQUEST` (the request's `unit`, a service name) and `remove LEASE`.

A provider is a description file the person keeps outside this folder; the tool names none. `machine.provider` (and `name.provider` for a DNS record) in a request is the path of that file, relative to the request file, and the lease keeps the path (`providerFile`, `namesFile`) so a status or removal needs only the lease. The description holds the provider's `base` URL, its `auth` header, the credential's vault handle (`vault_key`, never the value), its `requests`, and which request finds, creates, reads and removes a machine and its SSH key, reads a size's price, or points a name (`host`, `access_key`, `price`, `zone`, `record`); a description with no `base` is a machine already run, adopted at `placement.address`. Only the calls a description declares are sent. A new provider is a new file and no code change. Optional fields: `lease_label_key` (required with a `base`: the label every resource a lease owns carries, written into bodies and read back as `{lease_label_key}`), `async` (`ready_when`, `every_ms`, `tries`: a machine whose create answers before it runs is read until its `state_at` says ready), `first_boot` (`format`: the first-boot text the provider takes, given by the request as `machine.first_boot` `{format, text}` and spliced into a body as `{first_boot}`), `fingerprint` (`hash`, `encoding`, `prefix`: how the provider lists a stored public key), `terms_url` (what the person is billed, answered with the price). A description with `pull.line` is a machine nobody can reach from outside: a rent answers the one-time line (with `{token}` and `{name}`) to run on that machine, the lease waits, and the machine registers with `register LEASE ADDRESS` (the token on descriptor 3). A request's `machine.expires_at` (milliseconds, in the future, or none) is when the machine is given back; A computer row's `machine` object carries what only that computer needs, among it the `node` release (`version`, and per `uname -m` a `url` and `sha256`) its units' `node_bin` folders get; this tool pins none, and a computer with no unit that names a `node_bin` gets no node.

A start request names `lease_file`, `machine`, `name`, `ssh`, the computer row (`computer_row` or `computer_row_file`). A start rents (or adopts) the machine, applies the row exactly as `apply` does, caps the journal, and asks the row's `health` page through the public name; it answers the lease, the architecture, the price, what the apply wrote, built and restarted (`applied`) and that page's status (`health_status`). No user, folder or file name is built into the code. Local file paths are relative to the request file.

A computer's row (`request.computer_row`) may also name the sign-in unit: a unit with `template: serve-better-auth` runs official Better Auth from the Workshop's `tools/better-auth-official` folder (fetch its pinned commit, `npm ci` when the lock file changed, `node server.mjs`), with `workshop`, `repository`, `workshop_commit`, `tool_folder`, `node_bin`, `user` and `writable`; its `settings` object is written as JSON to `settings_file`; its secret is named by `secret_vault_key`: a start reads the value the person's vault holds under that name from descriptor 5 (a JSON object of vault name to value), sends it only on the SSH channel's standard input to `systemd-creds encrypt --name=<secret_name>` at `secret_file`, and the unit opens it with `LoadCredentialEncrypted`; no value is in the row, a unit, argv, a log or the answer. Set-up installs the apt packages settings.json `machine.packages` names and, into each unit's `node_bin` folder that has no node, the `machine.node` release for the machine kind, checked against its sha256; every unit names its `state` folder. `caddy.routes: ["better-auth"]` with `caddy.auth_port` sends `/api/auth/*` to it (`better-auth-discovery` adds `/.well-known/oauth-authorization-server*`). `better-auth-pages` sends the sign-in tool every address its own `tools/better-auth-official/pages/routes.json` lists (each page, what is under it, and its assets), so a page the tool adds is routed with no list in the row (a row that still names `auth_page_paths` is refused).

A unit's other sealed credentials are its `credentials` list, each `{vault_key, name, file, env?}`: a start seals each the same way (the descriptor-5 value by vault name, at `file`, under `name`) and the unit loads each with `LoadCredentialEncrypted`; one that names an `env` is handed to the program in that variable (the sign-in store's connection as `BETTER_AUTH_STORE_CONNECTION`: the server makes its own tables, so the unit runs no migration and installs no dev dependencies), and one with none is read by the program from its credentials folder by its name (the email sender's key). A unit's `settings_parts` puts files the person keeps into its settings: each key is a dotted place in `settings` and each value a path relative to the computer row's file, whose JSON goes at that place (the sign-in unit's `email.sender`, the person's description of their email provider's request).

A unit that runs from a Workshop copy pins its commit in `workshop_commit` (a full commit id), and the pin is in its unit file: a new pin is a changed unit, which `apply` writes and restarts. At each start the unit fetches the pinned commit into the copy it keeps at `workshop` (only what the copy lacks; a new computer starts an empty copy), checks it out, and runs `npm ci` only when that commit's `package-lock.json` is not the one installed last time (its git id is kept in the copy's `.git/npm-lock-id`). A unit's `folders` are made for its user, and its own `health` and `health_listen` are its boot check. A row's `machine` object replaces settings.json `machine` fields for that computer (its `packages`, and `firewall_allow`, null where another program keeps the firewall). A new unit is enabled and started. A row's `absent` lists files and folders the computer must not hold (a secret once kept in the clear, a program an old set-up left); `differences` reports each one there and `apply` removes it, a folder with everything in it. A systemd unit file in it is a unit the computer must not run: `apply` stops and disables it and removes its drop-ins before its file. `start-a-computer.mjs apply REQUEST_FILE` applies a computer's row to that running computer (`machine.address`, `ssh`, `computer_row`: the row itself, which the caller reads from their own data and hands in; this tool reads no store) and `differences REQUEST_FILE` answers what it runs that the row does not render.

Removal deletes only resources the saved lease owns; adopted machines are forgotten without deleting them.

## A database server and its backups

A computer row can run PostgreSQL from its own package and keep its backups, all rendered from the row. Who reaches the server is the database unit's `reach`, made into lines and files by `withReach` (do-work/render-what-a-computer-runs.mjs) before the row renders. The row's `machine` object gives what set-up installs before the units start (settings.json `machine` with the row's own fields over it): `packages`, `files` (path and text, written before the packages: a file that decides how one installs), `apt_sources` (`name`, `line`, `list_file`, `key_url`, `key_file` and `key_sha256`: the package source, the file that holds it, and the key it is signed by, refused unless the key's sha256 is the pinned one) and `downloads` (one program each: its `path`, and per machine kind `url`, `sha256` of the archive, `member` and `binary_sha256` of the unpacked program; or a whole toolchain: its `path` is a program the install makes, and `install` is the argv run inside the unpacked archive when that program is not there, such as a Rust release's `install.sh --prefix=...`). The tool names no address: every URL is the row's.

Five templates make the units. `serve-postgres` runs `postgres` as the unit's `user` on `data_dir` (`initdb` runs at the first start, data checksums on), reading the `settings_file` the row's `settings_lines` render, one line each, and the sealed credential `secret_name` (a file of `NAME=value` lines the server and the archive command it starts read). Its `files_read_at_start` (`{name, file}` each) are files another program on the computer keeps, such as the front door's certificate and key: systemd copies each into the unit's credentials folder at start (`/run/credentials/<unit>/<name>`, readable by the unit's user only, so the server's settings name that path and its user needs no right to the other program's folder). `watch-a-file` (a `.path` unit) starts its `runs` each time its `watch` file is written or replaced, and `restart-a-unit` restarts its `restarts` when that unit is running: together they make a renewed certificate reach the server that reads it at start. `run-a-script` is one run (`Type=oneshot`) of a script the row names in `script` (a file of read-data/scripts, written at `script_file`) with the sealed credential it names. `run-on-a-timer` runs a unit (`runs`) at `on_calendar`; a timer or path unit the row names that is not active is started at every apply. A file several units name (one script two jobs run) is written once, and every unit that reads a changed settings file, access file or script runs again. A unit that is not an HTTP server names `check_command`, a command run on the computer after its restart that must exit 0 (tried 12 times, 5 seconds apart), in place of the HTTP health row.

`reach` is a list of entries, each one way in: `for` (the tool or unit it lets in, for example `tool:run-sql-in-my-database`), `listen` (an address the server listens on), `hba` (rows in the server's own words: `type`, `database`, `user`, `address`, `method`), `credential` (the held name of the connection the caller uses), and `firewall_allow` and `routes` when it opens a port or a Caddy route. The server's `listen_addresses` is every entry's `listen` (none means no network listener), and its access file, at the unit's `hba_file`, holds every entry's `hba` rows and nothing else; a row's `settings_lines` may not set either. A database unit without `reach` keeps PostgreSQL's own defaults.

The scripts: `set-up-postgres-role.sh` reads a held connection string (`postgresql://ROLE:PASSWORD@HOST/DATABASE`) and makes the role, its password and the database it owns, with the right to connect taken from every other role (the store, not a query rule, keeps one person's rows from another's); `PG_MAKES_ROLES=yes` lets the role make roles of its own, which the role recipes of `tools/run-sql-in-my-database` need (a read-only share, standing or minted with `VALID UNTIL`). No computer makes a read role by default. `back-up-postgres.sh` takes a WAL-G base backup, switches the WAL segment and waits until the archive holds it, so each backup restores without a later one. `restore-a-postgres-backup.sh` fetches the newest backup into the run's private scratch folder, starts a second server from it with no network listener, replays the archived WAL and refuses unless the database `PG_DATABASE` is there.

## A public front door

A computer that serves the public door names a unit with `template: serve-door`. It runs the door program (`door_file`, for example `trillion-mcp-forwarder`) from the unit's own `builds` folder, as its own `user`. The door serves plain HTTP on the loopback address its `environment` names (a list of `NAME=value`, nonsecret settings only) and holds no key; the computer's Caddy in front of it holds TLS. The program is built from the unit's `source` on the computer, as above; nothing else moves `current`. A unit's `health` may name `host`, the Host its boot check asks for (the door answers only its own Host). In serving-computer-front-door, `door_transport_routes: ["door-over-tls"]` gives the upstream to `door_upstream` its TLS server name (`door_host`); a row whose `door_upstream` is `http://` leaves it out.

A computer row whose `caddy` has `front_door` makes the computer a public front door. Every such computer runs the Caddy the row names: `front_door.binary` is its path and `front_door.binary_files` gives, per machine architecture (`uname -m`), the address it is fetched from and the SHA-256 it is refused without (a row without the machine's architecture is refused); this tool pins no build and names no host and keeps its certificates in one shared store (`storage_env` names the address, password and encryption key, a host-held file the row never writes; `storage_server_cert` pins the store's TLS certificate), so any front door answers any name. A name no site block names gets a certificate on demand only when `door_upstream`'s `ask_path` (the forwarder's own `/origins/certificate`) answers 200 for it, and every such name and each of `door_hosts` is carried to `door_upstream` with its own Host and TLS name. The row's own sites are unchanged. `front_door` fields: `binary_urls`, `storage_server_cert`, `storage_env`, `ask_port`, `ask_path`, `door_upstream`, `door_host`, `door_server_name`, `door_hosts`.

A caddy row that names `site_file` gets that whole file from read-data/caddy-sites, each `{{field}}` filled from the row. A `{{routes}}` or `{{<name>_routes}}` slot is that list of route names (read-data/caddy-routes) in the row, and a line that is only an empty routes slot is left out. In serving-computer-front-door, `routes` goes in the home block and `every_name_routes` in the on-demand block, so `every_name_routes: ["better-auth"]` sends each attached name's `/api/auth/*` to the sign-in tool; `better-auth-webauthn` serves the passkey related-origins list at `/.well-known/webauthn`.

A computer that cannot be reached from outside (a Mac behind a home router) is carried to the front door by a program it starts that dials out (`tools/carry-a-computer-to-a-meeting-point`: a way row names the program, and the port at the front door is a hash of the computer's id). The front door's row names it in `caddy.carried_computers`, a list of `{ address, port }`: the computer's account address (lowercase letters and digits) and that loopback port. A site file with the slot `{{carried_computer_routes}}` sends `/a/<address>` and `/a/<address>/*` to `127.0.0.1:<port>` ahead of the forwarder's `/a/*`, with the door's own Host and no buffering. The route passes bytes only; the computer's own engine checks who calls. A row with no carried computers leaves the slot line out.

A front door can answer pages itself, and this tool holds none: the request hands them in as `pages_folder` (the person's own folder of files, a path relative to the request file), and a caddy row that names `pages_root` gets every file of that folder under `pages_root` on the computer (a text file as its text, any other as base64 that the computer decodes, so the bytes are the same). The site file serves a GET or HEAD for any of them through Caddy's `file_server`, a path without `.html` finding its page, and reaches no other host for a page. A row that names `pages_root` with no `pages_folder` is refused. The pages, their names, their contact address and their icons are the caller's own data.

## One name, no program in front of the engine

`caddy.site_file: "single-name-front-door"` makes a computer the front door of one name (`door_host`) with nothing between Caddy and the engine: Caddy keeps that name's certificate itself (no shared store, no attached names, no forwarder), answers the person's own pages from `pages_root` (the request's `pages_folder`), answers every other path 404, and sends the paths in `engine_paths` to the engine on `engine_listen` only when the row's `engine_routes` names `engine`. Its `routes` are read-data/caddy-routes files: the sign-in tool's (`better-auth`, `better-auth-pages`, `better-auth-discovery` for `/.well-known/oauth-authorization-server*`, `better-auth-webauthn`, `better-auth-home` for `/` to `/sign-in`). `caddy.carried_computers` (a Mac's `{address, port}` behind its outbound tunnel) sends that computer's `/a/<address>` to its loopback port ahead of `engine_paths`; an entry `{ paths, port }` instead sends those paths (for an engine that serves one door, `/mcp` and its `/.well-known/oauth-protected-resource` documents) to the port.

A computer row's `absent_users` names users the computer must not have (a tunnel user an old set-up made): `differences` reports each one there, and `apply` removes it with its home folder; a removed file under `/etc/ssh/sshd_config.d/` (listed in `absent`) makes `apply` check and reload the ssh server, so its user is no longer admitted.

A single-name front door (`site_file: single-name-front-door`) logs one JSON line per request to the journal: its method, its address without the query, its status and its duration, with every header, client address, cookie and query value removed, so a person's sign-in attempt is visible without keeping anything private.

## Source and checks

This is the existing canonical `start-a-computer` owner, recovered from its committed public origin implementation. Earlier product-filled DATA remains in that Git history; it is not a production default here. Recovery does not assert a new historical byte-copy baseline. The old `start-a-place` working files are outside this recovery's custody.

`test/start-a-computer.test.mjs` covers provider ownership, pricing, the lease lifecycle and a complete start that builds its engine from source; `test/apply-what-a-computer-runs.test.mjs` the apply, its source builds and boot checks; the other files the renderer, the site files, the sign-in unit, the Workshop pin and the init rows, all with synthetic rows. The shell commands target GNU/Linux; the tests answer them with made-up computers. Run `node --test tools/start-a-computer/test/*.test.mjs`.
