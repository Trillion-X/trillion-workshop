# Start a computer

Rent a Linux machine through a provider row or adopt an existing machine over SSH, install a caller-supplied engine release, write its config, start it and read back its sign-up page and monthly price. Provider credentials arrive on private pipes, never in argv, a lease or an answer.

The request must provide `product_settings`: a JSON object or an absolute JSON file path. `readRequest(file)` resolves a relative settings path against the request file. The settings must include `new_accounts.sign_in`, `sign_in_ways`, `sign_in_words`, `copies` and `copies_rules`. The tool supplies no product identity, engine program name, starting account fixture or release-feed default.

A start or update reads one settings snapshot before it contacts the machine. Those exact bytes are written as the remote settings file, and that snapshot's `new_accounts` fills missing config rows. Existing config rows remain intact; copies are the request's explicit policy or the supplied product policy bounded by the number of default holders. Copy counts follow the engine's admission bound and ordering rules. The engine remains responsible for validating each row's full schema.

A request's `release_feed` selects its signed feed. An omitted or null feed selects none for a start. An update requires an explicit feed; when its `releases` is an object rather than an absolute folder, the computer's existing releases folder is used.

## Requests and commands

Run `node tools/start-a-computer/do-work/start-a-computer.mjs OPERATION ...`. Operations are `price REQUEST`, `rent REQUEST`, `start REQUEST`, `status LEASE`, `install LEASE REQUEST`, `update LEASE REQUEST`, `rollback LEASE REQUEST BACKUP` and `remove LEASE`.

A start request names `lease_file`, `machine`, `name`, `ssh`, `port`, `engine` and `product_settings`. Engine inputs include its file, data environment name, data folder and release. Optional inputs include `place_config`, `config_from_release`, `default_places`, `copies`, `public_origin` and `release_feed`. Local file paths are relative to the request file. An update also accepts `layout` overrides; otherwise the running service's own config, current link, state folder, owner and release folder are discovered.

A computer's layout row (`request.host_layout`) may also name the sign-in unit: a unit with `template: serve-better-auth` runs official Better Auth from the Workshop's `tools/better-auth-official` folder (clone, `npm ci`, migrate, `node server.mjs`), with `workshop`, `repository`, `tool_folder`, `node_bin`, `user` and `writable`; its `settings` object is written as JSON to `settings_file`; its secret is named by `secret_vault_key`: a start reads the value the person's vault holds under that name from descriptor 5 (a JSON object of vault name to value), sends it only on the SSH channel's standard input to `systemd-creds encrypt --name=<secret_name>` at `secret_file`, and the unit opens it with `LoadCredentialEncrypted`; no value is in the row, a unit, argv, a log or the answer. Set-up installs the apt packages settings.json `machine.packages` names and, into each unit's `node_bin` folder that has no node, the `machine.node` release for the machine kind, checked against its sha256; a unit with no engine config names its `state` folder. `caddy.routes: ["better-auth"]` with `caddy.auth_port` sends `/api/auth/*` to it (`better-auth-discovery` adds `/.well-known/oauth-authorization-server*`). `better-auth-pages` sends the paths `caddy.auth_page_paths` lists (the sign-in pages, `/sign-in`, `/sign-up` and what is under them) to the same port; a path moved there leaves `forwarder_paths`.

A unit that runs from a Workshop clone names `workshop_feed` (`urls`, `public_keys`, `target`): its clone follows the newest entry of that signed feed one of the keys signed, or `workshop_commit` when the row pins one; `differences` reports a clone at another commit and `layout` moves it as the unit's user, restarting the unit only when its `tool_folder` changed. A unit whose template runs the engine (`serve-computer`, `serve-place`) names the `config` its `serve` reads and gives that config as `settings`: the config written there (its user's, 0600) is those settings with the product data's `new_accounts` under the row's own, so `layout` needs the request's `product_data` (the same manifest a start reads, which also writes `product_settings`). When the config names a `release_feed` and the unit's `releases` folder has no `current` yet, `layout` takes the feed's newest entry for the target the machine reports that one of the feed's keys signed, downloads it on the machine as the unit's user, refuses it unless its byte count and BLAKE3 content identity (`b3sum`) are the entry's, unpacks it beside the others with the entry as its `release.json`, and makes it `current` with the release's own `release switch`; from then on the engine follows the feed itself. A unit's `folders` are made for its user, and its own `health` and `health_listen` are its boot check. A row's `machine` object replaces settings.json `machine` fields for that computer (its `packages`, and `firewall_allow`, null where another program keeps the firewall). A new unit is enabled and started. A row's `absent` lists files the computer must not hold; `differences` reports each one there and `layout` removes it. `start-a-computer.mjs layout REQUEST_FILE` applies a computer's row to that running computer (`machine.address`, `ssh`, `host_layout`: the row or its `record:host-layout:<computer>` id) and `differences REQUEST_FILE` answers what it runs that the row does not render.

Updates back up replaced config, service unit, settings and release pointer. A failed service health check or sign-up response restores them. Explicit rollback uses the same backup and layout. Removal deletes only resources the saved lease owns; adopted machines are forgotten without deleting them.

## A public front door

A layout whose `caddy` row has `front_door` makes the computer a public front door. Every such computer runs the same Caddy (settings.json `caddy_front_door`: v2.11.9 with only the caddy-storage-redis module, both Apache-2.0, fetched by set-up and refused unless its SHA-256 is the pinned one) and keeps its certificates in one shared store (`storage_env` names the address, password and encryption key, a host-held file the layout never writes; `storage_server_cert` pins the store's TLS certificate), so any front door answers any name. A name no site block names gets a certificate on demand only when `door_upstream`'s `ask_path` (the forwarder's own `/origins/certificate`) answers 200 for it, and every such name and each of `door_hosts` is carried to `door_upstream` with its own Host and TLS name. The layout's own sites are unchanged. `front_door` fields: `storage_server_cert`, `storage_env`, `ask_port`, `ask_path`, `door_upstream`, `door_host`, `door_server_name`, `door_hosts`.

A caddy row that names `site_file` gets that whole file from read-data/caddy-sites, each `{{field}}` filled from the row. A `{{routes}}` or `{{<name>_routes}}` slot is that list of route names (read-data/caddy-routes) in the row, and a line that is only an empty routes slot is left out. In serving-computer-front-door, `routes` goes in the home block and `every_name_routes` in the on-demand block, so `every_name_routes: ["better-auth"]` sends each attached name's `/api/auth/*` to the sign-in tool; `better-auth-webauthn` serves the passkey related-origins list at `/.well-known/webauthn`.

## Source and checks

This is the existing canonical `start-a-computer` owner, recovered from its committed public origin implementation. Earlier product-filled DATA remains in that Git history; it is not a production default here. Recovery does not assert a new historical byte-copy baseline. The old `start-a-place` working files are outside this recovery's custody.

`test/start-a-computer.test.mjs` covers provider ownership, pricing, lease lifecycle, complete starts and updates, discovered layouts, failed-health rollback, exact settings snapshots and starting-row merges, using synthetic caller settings.

The shell commands target GNU/Linux. Tests discover a genuine GNU coreutils `mv` or `gmv` by its version, searching PATH and standard package bin folders. Each fixture links that executable as `mv` in its own PATH folder. Install coreutils when the discovery error names it; BSD `mv` is refused. Run plain `node --test tools/start-a-computer/test/start-a-computer.test.mjs`; an external PATH override is unnecessary. The shared test selector lives in `tools/process-session/test/target-tools.mjs`. Production SSH commands remain unchanged.
