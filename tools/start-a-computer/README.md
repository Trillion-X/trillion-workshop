# Start a computer

Rent a Linux machine through a provider description the person supplies, or adopt a machine they already run over SSH, and make it run what its own computer row says: set it up, build each program from source on the machine itself, write the files the row renders, start what changed and read back its health page and monthly price. There is no release, no release feed and no copied program. Provider credentials arrive on private pipes, never in argv, a lease or an answer.

What a computer runs is its own row, a `record:computer`: its `address`, `name`, `os` and `arch`, and `runs`, the units, set-up (`machine`), `unmanaged`, `absent` and `absent_users` it runs. A request hands the row in (`computer_row`, read by the caller from their own data; this tool reads no store), or names it as a file beside it (`computer_row_file`, resolved against the request file): the row is that file's JSON. A backup's `destination` in it is the path of the storage row's file, resolved against the computer row's file and read there.

## A program built from source on the computer

A unit whose row names `source` runs a program built from that source on the computer itself: `repository` (the git address the computer fetches from; any host, the address is the row's), `commit` (a full commit id), `build` (the argv run in the tree), `output` (the file the build makes, or a folder the build makes that holds `program` and everything it reads: the whole folder becomes `builds/<commit>`) and `environment` (the `NAME=value` lines the build runs with: the toolchain's `PATH`, `HOME`, and its target and cache folders). Each `{field}` in `output` and `environment` is the unit's own value (`{builds}`, `{state}`) or the `{commit}` built (an engine's RELEASE_COMMIT, which it reports). A private repository names `credential`, the vault name of an SSH key that may read it, and `host_keys`, its host's known_hosts lines: the apply hands the vault's value (descriptor 5) only on the build's standard input, into an ssh-agent for that one fetch, and the fetch accepts no other host key. The program is the unit's `program` (a door's `door_file`) and lives in the unit's `builds` folder: `differences` reports a `current` that is not the row's commit, and `apply` has the computer fetch that commit into the copy it keeps at `builds/repository` (only what the copy lacks), build it as the unit's user (do-work/build-from-source.sh, one build at a time per builds folder), put the program at `builds/<commit>/<program>`, move `current` to it with one rename and restart the unit. A commit already built there is only made `current`. No source is copied from the computer that runs the apply. A target folder kept in `builds` is reused by the next commit. The build runs at the lowest CPU priority in a systemd scope of its own with a memory cap and a time bound (settings.json `build_limits` by the kind of build, or the source's own `limits` { memory_max, seconds }): a build that outgrows its memory is ended alone, one that runs past its seconds is ended whole (`build_over_time`), the apply fails, and every program the computer serves keeps its memory and keeps serving. There is no memory high below the cap: it only slowed a build that outgrew it, for ever. The toolchain is a download of the row's `machine` (below) with an `install` argv. The engine's unit uses `template: tools/keep-an-engine-on-a-computer/serve-computer.service`: it serves its computer config (`settings` written as JSON at `settings_file`; trillion-rust src/native_entry/computer.rs), its `key_file` is made once by set-up as 32 random bytes in one base64 line, and its `folders` (the persons folder) are made for its user; `serve` creates none of them.

A unit whose row names `slots` is never stopped by a deploy. `slots` maps two or more slot names to the values each has of its own, at their dotted paths in the unit (`{"a": {"settings.listen": "127.0.0.1:7199", "health_listen": "127.0.0.1:7199"}, "b": {...}}`): each slot is its own unit (`<unit>-<slot>.service`), with its own settings file (`computer-<slot>.json`) and its own build link (`builds/current-<slot>`), and only one runs. When the slot that runs is behind its row (another commit, a file it reads changed, a credential sealed anew), `apply` builds the release into the other slot while the running one serves, starts it, and only once it answers its boot check makes it the slot that starts with the computer and stops the one that ran (`systemctl disable --now`): that one answers its health page 503, keeps taking calls for its hold, then finishes the calls it holds, for up to the row's `stop_seconds` (`TimeoutStopSec`; `KillMode=mixed`, so the tool runs it started are not ended with it). A slot that never answers is stopped again and the slot that ran keeps serving. A unit may also name `switch_check_command`, run on the computer with `{unit}` and `{listen}` filled after the new slot answers and before the one that ran stops, tried every 5 seconds for `switch_check_seconds` (default 60): a slot that answers but has not taken up what the one that ran was keeping fails the same way. The web server in front sends each call to the slot that answers its health page (the Caddy kit's `pools`: tools/keep-a-caddy-front-door-on-a-computer). A unit whose first start is long names `health.wait_seconds`. A unit with no `stop_seconds` gets settings.json `unit_defaults`. A new slot is started beside the one that runs only when the computer's MemAvailable holds the unit's `start_headroom_bytes` (else the running slot's MemoryCurrent) plus settings.json `slot_start.margin_bytes`; otherwise the apply is refused before anything stops and the slot that runs keeps serving.

A unit with slots may name `live_links`: fixed paths, each mapped to the path of a slot's own file with `{slot}` where the slot's name goes (`{"/var/lib/<user>/agent.sock": "/var/lib/<user>/agent-{slot}.sock", "/etc/<name>/computer.json": "/etc/<name>/computer-{slot}.json"}`). Each slot then names its own file (its own `settings.agent_socket` in `slots`), and a reader of the fixed path (a vault read, a person added on the engine's agent socket) reaches the slot that runs. A switch points every link at the new slot once it answers its checks and before the slot that ran stops, each with one rename (`ln -sfn` beside it, `mv -T` over it), so a reader finds the old target or the new one and never no file; the engine-only apply does the same. `differences` reports a link that does not point at the slot that runs, and `apply` points it back with no switch and no restart. Why: on Nov 24 2026 at 8:06 PM CST both slots of an engine bound one socket path; the slot being retired was killed for memory, restarted, and took the path from the slot that served, and every call on that socket was refused until the next switch.

A unit whose `source` names `prebuilt` (`blake3`: the 64 hex digits of the program's BLAKE3) beside its `commit` runs a program built elsewhere, so a computer too small to compile while it serves never builds. The computer running the apply keeps such files in its store (settings.json `prebuilt_store`), each named by its BLAKE3; the apply refuses one whose bytes are not that name, sends it on the SSH channel's standard input (compressed with zstd when the computer has `zstd`, about a quarter of an engine's size), keeps it at `builds/<commit>/<program>` only when its sha256 there is the sent bytes', and moves `current` (or the slot's link) to it. A commit already placed with those bytes is only made `current`. No repository, build or toolchain is needed for it.

A unit built from source keeps its older builds only so far: every `current` and `current-<slot>` link's build and the newest `keep_builds` (the unit's own number, else settings.json `builds.keep`, 5) of each `builds` folder stay, and a commit beyond them is a difference that `apply` removes, with its `build-<commit>.log` and `.memory-events`, before it builds the next one (do-work/keep-recent-builds.mjs; the listing, keep-recent-builds.sh, removes nothing). Units that share a folder (the slots of one program) are one folder. The answer's `builds_removed` names what went.

## Keeping a program running on any kind of computer

`read-data/init-rows.json` holds one row per init system (launchd user agent and system daemon, systemd user and system unit, a Windows startup task, a Quadlet container): the file's path and text (a file of `read-data/unit-templates`), and the steps that unload and load it. `do-work/install-init.mjs` (`selectInit`, `renderInit`, `installInit`, `removeInit`) picks the row whose `match` holds for what a computer is and whose `scope` is asked for, writes the file, unloads what the label already ran (a refusal the row's `absent` matches means nothing ran), waits until the init system no longer knows it, and loads the new one. No operating system or init system is named in code; a new one is a new row, and a row nothing has proved says so in `proved_on`. Rendering shares `do-work/fill-fields.mjs` with a computer row's own units. `tools/carry-a-computer-to-a-meeting-point` is its first caller.

## Requests and commands

Run `node tools/start-a-computer/do-work/start-a-computer.mjs OPERATION ...`. Operations are `price REQUEST`, `rent REQUEST`, `start REQUEST`, `apply REQUEST`, `differences REQUEST`, `status LEASE`, `unit LEASE REQUEST` (the request's `unit`, a service name) and `remove LEASE`.

A provider is a description file; the tool names none. `providers/` holds the published ones, one file per provider, each named for its provider: the same calls for everyone, and a starting `placement` a request's `machine.placement` replaces field by field. A person's own provider is a file kept anywhere else. `machine.provider` (and `name.provider` for a DNS record) in a request is the path of that file, relative to the request file, and the lease keeps the path (`providerFile`, `namesFile`) so a status or removal needs only the lease. The description holds the provider's `base` URL, its `auth` header, the credential's vault handle (`vault_key`, never the value), its `requests`, and which request finds, creates, reads and removes a machine and its SSH key, reads a size's price, or points a name (`host`, `access_key`, `price`, `zone`, `record`); a description with no `base` is a machine already run, adopted at `placement.address`. Only the calls a description declares are sent. A new provider is a new file and no code change. Optional fields: `lease_label_key` (required with a `base`: the label every resource a lease owns carries, written into bodies and read back as `{lease_label_key}`), `async` (`ready_when`, `every_ms`, `tries`: a machine whose create answers before it runs is read until its `state_at` says ready), `first_boot` (`format`: the first-boot text the provider takes, given by the request as `machine.first_boot` `{format, text}` and spliced into a body as `{first_boot}`), `fingerprint` (`hash`, `encoding`, `prefix`: how the provider lists a stored public key), `terms_url` (what the person is billed, answered with the price). A description with `pull.line` is a machine nobody can reach from outside: a rent answers the one-time line (with `{token}` and `{name}`) to run on that machine, the lease waits, and the machine registers with `register LEASE ADDRESS` (the token on descriptor 3). A request's `machine.expires_at` (milliseconds, in the future, or none) is when the machine is given back; A computer row's `machine` object carries what only that computer needs, among it the `node` release (`version`, and per `uname -m` a `url` and `sha256`) its units' `node_bin` folders get; this tool pins none, and a computer with no unit that names a `node_bin` gets no node.

A start request names `lease_file`, `machine`, `name`, `ssh`, the computer row (`computer_row` or `computer_row_file`). A start rents (or adopts) the machine, applies the row exactly as `apply` does, caps the journal, and asks the row's `health` page through the public name; it answers the lease, the architecture, the price, what the apply wrote, built and restarted (`applied`) and that page's status (`health_status`). No user, folder or file name is built into the code. Local file paths are relative to the request file.

A computer's row (`request.computer_row`) may also name the sign-in unit: a unit with `template: tools/better-auth-official/on-a-computer/serve-better-auth.service` runs official Better Auth from the Workshop's `tools/better-auth-official` folder (fetch its pinned commit, `npm ci` when the lock file changed, `node server.mjs`), with `workshop`, `repository`, `workshop_commit`, `tool_folder`, `node_bin`, `user` and `writable`; its `settings` object is written as JSON to `settings_file`; its secret is named by `secret_vault_key`: a start reads the value the person's vault holds under that name from descriptor 5 (a JSON object of vault name to value), sends it only on the SSH channel's standard input to `systemd-creds encrypt --name=<secret_name>` at `secret_file`, and the unit opens it with `LoadCredentialEncrypted`; no value is in the row, a unit, argv, a log or the answer. Set-up installs the apt packages settings.json `machine.packages` names and, into each unit's `node_bin` folder that has no node, the `machine.node` release for the machine kind, checked against its sha256; every unit names its `state` folder. The unit file and the web server's routes to it are the tool's own, in tools/better-auth-official/on-a-computer.

A unit's other sealed credentials are its `credentials` list, each `{vault_key, name, file, env?}`: a start seals each the same way (the descriptor-5 value by vault name, at `file`, under `name`) and the unit loads each with `LoadCredentialEncrypted`; one that names an `env` is handed to the program in that variable (the sign-in store's connection as `BETTER_AUTH_STORE_CONNECTION`: the server makes its own tables, so the unit runs no migration and installs no dev dependencies), and one with none is read by the program from its credentials folder by its name (the email sender's key). A credential that says `held_on: "computer"` is held only in the vault of the engine on the computer it runs on (a key made there with `secrets put`): the applier never asks its own vault for it (apply-a-computer-row leaves it out of the `held_value_reader` names, and a value handed on descriptor 5 under its name is not used), and the apply reads it on the computer by the reader the row names once in `runs.vault_read`: `{command, user?, answers_on?}`, the reader's command line with one argument exactly `{name}` where the vault name goes, the account it runs as (an engine answers its vault only to its own account) and the descriptor it writes the value on (1 when absent; an engine's `secrets --through-engine CONFIG PERSON read {name}` writes on 3, and gets a pipe there made by its own account). The value goes from the reader into a shell variable on the computer and from there into `systemd-creds encrypt`: never argv, a file, a log or the SSH channel. A sealed file that opens to another value than the computer's vault holds is sealed again; one the vault answers nothing for is kept; an absent one the vault holds nothing for is refused by its vault name before anything changes. Tests: test/sealed-from-the-computers-vault.test.mjs. A unit's `parts` fill it from what the person keeps: each key is a JSON Pointer (RFC 6901) into the unit (`/settings/...` for its settings, `/site/...` for a web server's site), and each value `{file, pointer}` is the value at that pointer of a file read relative to the computer row's file (no pointer: the whole file). The tool names no setting and no field, so an engine door's `/doors/0/server_name` can come from `/called` in the person's own description, and the sign-in unit's `/email/sender` from their email provider's description. A part may instead be `{workshop_file, pointer}`: a JSON file under `tools/` of the Workshop the apply renders from, so a definition kept once in its tool's folder is the same bytes on every computer that names it (an engine door's `/settings/doors/0/show_tools/0/description` is `/description` of `tools/ui/show/run-the-screen-an-ai-wrote/show-a-screen.json`); an engine release accepts such a part into the engine's settings only. Tests: test/sign-in-host.test.mjs, test/apply-what-a-computer-runs.test.mjs.

A unit that runs from a Workshop copy pins its commit in `workshop_commit` (a full commit id), and the pin is in its unit file: a new pin is a changed unit, which `apply` writes and restarts. At each start the unit fetches the pinned commit into the copy it keeps at `workshop` (only what the copy lacks; a new computer starts an empty copy), checks it out, and runs `npm ci` only when that commit's `package-lock.json` is not the one installed last time (its git id is kept in the copy's `.git/npm-lock-id`). A unit's `folders` are made for its user, and its own `health` and `health_listen` are its boot check. A unit that names `uid` (a number) has its user made with that id, and every set-up checks it: an account that already has another id is refused (exit 2) and left as it is, because something else on the computer names the unit by its id (an engine's socket rows admit a peer by the kernel's peer credentials). A row's `machine` object replaces settings.json `machine` fields for that computer (its `packages`, and `firewall_allow`, null where another program keeps the firewall). A new unit is enabled and started. A unit's `owned_folders` (a site's pages) hold only the files the row renders: a stray is a difference and `apply` removes it, a changed file keeps no copy beside it, and their files are read in one command (each file's SHA-256 against the rendered bytes) and written in one command (one tar unpacked at / as root, each file 0644), not one command per file (do-work/files-in-one-go.mjs: a front door of about 1,300 pages took about 20 minutes an apply on Nov 20 2026). A row's `absent` lists files and folders the computer must not hold (a secret once kept in the clear, a program an old set-up left); `differences` reports each one there and `apply` removes it, a folder with everything in it. A path the row both writes (a rendered file, or a credential a unit seals) and lists in `absent`, or one inside a folder or unit listed there, is refused before the computer is read (`namedAndAbsent`): take it out of one of them. A systemd unit file in it is a unit the computer must not run: `apply` stops and disables it and removes its drop-ins before its file. `start-a-computer.mjs apply REQUEST_FILE` applies a computer's row to that running computer (`machine.address`, `ssh`, `computer_row`: the row itself, which the caller reads from their own data and hands in; this tool reads no store) and `differences REQUEST_FILE` answers what it runs that the row does not render.

Removal deletes only resources the saved lease owns; adopted machines are forgotten without deleting them.

## What a computer installs and runs

The row's `machine` object gives what set-up installs before the units start (settings.json `machine` with the row's own fields over it): `packages`, `files` (path and text, written before the packages: a file that decides how one installs), `apt_sources` (`name`, `line`, `list_file`, `key_url`, `key_file` and `key_sha256`: the package source, the file that holds it, and the key it is signed by, refused unless the key's sha256 is the pinned one) and `downloads` (one program each: its `path`, and per machine kind `url`, `sha256` of the archive, `member` and `binary_sha256` of the unpacked program; or a whole toolchain: its `path` is a program the install makes, and `install` is the argv run inside the unpacked archive when that program is not there, such as a Rust release's `install.sh --prefix=...`). The tool names no address: every URL is the row's.

A unit names its files by path, and start-a-computer keeps no list of programs. Its `template` (none for a unit whose file the computer already has, a package's own: only its drop-ins and files are written), its `script` and each of its `drop_ins` is a file inside the Workshop (a relative path, read at the commit this tool runs at, never leaving the Workshop) or an absolute path to the person's own file; a path that names no file is refused. The program's own folder publishes them; the files under `read-data/unit-templates` and `read-data/scripts` are read the same way. A drop-in is written under its file's name without the extension.

A unit may name `prepare`: a module of its program's own folder, named by path like a template. Before the row renders, start-a-computer hands the unit, and what the request hands every module (`pages`, the files of its `pages_folder`), to that module's `prepare` export, which answers `{unit, firewall_allow?}`: the unit as the computer runs it and the ports it opens, which join the row's own. The unit's `files` are written beside it, each `{path, text}` with optional `binary` (the text is base64, decoded on the computer), `check` (an argv run on the new text, `{file}` its path, before it replaces the live file: a site file its own server validates) and `then` (the argvs that apply it once it changed, run after the units start: a reload; an empty list for a file nothing reads again). A changed file with no `then` restarts its unit. This is where a program's own grammar lives (PostgreSQL's access file: tools/keep-a-postgres-database-on-a-computer; Caddy's site file and pages: tools/keep-a-caddy-front-door-on-a-computer); start-a-computer reads none of it.

A unit may name `pages_hosts`: the host names whose pages it was built with (its `source.commit` is the commit those pages were built from). Before anything is written, each host's link in the request's `pages_folder` (followed to its realpath) must point into that commit; a link that points elsewhere, or is missing, refuses the whole apply and names the host, the link's target and the unit's `source.commit`. So pages and the program that serves them switch together: a site whose links are repointed to a new build is released at that commit, or its apply is refused. A unit without `pages_hosts` is not checked.

A unit's `files_read_at_start` (`{name, file}` each) are files another program on the computer keeps, such as a web server's certificate and key: systemd copies each into the unit's credentials folder at start (`/run/credentials/<unit>/<name>`, readable by the unit's user only, so the server's settings name that path and its user needs no right to the other program's folder). `watch-a-file` (a `.path` unit) starts its `runs` each time its `watch` file is written or replaced, and `restart-a-unit` restarts its `restarts` when that unit is running: together they make a renewed certificate reach the program that reads it at start. `run-a-script` is one run (`Type=oneshot`) of a script the row names in `script` (a file named by path, written at `script_file`) with the sealed credential it names. `run-on-a-timer` runs a unit (`runs`) at `on_calendar`; a timer or path unit the row names that is not active is started at every apply. A file several units name (one script two jobs run) is written once, and every unit that reads a changed settings file, script or file of its own (`files`) runs again. A unit that is not an HTTP server names `check_command`, a command run on the computer after its restart that must exit 0 (tried 12 times, 5 seconds apart), in place of the HTTP health row. A check that knows trying again cannot pass (the door refused the unit's rights, say) exits settings.json `check_command.stop_trying_exit` (77), and the apply fails at once with its words; the same holds for a container's ready command and a `switch_check_command`.

`run-a-script-with-its-credentials.service` is `run-a-script` with every credential of the unit's `credentials` list loaded and no `secret_*` of its own, so a one-shot job can read a value held only in the computer's own vault (`held_on: "computer"`, sealed on the computer through `runs.vault_read`), which never leaves that computer.

A unit whose `template` is `read-data/unit-templates/keep-a-disk-in-a-file.service` gives a folder a disk of its own: the file `image`, `size` taken at once (fallocate), with its own ext4 filesystem, mounted at `mount` for `owner`, started `before` the units that write there (they name it in a drop-in's `Requires=` and `After=`). What they write can fill only that disk, never the computer's own, and the disk is its own line in df, so the computer's check reads its used percent. The file is made once; a file that is there is mounted as it is.

## The names a row says answer at its address

A row's `runs.names` lists the names that answer at the computer's `address`, each `{ host_name, provider, adopt? }`: `provider` is a DNS provider description (an absolute path of the person's own file, or one published in this Workshop under `providers/`), and its key reaches the run on descriptor 5 under the description's `vault_key`, like every other held value. `differences` reports a name that answers with anything but the row's address; `apply` keeps it answering with that address alone (tools/move-the-public-door `keepHealthyRecords`): the address is added first, records this row made for other addresses are removed after, other records are untouched, and a record nobody marked as this row's is refused unless the row says `adopt` (the name is the row's: a record made by hand becomes the row's as it is). So a person's address and its DNS come from their own row and their own provider; the tool names no domain. A provider whose records keep no owner mark (Namecheap: `providers/namecheap.json`, an MCP server with `record.owner_by: "address"`) owns a name's address records only where the address is the row's own; a name holding another address is refused unless the row says `adopt`, and nothing else at the name or in the zone is sent a change. With `adopt: true` the name is the row's alone: after the row's address record is added, every other record of the provider's `address_types` at exactly that host name is removed (the parking A, a CNAME, a redirect), and each is named in the apply's `removed` (by its content). Records of other names, other types and the rest of the zone are left alone. A record the provider's list omits (`omitted_at`: Namecheap's redirect records, URL, URL301 and FRAME, which its delete call does not take) cannot be removed by this tool; the apply names it as `unremovable` (type and host) so it is removed by hand at the provider. Example, a computer row that keeps `files.example.org` at its address: `"names": [{"host_name": "files.example.org", "provider": "tools/start-a-computer/providers/namecheap.json"}]`. The Namecheap description has `transport: "engine"`: it holds no credential; each call is run through the engine that holds the person's connections, by the command line the computer row names once as DATA in `runs.engine_call` (its program first and one argument exactly `{run}` where the call's JSON goes), or the request's own `engine_call` over it; one of them is checked for every name before any call, and this tool names no engine. A DNS provider that does not answer is asked again (after 3 s, then 10 s); a name whose provider is still silent is left as it was and reported `unanswered`: `apply` then exits 4 (its units are applied; 1 stays a failed apply), and `differences` lists the name as not known. Every other refusal of a name still ends the apply, and the engine signs in to and refreshes the person's Namecheap connection. A description with a held key instead names its key by `vault_key`, as before.

## Resizing a rented machine

`node do-work/resize-a-machine.mjs LEASE_FILE SIZE`, with the provider's API key on stdin (piped, never argv), changes a running rented machine to another size of the same provider and keeps its disk. The lease names its provider description, which must carry a `resize` job (a published one under `providers/` and the made-up `made-up-providers/rented-machine.json` do). `resizeMachine` in `do-work/rent-a-machine.mjs` is the same operation for a caller that already holds a client.

| Step | Row request | Call |
| --- | --- | --- |
| read the machine | `read_server` | GET the server; it must be `running_state`, and one already at SIZE answers `{unchanged: true}` |
| price both sizes | `read_size_price` | the monthly price of the machine's size and of SIZE at the lease location (refused before any change when one has none) |
| power off | `power_off_server` | POST its action; the action is polled with `read_action` |
| change the type | `change_server_type` | POST `{server_type, upgrade_disk: false}`: the disk is kept (a disk upgrade is refused) |
| power on | `power_on_server` | POST its action, polled the same way |
| read back | `read_server` | the type and status it reads; the lease takes that type |

Every poll waits `every_ms` and is made at most `tries` times after the first; both come from the row's `resize` job. An action that ends in error (`action_words.failed`) or stays unfinished ends its step. A failure after the power-off still asks for the power-on, and the error says what the machine reads back as. The answer is `{from, to, price_from, price_to, off_at, on_at, seconds_down, status}`. After a resize the lease holds the new size, so a `start` of the old placement is refused as another placement.

## A computer key kept sealed

An engine unit that names `key_sealed_file` (an absolute path, such as `/etc/<name>/computer-key.cred`) has no plain key file. Its `template` is `tools/keep-an-engine-on-a-computer/serve-computer-key-sealed.service`: systemd unseals the file (`LoadCredentialEncrypted=computer-key:<file>`) into the unit's own credentials folder, which is memory, and a one-line shell opens that credential on descriptor 4 and becomes the engine, so the engine's config says `secrets.unlock.key_descriptor: 4` and no key file (the engine takes descriptor 4 or above; it reads one base64 line once and closes it). systemd has no setting that names a credential on a descriptor, which is why the shell is there. The apply seals the key when the computer lacks the file: from the plain `key_file` the unit still names (the same bytes, so the person's vaults still open), else from 32 new random bytes in one base64 line; set-up then makes no plain file. The unit restarts, and the plain file is removed only after the unit answers its health row and the sealed file opens to the plain file's own bytes (a different key keeps the plain file and fails the apply). `differences` reports a missing sealed file and a plain copy still held. A unit whose settings still name its plain `key_file` is refused, and a row that names only `key_file` runs as before. Sealing needs systemd 250 or later (`systemd-creds`); the seal is bound to the computer's own systemd secret (`/var/lib/systemd/credential.secret`), so it is not moved to another computer. do-work/keep-the-key-sealed.mjs.

## Health, meeting points and removed users

A unit's `health` may name `host`, the Host its boot check asks for (a web server that answers only its own Host); its `health_listen`, or the row's, is the address the check asks, and a restarted unit with neither is refused.

While an apply runs, `do-work/probe-while-applying.mjs` asks the computer's names one GET at a time until it is stopped, and with `--log FILE` keeps every request (time, URL, status, milliseconds, the server's `x-answered-by` when it says) so a slow one names its target. It measures its own lateness: a request sent while the computer running the probe was busy (its timer late by more than `--lag-ms`) is counted apart as `slow_while_lagging`, never as the served computer's slowness. Its summary gives p50, p99 and every slow request. A probe run across the internet sees the round trip (about 100–400 ms from a home Mac to a rented computer), so a switch is judged by what it adds to the probe's own baseline, not by a bare time.

The same probe runs as a standing probe on any computer, to ask sites from a second place: a unit of that computer's row with `template` `init-systemd-system.service`, `drop_ins` `[read-data/unit-templates/writable.conf]` (its `writable` folder is the one it may write), `script` `tools/start-a-computer/do-work/probe-while-applying.mjs` placed at its `script_file`, a `node_bin`, and a `command` that runs the probe with `--every-ms`, `--log FILE --log-max-bytes N` and the URLs. The URLs are the row's own data, each with whatever query its owner wants on a check (`?utm_content=check`). With `--log-max-bytes` the probe keeps nothing in memory and prints no summary: each request is one JSON line (`at`, `url`, `status` or `error`, `ms`, `lag_ms`), and a line that would take the file past N first moves it to `FILE.1`, so the log never holds more than about 2 N. Round-robin over U URLs every `--every-ms` asks each URL once every U x every-ms.

A site program served on one socket (a unit whose `runtime_directory` is `sites/<name>`) restarts in place, and its requests wait. `do-work/give-a-site-program-slots.mjs COMPUTER_JSON NAME [start|retire] [--slots a,b]` edits a computer row file in place so the program runs in slots instead, each on its own socket in `/run/sites/<name>-slots` (`runtime_preserve: yes`, so a slot's stop never removes the folder), and the front door's `site_sockets` sends the name to the first socket that answers. It takes two applies. `start` adds the slots and lists the old socket last, so the old unit (no longer in the row) serves until a slot answers. `retire`, once that apply has switched, puts the old unit's file in `runs.absent` and drops its socket. One apply would leave the name with no program, because the apply removes what `runs.absent` names before it switches slots and before the front door reloads.

A computer that cannot be reached from outside (a Mac behind a home router) is reached through a meeting point: a program it starts dials out (`tools/carry-a-computer-to-a-meeting-point`), and the engine on the public computer passes a signed-in person's calls to their own computers. A row's `meeting_point` (`{ way, values }`) names the way row whose host half that computer runs (for `ssh-certificate`: one `carry` user and one ssh server file that admits a certificate the engine signed, on its own port alone); its files are written like every other and its commands (`then`) run after one of them changed. No route, user or file is made per computer.

A computer row's `absent_users` names users the computer must not have (a tunnel user an old set-up made): `differences` reports each one there, and `apply` removes it with its home folder; a removed file under `/etc/ssh/sshd_config.d/` (listed in `absent`) makes `apply` check and reload the ssh server, so its user is no longer admitted.

## Changing a computer's row and applying it

`node tools/start-a-computer/do-work/apply-a-computer-row.mjs [--dry-run | --plan] --targets FILE REQUEST_FILE`, with the database connection string on descriptor 3 (the first stage of a pipe or a redirect, never argv), reads a computer's row, makes the request's edits, writes it back, and applies it with the start-a-computer of a named Workshop commit. The request is `{ computer, workshop_commit, edits, links? }`. Each edit is `{ at, from?, to?, remove?, add? }`: `at` is a path of dotted keys whose array steps may select an element by a field (`runs.units[unit=example.service].source.commit`) or by position (`runs.units[0]`); `from` is compared with what is there before `to` is written or `remove` deletes it; `add` appends to an array unless an equal element is there. An edit that cannot be made, a `from` that does not match, or a selector that matches none or several, refuses the whole request before anything is written. `links` is `{ folder, set: { name: target } }`, the symlinks of a pages folder an apply carries: they are set after the row is written, before the apply reads them, and put back as they were when the apply fails. A failed apply also puts the row back to exactly what was read, by the same compare-and-set (it changes the row only while it still is what this run wrote), because the computer keeps serving what it served; the summary says `row_put_back` and whether the database read back what was put. The row is written by one statement that changes it only while it still is what was read, and its answer is compared with what was written. The commit's tree is unpacked with `git archive` into a temporary run folder named by its real path (a symlinked temp path made the unpacked program fail to run), `probe-while-applying.mjs` asks the row's hosts while the apply runs, and the held values the row's units name go to the apply on descriptor 5. The program prints one JSON summary (times in the local zone, the apply's exit, the probe's totals, the run folder) and exits with the apply's exit code; `--dry-run` stops after the edits, prints what each changed, and writes nothing. `--plan` also writes nothing and holds no row: it renders the edited row at the request's commit and runs that commit's `start-a-computer.mjs plan`, which runs the apply's own steps (`applyWhatItRuns`) through `readsOnly`: the computer is sent only the apply's reads (a command it cannot tell from a write is held back, so a plan may show more than the apply does, never less), and the summary lists the files the apply would write, the units it would restart, what it would remove and every changing command, in order, none sent (`not_run`). A refusal the apply would meet before changing anything (a credential its computer's vault does not hold yet) is the plan's answer, exit 1; a check that reads what an unsent change would make (a restarted unit's health) cannot pass, so then the lists are read from the held-back commands and `checks_after_the_changes` says which check stopped. Why: on Nov 25 2026 a preview named a drop-in the row writes as a file, and proving the apply left it alone took a hand-built guard in a scratch folder (6:49 PM CST); `test/plan-an-apply.test.mjs` covers it. `read-data/apply-a-computer-row.json` holds the defaults (the argv of the SQL process, the probe's timings); the person's own `--targets` file lays over it `machines` (by the computer's address: `ssh` { known_hosts, identity_file } and `pages_folder`) and `held_value_reader` (the argv of the program that prints a held value by vault name, its name added last); `{home}` in either is the running person's home folder. This shared tool names no one's machine. `test/apply-a-computer-row.test.mjs` covers it with a made-up row store, unpacking, probe and apply.

A site's act (the tools a site's own key may run, a `vault_readers` entry's `act`) is never a hand list: the row gives it as `{ "derive_from": { "connection", "database", "use", "site", "pin" } }` and the apply makes it from the site's own rows at the Workshop commit `pin` (`tools/serve-a-sites-pages-from-its-rows/do-work/rights.ts` over every tool row of that commit: the site's `runs` row of `site_settings`, its pages and its action rows, read with the held connection `connection` by `tool:run-sql-in-my-database` on the engine of the row's own computer, whose vault holds that connection and which runs the site: `engine_runner` in the `--targets` file, the computer named last with `--pin`; the connection is never read or held anywhere else). The row keeps `{ derive_from, derived: { pin, grant } }`, written by the same compare-and-set as the edits, and the computer is given the grant itself; the summary lists `derived_acts`, a dry run too. Rows the grant cannot serve as written refuse the request before anything is written, and so does a grant that gives more than the act the computer runs now (the row's last derived grant, or the hand list it replaces) unless the request says `"widen_acts": true`: an apply made for another reason never grants a site a tool its rows began asking for meanwhile, and the refusal names what would widen. Tests: the last test of `test/apply-a-computer-row.test.mjs`.

One apply of a row at a time. A run (not `--dry-run`) holds the row from before it reads it until after its last write-back: a PostgreSQL advisory lock on (hashtext `apply-a-computer-row`, hashtext of the row's name), taken with `pg_try_advisory_lock` on a database session of its own (the pg the SQL tool ships, through the run's proxy when there is one) and kept open for the whole apply (`do-work/hold-a-computer-row.mjs`). A second run of the same row is refused at once, exit 3, before it reads the row, saying who holds it and since when: the holder writes its words (the `--targets` file's `applied_by`, or the login name; its process, host and run folder; when it took the row) into its own session's last statement, which the database shows every session of the same login. Another row's apply is not held up. The lock ends with its session, so a run that dies, or a session the network drops, holds nothing; before the row is written the run checks it still holds it. `--dry-run` and `start-a-computer.mjs differences` take no hold. Why: on Nov 25 2026 four lanes shared one row by messaging "row free" and "done" and two applies still raced (a preview read a row another apply was about to change, 4:08 AM CST; two applies nearly overlapped, 5:30 AM CST). `test/hold-a-computer-row.test.mjs` covers it over a made-up database of sessions and advisory locks.
