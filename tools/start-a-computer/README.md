# Start a computer

Rent a Linux machine through a provider description the person supplies, or adopt a machine they already run over SSH, install a caller-supplied engine release, write its config, start it and read back its sign-up page and monthly price. Provider credentials arrive on private pipes, never in argv, a lease or an answer.

The request must provide `product_settings`: a JSON object or an absolute JSON file path. `readRequest(file)` resolves a relative settings path against the request file. The settings must include `new_accounts.sign_in`, `sign_in_ways`, `sign_in_words`, `copies` and `copies_rules`. The tool supplies no product identity, engine program name, starting account fixture or release-feed default.

A start or update reads one settings snapshot before it contacts the machine. Those exact bytes are written as the remote settings file, and that snapshot's `new_accounts` fills missing config rows. Existing config rows remain intact; copies are the request's explicit policy or the supplied product policy bounded by the number of default holders. Copy counts follow the engine's admission bound and ordering rules. The engine remains responsible for validating each row's full schema.

A request may hand the computer's layout row as a file beside it (`host_layout_file`, resolved against the request file): the row is that file's JSON.

A request's `release_feed` selects its signed feed. An omitted or null feed selects none for a start. An update requires an explicit feed; when its `releases` is an object rather than an absolute folder, the computer's existing releases folder is used.

## Requests and commands

Run `node tools/start-a-computer/do-work/start-a-computer.mjs OPERATION ...`. Operations are `price REQUEST`, `rent REQUEST`, `start REQUEST`, `status LEASE`, `install LEASE REQUEST`, `update LEASE REQUEST`, `rollback LEASE REQUEST BACKUP` and `remove LEASE`.

A provider is a description file the person keeps outside this folder; the tool names none. `machine.provider` (and `name.provider` for a DNS record) in a request is the path of that file, relative to the request file, and the lease keeps the path (`providerFile`, `namesFile`) so a status or removal needs only the lease. The description holds the provider's `base` URL, its `auth` header, the credential's vault handle (`vault_key`, never the value), its `requests`, and which request finds, creates, reads and removes a machine and its SSH key, reads a size's price, or points a name (`host`, `access_key`, `price`, `zone`, `record`); a description with no `base` is a machine already run, adopted at `placement.address`. Only the calls a description declares are sent. A new provider is a new file and no code change.

A start request names `lease_file`, `machine`, `name`, `ssh`, `port`, `engine` and `product_settings`. Engine inputs include its file, data environment name, data folder and release. Optional inputs include `place_config`, `config_from_release`, `default_places`, `copies`, `public_origin` and `release_feed`. Local file paths are relative to the request file. An update also accepts `layout` overrides; otherwise the running service's own config, current link, state folder, owner and release folder are discovered.

A computer's layout row (`request.host_layout`) may also name the sign-in unit: a unit with `template: serve-better-auth` runs official Better Auth from the Workshop's `tools/better-auth-official` folder (clone, `npm ci`, migrate, `node server.mjs`), with `workshop`, `repository`, `tool_folder`, `node_bin`, `user` and `writable`; its `settings` object is written as JSON to `settings_file`; its secret is named by `secret_vault_key`: a start reads the value the person's vault holds under that name from descriptor 5 (a JSON object of vault name to value), sends it only on the SSH channel's standard input to `systemd-creds encrypt --name=<secret_name>` at `secret_file`, and the unit opens it with `LoadCredentialEncrypted`; no value is in the row, a unit, argv, a log or the answer. Set-up installs the apt packages settings.json `machine.packages` names and, into each unit's `node_bin` folder that has no node, the `machine.node` release for the machine kind, checked against its sha256; a unit with no engine config names its `state` folder. `caddy.routes: ["better-auth"]` with `caddy.auth_port` sends `/api/auth/*` to it (`better-auth-discovery` adds `/.well-known/oauth-authorization-server*`). `better-auth-pages` sends the paths `caddy.auth_page_paths` lists (the sign-in pages, `/sign-in`, `/sign-up` and what is under them) to the same port; a path moved there leaves `forwarder_paths`.

A unit that runs from a Workshop clone names `workshop_feed` (`urls`, `public_keys`, `target`): its clone follows the newest entry of that signed feed one of the keys signed, or `workshop_commit` when the row pins one; `differences` reports a clone at another commit and `layout` moves it as the unit's user, restarting the unit only when its `tool_folder` changed. A unit whose template runs the engine (`serve-computer`, `serve-place`) names the `config` its `serve` reads and gives that config as `settings`: the config written there (its user's, 0600) is those settings with the product data's `new_accounts` under the row's own, so `layout` needs the request's `product_data` (the same manifest a start reads, which also writes `product_settings`). When the config names a `release_feed` and the unit's `releases` folder has no `current` yet, `layout` takes the feed's newest entry for the target the machine reports that one of the feed's keys signed, downloads it on the machine as the unit's user, refuses it unless its byte count and BLAKE3 content identity (`b3sum`) are the entry's, unpacks it beside the others with the entry as its `release.json`, and makes it `current` with the release's own `release switch`; from then on the engine follows the feed itself. A unit's `folders` are made for its user, and its own `health` and `health_listen` are its boot check. A row's `machine` object replaces settings.json `machine` fields for that computer (its `packages`, and `firewall_allow`, null where another program keeps the firewall). A new unit is enabled and started. A row's `absent` lists files the computer must not hold; `differences` reports each one there and `layout` removes it. A systemd unit file in it is a unit the computer must not run: `layout` stops and disables it and removes its drop-ins before its file. `start-a-computer.mjs layout REQUEST_FILE` applies a computer's row to that running computer (`machine.address`, `ssh`, `host_layout`: the row itself, which the caller reads from their own data and hands in; this tool reads no store) and `differences REQUEST_FILE` answers what it runs that the row does not render.

Updates back up replaced config, service unit, settings and release pointer. A failed service health check or sign-up response restores them. Explicit rollback uses the same backup and layout. Removal deletes only resources the saved lease owns; adopted machines are forgotten without deleting them.

## A database server and its backups

A layout can run PostgreSQL from its own package and keep its backups, all rendered from the row. The row's `machine` object gives what set-up installs before the units start (settings.json `machine` with the row's own fields over it): `packages`, `files` (path and text, written before the packages: a file that decides how one installs), `apt_sources` (`name`, `line`, `list_file`, `key_url`, `key_file` and `key_sha256`: the package source, the file that holds it, and the key it is signed by, refused unless the key's sha256 is the pinned one) and `downloads` (one program each: its `path`, and per machine kind `url`, `sha256` of the archive, `member` and `binary_sha256` of the unpacked program). The tool names no address: every URL is the row's.

Three templates make the units. `serve-postgres` runs `postgres` as the unit's `user` on `data_dir` (`initdb` runs at the first start, data checksums on), reading the `settings_file` the row's `settings_lines` render, one line each, and the sealed credential `secret_name` (a file of `NAME=value` lines the server and the archive command it starts read). `run-a-script` is one run (`Type=oneshot`) of a script the row names in `script` (a file of read-data/scripts, written at `script_file`) with the sealed credential it names. `run-on-a-timer` runs a unit (`runs`) at `on_calendar`; a timer the row names that is not active is started at every apply. A unit that is not an HTTP server names `check_command`, a command run on the computer after its restart that must exit 0 (tried 12 times, 5 seconds apart), in place of the HTTP health row.

The scripts: `set-up-postgres-role.sh` reads a held connection string (`postgresql://ROLE:PASSWORD@HOST/DATABASE`) and makes the role and its password; with `PG_KIND=owner` it also makes the database, owned by that role, with the right to connect taken from every other role (the store, not a query rule, keeps one person's rows from another's); with `PG_KIND=read` the role may connect to that database and read it through `pg_read_all_data` and holds no other right. `back-up-postgres.sh` takes a WAL-G base backup, switches the WAL segment and waits until the archive holds it, so each backup restores without a later one. `restore-a-postgres-backup.sh` fetches the newest backup into the run's private scratch folder, starts a second server from it with no network listener, replays the archived WAL and refuses unless the database `PG_DATABASE` is there.

## A public front door

A computer that serves the public door names a unit with `template: serve-door`. It runs the door program (`door_file`, for example `trillion-mcp-forwarder`) from the unit's own `releases` folder, as its own `user`. The door serves plain HTTP on the loopback address its `environment` names (a list of `NAME=value`, nonsecret settings only) and holds no key; the computer's Caddy in front of it holds TLS. The program comes from the signed feed the unit's `program_feed` names (`urls`, `public_keys`; the builder's forwarder-feed.json): `differences` reports a `current` that is not the feed's newest entry for the machine's target signed by one of the keys, and `layout` downloads that entry as the unit's user, refuses it unless its byte count and BLAKE3 content identity are the entry's, unpacks it beside the others with the entry as its `release.json`, moves `current` to it with one rename and restarts the unit. Nothing else moves `current`: no program follows a feed by itself. A unit's `health` may name `host`, the Host its boot check asks for (the door answers only its own Host). In serving-computer-front-door, `door_transport_routes: ["door-over-tls"]` gives the upstream to `door_upstream` its TLS server name (`door_host`); a row whose `door_upstream` is `http://` leaves it out.

A layout whose `caddy` row has `front_door` makes the computer a public front door. Every such computer runs the same Caddy (settings.json `caddy_front_door`: v2.11.9 with only the caddy-storage-redis module, both Apache-2.0, fetched by set-up from the address the row's `front_door.binary_urls` gives for the machine's architecture (`x86_64`, `aarch64`; a row without it is refused) and refused unless its SHA-256 is the pinned one) and keeps its certificates in one shared store (`storage_env` names the address, password and encryption key, a host-held file the layout never writes; `storage_server_cert` pins the store's TLS certificate), so any front door answers any name. A name no site block names gets a certificate on demand only when `door_upstream`'s `ask_path` (the forwarder's own `/origins/certificate`) answers 200 for it, and every such name and each of `door_hosts` is carried to `door_upstream` with its own Host and TLS name. The layout's own sites are unchanged. `front_door` fields: `binary_urls`, `storage_server_cert`, `storage_env`, `ask_port`, `ask_path`, `door_upstream`, `door_host`, `door_server_name`, `door_hosts`.

A caddy row that names `site_file` gets that whole file from read-data/caddy-sites, each `{{field}}` filled from the row. A `{{routes}}` or `{{<name>_routes}}` slot is that list of route names (read-data/caddy-routes) in the row, and a line that is only an empty routes slot is left out. In serving-computer-front-door, `routes` goes in the home block and `every_name_routes` in the on-demand block, so `every_name_routes: ["better-auth"]` sends each attached name's `/api/auth/*` to the sign-in tool; `better-auth-webauthn` serves the passkey related-origins list at `/.well-known/webauthn`.

A computer that cannot be reached from outside (a Mac behind a home router) is carried to the front door by one outbound SSH reverse forward it keeps open (`tools/keep-a-door-tunnel-open`: the server's host key pinned, a user on the front door that may listen on one loopback port only). The front door's row names it in `caddy.carried_computers`, a list of `{ address, port }`: the computer's account address (lowercase letters and digits) and that loopback port. A site file with the slot `{{carried_computer_routes}}` sends `/a/<address>` and `/a/<address>/*` to `127.0.0.1:<port>` ahead of the forwarder's `/a/*`, with the door's own Host and no buffering. The route passes bytes only; the computer's own engine checks who calls. A row with no carried computers leaves the slot line out.

A front door can answer pages itself, and this tool holds none: the request hands them in as `pages_folder` (the person's own folder of files, a path relative to the request file), and a caddy row that names `pages_root` gets every file of that folder under `pages_root` on the computer (a text file as its text, any other as base64 that the computer decodes, so the bytes are the same). The site file serves a GET or HEAD for any of them through Caddy's `file_server`, a path without `.html` finding its page, and reaches no other host for a page. A row that names `pages_root` with no `pages_folder` is refused. The pages, their names, their contact address and their icons are the caller's own data.

## One name, no program in front of the engine

`caddy.site_file: "single-name-front-door"` makes a computer the front door of one name (`door_host`) with nothing between Caddy and the engine: Caddy keeps that name's certificate itself (no shared store, no attached names, no forwarder), answers the person's own pages from `pages_root` (the request's `pages_folder`), answers every other path 404, and sends the paths in `engine_paths` to the engine on `engine_listen` only when the row's `engine_routes` names `engine`. Its `routes` are read-data/caddy-routes files: the sign-in tool's (`better-auth`, `better-auth-pages`, `better-auth-discovery` for `/.well-known/oauth-authorization-server*`, `better-auth-webauthn`, `better-auth-home` for `/` to `/sign-in`). `caddy.carried_computers` (a Mac's `{address, port}` behind its outbound tunnel) sends that computer's `/a/<address>` to its loopback port ahead of `engine_paths`; an entry `{ paths, port }` instead sends those paths (for an engine that serves one door, `/mcp` and its `/.well-known/oauth-protected-resource` documents) to the port.

A layout's `absent_users` names users the computer must not have (a tunnel user an old set-up made): `differences` reports each one there, and `layout` removes it with its home folder; a removed file under `/etc/ssh/sshd_config.d/` (listed in `absent`) makes `layout` check and reload the ssh server, so its user is no longer admitted.

A request's `releases` (`[{unit, commit, tarball}]`, the tarball a path on this computer, read relative to the request file) hands a unit its program with no signed feed: when the unit's `releases/current` is not `commit`, `layout` unpacks the tarball into `releases/<commit>` as the unit's user (once), moves `current` to it with one rename and restarts the unit; `differences` reports a unit behind it.

## Source and checks

This is the existing canonical `start-a-computer` owner, recovered from its committed public origin implementation. Earlier product-filled DATA remains in that Git history; it is not a production default here. Recovery does not assert a new historical byte-copy baseline. The old `start-a-place` working files are outside this recovery's custody.

`test/start-a-computer.test.mjs` covers provider ownership, pricing, lease lifecycle, complete starts and updates, discovered layouts, failed-health rollback, exact settings snapshots and starting-row merges, using synthetic caller settings.

The shell commands target GNU/Linux. Tests discover a genuine GNU coreutils `mv` or `gmv` by its version, searching PATH and standard package bin folders. Each fixture links that executable as `mv` in its own PATH folder. Install coreutils when the discovery error names it; BSD `mv` is refused. Run plain `node --test tools/start-a-computer/test/start-a-computer.test.mjs`; an external PATH override is unnecessary. The shared test selector lives in `tools/process-session/test/target-tools.mjs`. Production SSH commands remain unchanged.
