# account files

The person's files (every file they keep), served by the native engine. The file list is record store records; the bytes stay in S3-compatible object stores (the account's own stores, read with ranged GETs). The tools answer the hosted Worker's contract (`src/file-tools.mjs` in the app) with the same names and fields: `list_files`, `find_file`, `files_summary`, `show_file`, `read_file`, `write_file`. Generic name operations sit beside them: `find_names` (the names in a folder that start with a prefix), `move_names` and `copy_names` (a name or a whole folder, in bounded pages), `set_aside` and `put_back` (a name or folder moved into the set-aside tree at the same full name, and back), `list_set_aside`.

## Records (account = the person's account)

| Resource | Record id | Kind | Holds |
| --- | --- | --- | --- |
| `@namespace/names<folder>` | full name | `namespace-name` | identity as named, resolved file identity, size, modified and named times |
| `@namespace/folders<folder>` | child folder path | `namespace-folder` | the folder |
| `@namespace/set-aside/names<folder>` | full name | `namespace-set-aside` | a name set aside: its name record as it was, `named_at` = when it was set aside |
| `@namespace/set-aside/folders<folder>` | child folder path | `namespace-folder` | a folder set aside |
| `@namespace/files` | `1f:` + BLAKE3 hex | `namespace-file` | size, media type, store (`origin`), key, span count, aliases, names |
| `@namespace/spans` | legacy: file identity; uploads: `<upload-id>:p<page>` | `namespace-spans` | legacy span array, or at most 256 spans per upload page: fixed 32 KiB pieces (`pages-32k-v1`), appended pieces (`pages-append-v1`) or chunks (`chunks-v1`) |
| `@namespace/chunks` | `1f:` chunk identity | `namespace-chunk` | size, store, key: one stored object per chunk (a `chunks-v1` chunk is at most `chunks.bytes`, identical chunks are kept once) |
| `@namespace/aliases` | `12:` alias | `namespace-alias` | the file identity it names, grade |
| `@namespace/home` | `this` | `namespace-home` | the account files' own random binding, made by `account-files-bind` |
| `@namespace/origins` | store id | `namespace-origin` | rank, whether it takes new bytes, where new files are kept, each connection fact as a value or a vault name |
| `@namespace/moved/<from>` | storage key | `namespace-moved` | where a key of the `from` store was carried, its size and BLAKE3, and how it was proved (`identity` or `source`) |
| `@namespace/uploads` | 32 lowercase hexadecimal upload id | `namespace-upload` | declared size, accepted offset, server-owned BLAKE3 checkpoint, target-name version, optional app attribution and lifecycle state |
| `@account-files/recent/files` | file identity | `files-recent` | each kind of use's newest time, the newest use (`last_at`, `last_kind`) and the order row that names it (`recent.rs`) |
| `@account-files/recent/order` | 13-digit inverted milliseconds `:` file identity | `files-recent-order` | the file identity; ids sort newest first, at most DATA `recent.keep` |

`files_summary` reads the record store declared totals `namespace-file/origin`, `namespace-name/all`, `namespace-chunk/all` and `namespace-upload/all` (`src/storage/record_store/settings.json`): one range scan.

## Reads and writes per call

| Call | record store reads | Store requests |
| --- | --- | --- |
| `list_files` page of N | 1 scope walk (`list_page`, values included) + 1 batch get of the page's files; the first page adds 1 walk of the child folders and 2 seeks per child folder (its revision stamp) | 0 |
| `find_file` by name | 1 get (name) + 1 get (file), +1 get when the name points at an alias | 0 |
| `files_summary` | 1 range scan | 0 |
| `read_file` (at most 256 KiB) | as `find_file`, + 1 get (spans) + 1 batch get (the crossed chunks) for a chunked file | 1 ranged GET per crossed chunk (1 for a whole-file object) |
| `share_file` | as `find_file` + 1 share record | 0 (the caller's grant-aware delivery owner mints the URL; without one the share is refused) |
| `write_file` new content | 2 gets (file, name) + 1 get per missing folder level | 1 PUT (refused stores pass to the next rank) |
| `write_file` new content: records written | file record (1 version row + 1 totals row), name record (1 version row + 1 totals row), 1 record per new folder | — |
| `write_file_start` | existing token: 1 get; new token: upload lookup + held upload and target-name versions | 0 |
| `write_file_piece` | upload, current target version, chunk lookup, span-page lookup; accepted pieces write chunk, span page and upload checkpoint, with a fresh target-version check at each mutation | 1 PUT for a new chunk in the first accepting store (a `chunks-v1` piece is one chunk, so one PUT) |
| `write_file_finish` | upload, all span pages and chunk records (verified in batches of at most 768 spans), file, target name and missing folders; a `chunks-v1` file checks its spans and uses the server checkpoint, with no read-back | 0 |
| `write_file_cancel` | upload | 0 |
| `find_names` page of N | 1 get (a name equal to the prefix) + 1 scope walk + 1 batch get of the page's files | 0 |
| `move_names` / `copy_names` / `set_aside` / `put_back`, per name | 2 gets (source and destination name) + 1 get per missing folder level; writes: the destination name, the file's names (1 get + 1 write, when they change), the source tombstone (not for a copy) | 0 |
| a folder carry | 1 get (is it a name or a folder) + one scope walk per folder visited + one id walk of its child folders; per folder finished: the destination folder (when missing) and the source tombstone (not for a copy) | 0 |

## Usage

The person's own page reaches every door operation at `/work/api/files/<operation>` (`src/server/owner-routes.json`, the `@namespace` row; `AccountFilesDoor::page_call`): a DATA `page.reads` operation is a GET with `?input=<JSON>`, every other one a POST with its input as body. The page's session admits it and the call is `call_while`, the same call an AI's key makes. A call's bytes are let in as DATA `call_bytes` says (`counted`: under one name, each byte also the account's usage; `refused`: none).

A folder of this computer is kept with the engine's own subcommand, not through the door: `trillion-local namespace-take STATE_FOLDER ACCOUNT FROM_FOLDER TO_FOLDER [--width N] [--skip NAME]...` (`take.rs`). Every regular file under `FROM_FOLDER` becomes the name `TO_FOLDER/<its path below FROM_FOLDER>`; entries named by a `--skip` (for example `.git`, `node_modules`) are left out at any depth, and symbolic links are passed over. `N` workers (16 by default) each open their own handle on the store file; S2h orders their commits, and a worker that finds the one writer busy waits and tries again. Output is one JSON line per file (`name`, `identity`, `byte_length`, `sent`, `named`, or `failed`) and a last `totals` line. A store that denies access (a spending cap answers 403) stops the take. Writes are the named unmetered operator admission `namespace take`. A file's `names` list holds at most `NAMES_LISTED` (256) names; every name past that is still its own name record pointing at the file.

The store file is installed into a state folder with `trillion-local namespace-bind NAMESPACE_STORE_FILE ACCOUNT into STATE_FOLDER`: it binds the store (as below), then moves it in with one rename to the file the namespace is placed in there. It refuses a state folder that already holds a namespace, and a store with a write-ahead log beside it. Until this step an account answers `namespace_unavailable` with step `no_store_file`, because the door never creates a store.

Large files use `write_file_start`, `write_file_piece`, `write_file_finish` and `write_file_cancel`. Start binds a caller-generated 32-character lowercase hexadecimal token to the absolute target name, media type and optional `app` attribution. A known-length call supplies `byte_length` and is cut into `chunks-v1` chunks: each piece is one chunk of any length up to `settings.json` `chunks.bytes` (chunks are cut by content, so their lengths vary). The server checkpoint takes whole 32 KiB subtrees: the bytes after the last whole subtree wait in the upload's `tail` with the cursor, and the file's last piece pushes them. A chunk is kept as one object keyed by its BLAKE3, so 1 GiB is about 32 objects at 32 MiB, not 32,768. A repeated accepted offset is answered only for the same bytes; a piece past the declared length or larger than a chunk is refused before anything is kept. An open-length stream supplies `length_known: false` and omits `byte_length`; each piece may then be any 1–32768 bytes at the exact next `offset`. The server hashes each piece before deduplication, writes it through the existing content-addressed CHUNKS owner, then records a bounded append span page before advancing the accepted offset. Repeating an accepted offset succeeds only for the same saved bytes; a crash after the span page but before the upload cursor is repaired by that same retry. Open-length finish verifies contiguous span metadata first, then reads chunks in bounded order, checks each actual chunk hash and computes the whole-file BLAKE3 identity from stored bytes before creating or reusing a file record and binding the name. Known-length uploads retain their existing checked span and server checkpoint finish path. The identity is never supplied or trusted from the caller. Cancel retires only that upload token; retained bytes are not deleted.

Known-length files carry `span_layout: "chunks-v1"`, and an upload opened before chunks-v1 keeps `span_layout: "pages-32k-v1"` (fixed 32 KiB pieces, read unchanged); open-length files carry `span_layout: "pages-append-v1"`. Each uses `span_set: <upload-id>` on the final file record; legacy files continue to use their existing single span array. A known-length finish checks that its span pages cover the declared length exactly and that each chunk record has the span's length, then uses the checkpoint identity; it never reads the bytes back (B2 bills every byte it serves). For open-length uploads, generic `read_file` may also include both its normal `name_or_identity` target (the bound upload name) and an `upload_id` to read the currently arrived prefix. The token is only a locator: each call retains the target-name rights and checks the captured name generation. Open reads report `length_known: false`, `arrived_length`, and `retry` when the requested range extends beyond arrived bytes; they return no canonical file identity. Cancelled uploads cannot be read. After finish, the token only reads through the ordinary immutable file path when that same name still points to the finished identity. Range reads validate append-page seams and exact requested byte coverage before fetching chunks, then use the same `read_range` path for direct reads and grant-aware share delivery; an unknown layout fails closed. Finish verification work grows linearly with accepted pieces, while metadata batches remain capped at three pages (768 spans/chunks).

```rust
let store = RecordStore::new(sqlite::open_owned(&path, "record_store", bounds)?, Box::new(RealClock), limits)?;
let kept = KeychainItem::shipped()?;
let naming = VaultIdentity::new(account_files::identity::word()?)?;
let vault = secrets::Secrets::open(secrets::open_store(&path)?, account, &SecretsKey::from_keychain(&kept)?, naming)?;
let mut account files = AccountFiles::open(store, account, Box::new(vault))?;

```

Emptying a store: `examples/account_files_move.rs RECORD_STORE_SQLITE ACCOUNT FROM TO (dry-run | run | audit | retire) [CONCURRENCY] [unnamed-keys]`. `dry-run` counts from records and estimates requests without sending any; `drain` only marks the `from` store as taking no new bytes; `work-list` writes every unproved key (records first, then the store's listing) as `Carry` lines with the plan and a 110% budget on stderr; `remote-setup WORK_LIST` writes the one setup line a copier on another machine needs (plain facts and SigV4 day keys for two UTC days: secrets never leave the vault); `import-proofs` writes the copier's proof lines as records; `run records-only` rewrites proved keys' records with no request; `remote-setup ... pack` packs small keys no record names into archives with manifests; `verify-sample N [AT_MOST_BYTES]` is the one read of a destination, an explicit spot check of N proofs refused before any request past the byte ceiling in `moves.json`; `run` is resumable (the proof records and the rewritten records are the checkpoint); `audit` lists what the `from` store still holds against the proofs; `retire` deletes the `from` origin record once the audit is complete. Deleting the `from` store's objects is outside this tool.

An account's files that is not the account's own never writes into the account's real store. The door opens the account files held to its own binding (`bind::binding_in`: a random id in the account files' `@namespace/home` record, made once by `account-files-bind`) tied to the account (`bind::tie`): a store off this computer's loopback (`Origin::is_loopback`) takes new bytes only when its origin record says `bound_to` exactly that, else the write is refused before any byte is sent (`account_files_origin_not_bound`, naming the origin and the fix). The binding is inside the account files, never read from the file system, so the account's folder copied to another place, or restored, still opens and writes (it was refused when the check read the folder's inode). A store file never bound, an origin bound for another account, another binding or the old way (an inode) is refused; a loopback store (the stand-in) is always allowed. The engine's own subcommand `trillion-local account-files-bind ACCOUNT_FILES_STORE_FILE ACCOUNT [show]` (`bind.rs`) binds the origins on purpose (app quit; `show` only reports); the install runs it when the store file is put into the live folder; run it again for a store bound the old way. The refusal's fix names that command with the running engine's full path. A copy made only to try something is no longer told apart by the check: a clone proof points its origins at the loopback stand-in, `examples/account_files_standin.rs (serve FOLDER PORT | point RECORD_STORE_SQLITE ACCOUNT PORT | show RECORD_STORE_SQLITE ACCOUNT)` (the SigV4-checking loopback store).

| Move phase | Per key: requests |
| --- | --- |
| a key of at most 32 MiB | 1 ranged GET at `from`; 1 PUT signed with its SHA-256; 1 HEAD at `to`; 2 record writes (proof, then the record) |
| a larger whole file | 2 passes of 32 MiB ranged GETs at `from` (hash and check, then stream into the PUT); 1 PUT signed with the first pass's SHA-256; 1 HEAD at `to` |
| a packed key | 1 ranged GET at `from`; per archive and per manifest, 1 signed PUT and 1 HEAD at `to` |
| `unnamed-keys` | 1 LIST per 1000 keys of `from`, 1 batch get of proofs per page; each unproved key as above, plus a HEAD at `from` for its media type |

Migration: `examples/account_files_migrate.rs SOURCE_SQLITE OUT_FOLDER ACCOUNT ORIGIN_SETTINGS_JSON VAULT_NAME_PREFIX` (clones the source with APFS clonefile and opens the clone read-only). Proof on real stores: `examples/account_files_prove.rs`.

## Invariants

- A read asks a store for exactly the bytes asked (a `Range` request); a store that answers anything but `206` with the asked `Content-Range` is refused before its body is read. A `chunks-v1` read fetches only the byte ranges of the chunk objects it crosses, never a whole chunk for a short range.
- An upload keeps its bytes before any record names them; nothing here deletes bytes in a store.

- Every physical read and write of file bytes passes the caller's one byte admission before any request is sent (`source_reads.rs`): no admission refuses every read and write; a metered allowance refuses what it cannot cover and otherwise takes exactly the requested bytes with one atomic subtraction; refill and settlement run on the allowance's own thread. A finished Workshop run's outputs are kept under the one named unmetered admission `AccountFilesDoor::run_outputs_control`. The counters (`counters.rs`, RAM only) leave the process as one host stderr line per five minutes, only when a count changed (`flush_changes_every`). Each byte a door's call admits is also its account's own usage count (`usage.rs`): one more atomic add on that path, and the account's day row is written later by the usage flush thread, never by the request.
- A share is minted only by the caller's grant-aware delivery owner, at most seven days; this byte port never signs a provider URL. Its `@namespace/shares` record keeps what, when and the grant, never the URL.
- New bytes land only in stores whose origin record takes new bytes; a move first marks its `from` store as taking none.
- Every run has a hard budget (110% of its plan per counter: requests per origin and method, bytes read and written); a request that would pass its cap is refused before it is sent and the run stops; each key gets at most 5 retries, which count toward the budget.
- A move rewrites a chunk or file record only after its key is proved at the destination and the proof record is written. A copy has one proof (`upload-sha256`): the BLAKE3 computed while the bytes stream from the source (equal to the record's identity before any byte is sent), the SHA-256 signed into the PUT so the destination refuses any other body, and one HEAD of the length. A copy is never read back (B2 bills every byte it serves).
- Credentials never enter a record or a log: origin records hold vault names; the secret stays in the vault, which answers SigV4 day keys.

Remote door calls pass their original absolute deadline and a transient current/cancellation checker through
`AccountFilesDoor::call_while`. Every account files record mutation uses record store's existing atomic commit check, including
recovered receipts. The S3 byte owner checks the same control before requests and between socket reads/writes,
and limits connect, TLS socket and I/O waits to the remaining deadline. The control adds no credential or
capability of its own; its callback retains the caller's existing witness.
This stops later atomic steps; it does not undo an accepted PUT or earlier name/file steps. A refused call may
therefore leave already accepted, unnamed bytes or earlier completed steps, and keeps the existing unknown-effect
failure semantics. A blocking socket step notices cancellation at its next boundary or timeout. The original
synchronous system DNS resolver remains outside that deadline bound. The checker enforces the witness the caller
supplies; this byte owner does not invent or independently refresh OAuth/native-key admission.

## Why This Design?

The Worker kept the file list in one SQLite object with triggers for counts and folders. Here each kind of fact has one owner record and one scope, so a folder page is one walk in name order (the old `ORDER BY name`), a chunk's location lives in one record (a move rewrites one record, not every file that shares the chunk), and counts are maintained by the store's declared totals in the same write rather than by triggers.
