# src/workspace/walkthroughs/

The guided tours the signed-in workspace ships, one file per tour, as DATA for `parts/guided-overlay`. `scripts/build-workspace.mjs` writes every `.json` here into one content-named file the page fetches when a tour is first wanted (the module `trillion-walkthroughs` is that read: its default is a promise of every tour), so no script carries the tours' words and adding a tour is adding a file. A step points at a real control with a selector: a sidebar row is `[data-sidebar-surface-id="<surface id>"]`, anything inside a screen is `[data-trillion-screen="<screen>"] <selector>` (main.tsx marks each pane with its screen); a list of selectors separated by commas points at whichever is there (a full screen and its empty state). A step whose control may not be on screen (an empty or locked screen) sets `centered_when_target_missing`, so it shows centred in its own words instead of waiting. A step pointing inside a screen opens that screen first (`target_preparation` `surface`), so the page and its address change to what the step talks about; a step pointing at the sidebar also names `[data-sidebar-open-toggle]`, so it points at the closed sidebar's Show button; a What is new step never points at a screen's sidebar row, it opens the screen. A step can do the thing instead of describing it: `act` (`{ do: 'type', text }`, `{ do: 'press' }`, `{ do: 'choose', text }`) runs on the control it points at when its Next is pressed, and its Next says what it does (Search for me, Open it). A `type` act with `every_ms` types letter by letter. A tour with `play` (`{ step_ms }`) moves by itself: each step shows for its `look.hold_ms` (else `step_ms`) and then does its act, the last step waits for the person, and the person's own press or key outside the card stops it playing (a live showcase, src/showcases.mjs). Each step's `look.spotlight` lays its own `scrim_color` and `blur_px` over the tour's; a scrim with no colour and no blur catches no click, so the whole page stays usable. When a control shows in more than one place (a row in its own list and in New), the step points at the first one fully in view. `scripts/walk-every-tour.mjs` takes every tour on a proof account, live, at 1280 and 390 wide, and fails on a step that waits, does not open its screen, or cannot find what it points at. A tour naming an `audience` (like a screen row's) starts only for a viewer holding it (`audience:<name>` in /work/api/viewer). Each screen has a tour that can be taken from Tours. Most screen tours start once on `screen-opened`; the AI screen is already part of the first-use welcome, so its own tour is replay-only and does not stack another overlay when welcome closes. The welcome starts on `first-use-ready` after the Connect AI step closes. A what-is-new tour starts on `app-opened` once the welcome tour is taken.

| `workshop-tool.json` | Tool: One tool: what it does, what it needs, how its runs went and your runs of it. |
| `workshop.json` | Workshop: Every tool your AI can use: who made it, where it runs and whether it worked, and every run of them. |

## Key Types / Functions

Each file is one `WalkthroughDefinition` (`parts/guided-overlay/read-data/walkthrough-eeaf.ts`); `test/walkthroughs.test.mjs` checks every file folds, points only at rows and screens `../surfaces.json` has, uses plain words, and can be taken again.

## Dependencies

**Depends on:** `../surfaces.json` (the surface ids and screens steps point at).

**Depended on by:** `scripts/build-workspace.mjs` (bundles them), `../main.tsx` (hands them to the host), `../tours-screen.ts` (lists them).

Every screen row has a tour: `test/every-row-has-its-guide.test.mjs` (run by the deploy) refuses a screen no tour starts on or opens, unless its row names the tour that covers it (`screen.surface.tour`, for a part of another screen such as a Home card). A tool's own screen sends its `tool_id` when it opens (`screenOpenedEvent` in `../screens.mjs`), so each tool's screen has its own tour.
