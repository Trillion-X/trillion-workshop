# tools/decide-with-a-method/

Decisions a person's AI makes with a method, kept as the person's own `decision` records: start one, answer the method's questions one at a time (every check answered, the calling AI's own judge's verdicts beside each answer), make the decision, say what was done, and report how it turned out. At the moment of choice the person's earlier similar decisions come back with how each turned out. A decision is a growing record, not a fixed one: evidence can be added at any time (`tool:add-decision-evidence`), an answered step can be revised with its reason (`revise.because` on `tool:answer-a-decision-question`) so the old version stays readable and every later answer is asked again, a re-asked answer is confirmed unchanged (`confirm`), and an answer or an evidence row can be brought in from another of the person's decisions as it stood (`from`), checked like a typed one. A revision of a decided decision's answer reopens the decision: the decision it had moves to `decision_history`, marked reopened with its reason and when, and the decision is made again. Verdicts can be added to an answered step at any time (`confirm` with `verdicts`) as a new version with the same answer, so a decided decision stays decided. A decided decision can be made safe to show strangers (`tool:share-a-decision`): the calling AI rewrites its redacted facts in general terms, the plain privacy pass finds nothing in the rewrite with the person's own private terms, and a second model's re-identification verdict is accepted for exactly those words. Ported from the old app's `src/engine.mjs` (DecisionEngine), `src/private-method.mjs`, `src/check-uses.mjs`, `src/check-judge.mjs` (the caller's verdicts) and the record layout of `src/decision-store.mjs`, so the Decisions screen reads what these tools write. The method is the person's own rows, which they see and edit: one row per method in their Methods list (`list:methods`, row type `method`) and one row per check in their Method checks list (`list:method-checks`, row type `method-check`, naming its step and method), never this folder's; Trillion asks no model. A call reads every method row (a few) but only the check rows of the step it asks or judges, through the records door's `where` (`{ step }`, and `{ id }` for each check a step names by id), so a step's few checks never cost the whole list. A question sends each check as its id and question; `tool:next-decision-question` with `explain: [ids]` sends the whole words of those checks (what a good answer does, what it refuses). An answered step keeps each check it asked as its id, question and the content identity of its row as asked; a decision's root keeps its method's id (`method_id`) beside the snapshot, so similar decisions are weighed without reading snapshots; and a change too large for one door message is written in parts (`writeBatches` of `tools/records-door`), its root last.

## Key Types / Functions

| Function | Signature | Role |
|----------|-----------|------|
| `startADecision` | `({ source_id, goal, evidence, options, method? }, { door }) -> reply` | One source opens one decision under the method's snapshot. |
| `answerADecisionQuestion` | `({ decision_id, step_id, answer? \| from?, revise?: { because, by? }, confirm?: true, verdicts?, usage? }, { door }) -> reply` | Validates the answer against the method, takes grounded refusals, keeps the step; a `revise` keeps the old version and flags every later step, and on a decided decision reopens it; `confirm` keeps a re-asked answer unchanged, or with `verdicts` adds them as a new version of the same answer; `from` copies another decision's step as it stood. |
| `addDecisionEvidence` | `({ decision_id, evidence: [{ ref, claim } \| { ref, from: { decision_id, ref } }] }, { door }) -> reply` | Adds evidence rows at any time, each kept with when it came in; the same rows again replay. |
| `makeTheDecision` | `({ decision_id, decision, verdicts?, usage?, expected_generation? }, { door }) -> reply` | The choice, its fields and evidence; a new one only after a failed result or a revision that reopened the decision. |
| `reportADecisionResult` | `({ decision_id, result, summary, answered_by: "person", ... }, { door }) -> reply` | The person's result; a failed one opens the decision again. |
| `methodCatalogue` | `(methods, checks, { grader }) -> functions` | Every method function over the person's method rows and check rows. |
| `similarDecisions` | `({ decision_id, limit? }, { door }) -> { similar_decisions }` | Earlier decisions like this one, each with its choice and how it turned out. |
| `shareADecision` | `({ decision_id, rewrite?, reidentification? }, { door }) -> { next: "rewrite" | "check" } or { shared, send }` | The redacted facts to rewrite; then the plain pass on the rewrite; then the review identity a verdict must carry; then the entry kept and the pool tool to send it to. |

## Not here yet

- A confirmation with verdicts takes only the verdicts a typed answer would take: a refusal that names no words of its check, or a verdict that rests on nothing of the answer or the evidence, is ignored, not refused. A verdict is never changed once kept.
- Adding evidence flags nothing: answers already given do not cite it, so a step that should weigh it has to be revised (with its reason) to do so.
- Revising the scope flags every answer after it. A step the old scope asked and the new one does not is kept and not asked, so its answer stays in the record unused.
- A reopened decision moves its share into the history, but a copy already sent to the pool stays there: nothing here can take it back out.
- A reopened decision's new decision waits until every answer is asked again (confirmed or revised), as before.
- A workflow run named by `run_id` cannot be read by these tools, so it is refused, and a plan whose decision needs a finished decision-phase run waits (`words.decision_phase_runs`).
- A report from a trusted person source (the signed-in host's basis) cannot be marked here: every report is kept as the caller's claim.
- The pool account's door admits other people through a share's act grant (trillion-rust `src/account_rights/share_grant.rs`). Sending a shared decision there is the calling AI's own call with the pool's share bearer: `tool:add-a-shared-situation` with `send.entry` and the meaning of its situation (the embedding the pool names), then `tool:add-a-pooled-result` with the bit `tool:randomize-a-result` drew. No tool here reaches another account's door.
- The re-identification verdict comes from `tool:ask-a-small-model-for-a-verdict`, whose rows run on the person's computer, not at the engine yet; this tool only checks that the verdict was accepted for exactly the rubric and words it names (`contentReviewIdentity`). A result's own words are not shared: the pool takes only its randomized bit.
