# tools/decide-with-a-method/

Decisions a person's AI makes with a method, kept as the person's own `decision` records: start one (its goal, its evidence and its options), read its method and record answers to the method's rows (any number of rows in one call each way, see "A method as rows and a saved view"), make the decision, say what was done, and report how it turned out. The method is the person's own rows, never this folder's: their files and the sections of their files are rows of one list, a method is a saved view over those rows, and the decision is made when every row of its view has an answer. Strictness (how much an answer to a row must show) is an open value on the row or the view, never a level; Trillion asks no model. At the moment of choice the person's earlier similar decisions come back with how each turned out. A decision is a growing record, not a fixed one: evidence can be added at any time (`tool:add-decision-evidence`), a row of evidence can be brought in from another of the person's decisions as it stood (`from`), and an answer to a row is a record of its own that a later answer replaces as its next version, the old version kept. A decision no one will carry on is ended with `tool:end-a-decision`, never deleted, and keeps what it was and why. A decision whose root is too large to send with its condition (`expected`) in one 64 KiB door message, or one the door refuses as too large (413), is ended through its record layout instead, laid apart with its root last and checked by a second read of the root just before the write, and answers `laid_apart`. One whose laid-apart write the door still refuses as too large is left as it was and answers not ended with `too_large`, so the decisions beside it still end. A decided decision can be made safe to show strangers (`tool:share-a-decision`): the calling AI rewrites its redacted facts in general terms, the plain privacy pass finds nothing in the rewrite with the person's own private terms, and a second model's re-identification verdict is accepted for exactly those words. The record layout is the one of the old app's `src/decision-store.mjs`, so the Decisions screen reads what these tools write; a decision of any size fits under the records door's 64 KiB write cap, because everything in it that grows is a record of its own linked to its id (see Record layout), and a change too large for one door message is written in parts (`writeBatches` of `tools/records-door`), its root last. Decisions made before the method became rows keep the answered steps they were made with; they read as they were written.

## A decision the person made themselves

`tool:record-a-persons-own-decision` (`recordAPersonsOwnDecision` in `read-data/decisions.mjs`) keeps a verdict the person gave as the decision, without the method's questions. Only the person's word is taken: `person.message_id` names a `message` row they sent (`speaker` is `person`, the row the harness hooks and the web chat keep) and `person.said` must be their exact words in it, or the run comes from their own signed-in page, which the engine attests as the task's `origin` (trillion-rust `tool_runs/tools.rs` `Place::origin`; the row's stdin fills `origin` and `run` from the task and the call's input as `verdict`, so no input can set it). With neither, the call is refused and the AI is told to walk the method, which every decision an AI makes still needs (`tool:make-the-decision` still refuses until every row of the method has an answer). The person's words are kept as an evidence row (`person-verdict-<generation>`) with `person_source` { basis, source_ref, said, at } (old trillion's trusted person sources, `kept_person_message` or `signed_in_person_screen`, src/check-uses.mjs); the decision and its root carry `decided_by: "person"` and `method_walked: false`; the Decisions screen's summary shows `decided_by` and `method_walked`. The person's word stands over a decision already made, which moves to `decision_history` with `replaced_by: "person"`. Names and words are in `person_verdict` and `words` of `read-data/decide-with-a-method.json`. Old trillion had no person-decided decision path; it had the trusted person source for results, which this reuses. A `message` row is written through the account's records door, so this trusts that only the person's own roads write `speaker: "person"`.

## Record layout

`read-data/decision-records.mjs` lays a decision out; every name is in `records` of `read-data/decide-with-a-method.json`.

| Record | Holds |
|--------|-------|
| `decision` (id `source:<base64url>`) | The root: fields each set by one call (`source_id`, `input` with its `goal` and its `options`, bounded at start, `status`, the current `decision`, `shared`, `workflow_plan`, `decided_at`, `recheck_on`, ...), `method_id` and `method_identity` (where its snapshot is), `input_identity` (the input it was started with, so the same start is still that decision), `counts` (the length of each list below) and `call_count`. Nothing in it grows as the decision grows. |
| `decision-evidence:<id>:<nnnn>` | One evidence row: `ref`, `claim`, and `added_at`, `from`, `retracted_at` when it has them. |
| `decision-answered-step:<id>:<nnn>:c<identity>` | One answered step's summary: `step_id`, `answered_at`, `checks`, `graded`, `graded_by`, `version`, `needs_recheck` (`recheck_of`, `rechecked_at`). A flag is set here, so flagging later steps never rewrites their answers. |
| `decision-step:<id>:<nnn>:c<identity>` | One answered step whole: its answer, the checks it was asked (`{ checks }`) and the verdicts taken (`{ given }`); each superseded version beside it as `decision-step:<id>:<nnn>:v<vvv>`. |
| `decision-candidate:<id>:<nnn>` | One candidate a step left standing. |
| `decision-option:<id>:<nnn>` | Written only by 55179fc, which laid options apart too: such a root (`counts.options`) reads them back, and its next change folds them into the root's `input.options` and removes these records. |
| `decision-report:<id>:<nnnn>`, `decision-carried-out:<id>:<nnnn>` | One result the person reported; one receipt of what was done. |
| `decision-history:<id>:<nnn>` | One earlier decision (with its reopen mark and share, when it had them). |
| `decision-cited-pursuit:<id>:<nnnn>` | One cited pursuit as it stood: `{ ref, said }`. |
| `decision-call:<id>:<nnnnnn>` | One logged call of a decision that was once kept whole. |
| `decision-method:<identity>` | A method snapshot `{ method }`, kept once under its content identity and shared by every decision made with that same method. |
| `decision-part:<key>:part:<nnn>` | A piece of any record above larger than `record_bytes` (32000): that record keeps its short fields and `kept_in_parts`, and its whole value is the text of its parts, in order. A step with hundreds of checks and verdicts, or a long method, goes this way. |

A reader takes the first `counts` items of each list, so a record written in a write whose root never came is never read. A write keeps only the records that changed: the root, the step answered and its summary, the rows added. A root written the old way (evidence, options, results, history and cited pursuits inside it, the method snapshot inline, `answered_steps` on it, the original input kept whole, or the whole guidance in it) reads as it is, and its next change lays it apart: every list becomes its records, the snapshot goes to its identity, `original_input` becomes `input_identity`, all in parts with the root last when one write cannot carry it.

**Options on the root.** Options are set once at start and never grow, and readers outside this folder read them from the root (`input.options`), so they stay there, bounded: a start with more than `options.most` (32) options, or more than `options.most_bytes` (8000) bytes of their JSON, is refused (`words.options_too_large`: the limit, and to shorten or group them). The bound is checked only when a decision is opened, so an older decision with more options still replays. The arithmetic for the root at its largest: options at most 8,000 bytes; every other field the case adds to the root (`counts` with seven numbers, `method_identity` and `input_identity`, `method_id`, `call_count`, `change_count`, `outcome_revision`, `decision_generation`, status and times, the empty `scratchpad`, `actions` and `checks`) about 700 bytes and never more as the case grows; the one-call fields (goal, the current decision with its fields and refs, `shared`, `workflow_plan`, `decision_usage`) were about 450 bytes in the big-case test, whose largest root was 1,158 bytes with two options. With 8,000 bytes of options that root is about 9.2 KB, leaving about 56 KB of the 64 KiB (65,536 bytes) cap for the one-call words, which are bounded by their own calls, not by how large the case grows.

**Size guarantee.** Every record and write is measured as carried (`carriedBytes`: its JSON with every character past ASCII as a `\u` escape, quoted once more as a JSON string), the most a door can make of it on the way, so a part, whose text is JSON already escaped once, still fits when a door re-encodes it: a 67 KB chat message full of quotes, newlines and emoji once made a write of 46 KB plain that was 74 KB carried, and the door answered 413. Every record the tools write except the root is at most `record_bytes` carried; the root holds only one-call fields and counts; every door write is at most `writes` records and about `write_bytes` bytes, the root last when a change takes more than one. The test `a decision of any size fits` builds a made-up case of about 400 KB (500 evidence rows, 43 steps, a step with 300 checks and verdicts, three earlier decisions, twelve receipts, thirty cited pursuits, a 32 KB method) and checks every write against the 64 KiB cap of the in-memory door (`test/fixtures.mjs` refuses a larger write as the door does): its largest write is about 48 KB, its largest record 32 KB (a part), its largest root 1,158 bytes.

## A method as rows and a saved view

A method is a saved view over the person's method rows, never a fixed list of steps with a judge on each check (the person's own order, Nov 14 2026, case `source:ZGVjaXNpb24tdG9vbC1pcy1yb3dzLWFuZC12aWV3cy0yMDI2LTExLTE0`). The person's files, and the sections of those files, are rows of one list (`list:method-rows`, row type `method-row`: each file whole, each section a row of its own linked to its file, made by the documents row source of `tools/documents-as-list-rows`); a method is a saved view (a `list-view` record: its rules keep rows, its sort orders them), so any mix of files and sections is a method and a row can be in any number of them. Two tools make the pair every method uses:

- `tool:read-a-method` (`method-rows/view.mjs`) reads the saved view a page at a time (`next` becomes `after`), each row with its whole values and the strictness an answer to it is checked by. Which rows a view holds is decided by the rule filter of `tools/formulas`, the filter the person's own list views use.
- `tool:record-method-answers` (`method-rows/answers.mjs`) records answers to any number of those rows in one call: `{ decision_id, method, answers: [{ row, answer, cites?, evidence_refs? }] }`. An answer is recorded only if its row and every row it cites are rows of the method, every evidence ref it cites is evidence of the decision, and it passes its strictness; one that fails is named with why and not written, and the others are recorded. Each answer is a record of its own (`method-answer:<decision>:<row>`), the same answer again is unchanged, a different one the next version. No model is asked.

**Strictness is an open value, never a level.** It is `{ rules, review }` on the row (`strictness`), else on the saved view, else the default of `method-rows/settings.json` (the answer says something and cites a row or evidence: the cheap check): `rules` a rule tree in the vocabulary of the person's own view rules, decided by the formula engine's rule filter; `review: true` asks an AI to look at the answer too. Only then is the answer kept with review `asked` and the words of the review (`review_job`, `review_said`), and the rule of `starting-rules.json` (the trigger engine) hands it to an AI. A row or a method asks for as much or as little as it says; nothing here names a level, a kind of row or a number of checks.

The earlier way (a Checks list with a branch row per method, a fixed step walk asked one question at a time, a judge's verdict on every check, `tool:next-decision-question` and `tool:answer-a-decision-question`) is gone: no code of it is left, and the open decisions of the person were moved onto this pair (their old answers are kept as answered steps on the decision, read as they were written). `tool:make-the-decision` refuses with `method_unanswered` and names the first unanswered rows until every row of the decision's method (`method_view` on the decision, else `default_method_view` of `method-rows/settings.json`) has an answer. A decision's answers cite evidence of the decision or a current pursuit, which is copied in as it stood.

## Port contract

`read-data/decisions.mjs` and `read-data/decision-records.mjs` have no contract in `ports/`, and the root test
`test/every-feature-file-has-a-port-contract.test.mjs` names them. The reason: they were written here, not first
committed as a byte copy of their older owner. `decisions.mjs` names that owner itself, the old app's `src/engine.mjs`
(DecisionEngine) and `src/decision-store.mjs`. Since the first commit here is not a byte copy, a SOURCE_FIRST_PORT
written now would be false, and so would NO_PRIOR_OWNER. Writing a contract after the fact is not the fix. The owner
decides what happens next: port `src/engine.mjs` and `src/decision-store.mjs` again, byte copy first, and adapt them
until they do what these files do now; or let this repository accept a rewrite of a named owner as a mode of its own
(`ports/feature-files.json`).

## Dependencies

**Depends on:** `tools/formulas` (the rule filter of the method view, `do-work/requests.mjs`), `tools/records-door` (the door client, `run-an-export.mjs` and `writeBatches`), `tools/content-identity`, and, loaded only for a share, `tools/learn-from-everyones-results` (the plain privacy pass, public) and `tools/ask-a-small-model-for-a-verdict` (`contentReviewIdentity`, public); Node 24 in the tool container. Every row packs records-door, content-identity and `@noble/hashes`.

**Depended on by:** `tool-rows.json`, the tests here.


_Write-once layout (2026-11-12):_ a step and an answered-step summary are kept at the content identity of their value (`:c<identity>`), never overwritten. The root names no step itself: its `refs` names one `decision-refs:<id>:c<identity>` record that gives the identity each index holds. A write that is refused before its root lands leaves nothing the root names (test: 'a refused root write of a revision leaves nothing visible').

_Commit (2026-11-12):_ a write adds its records first, all write-once, and only the root and its revision commit it; the revision is the only expectation, checked there. A write refused before its root no longer moves the revision, so a writer that read the case before it is not refused as changed (test: 'a write refused before its root does not move the revision'). Removals land with the root.
