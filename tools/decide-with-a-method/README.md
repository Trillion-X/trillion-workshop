# tools/decide-with-a-method/

Decisions a person's AI makes with a method, kept as the person's own `decision` records: start one, answer the method's questions one at a time (every check answered, the calling AI's own judge's verdicts beside each answer; a step with fewer verdicts than checks stays unanswered and is asked again, and no decision is made while any step is ungraded), make the decision, say what was done, and report how it turned out. At the moment of choice the person's earlier similar decisions come back with how each turned out. A decision is a growing record, not a fixed one: evidence can be added at any time (`tool:add-decision-evidence`), an answered step can be revised with its reason (`revise.because` on `tool:answer-a-decision-question`) so the old version stays readable and every later answer is asked again, a re-asked answer is confirmed unchanged (`confirm`), and an answer or an evidence row can be brought in from another of the person's decisions as it stood (`from`), checked like a typed one. A revision of a decided decision's answer reopens the decision: the decision it had moves to `decision_history`, marked reopened with its reason and when, and the decision is made again. Verdicts can be added to an answered step at any time (`confirm` with `verdicts`) as a new version with the same answer, so a decided decision stays decided. A decision no one will carry on is ended with `tool:end-a-decision`, never deleted, and keeps what it was and why. A decision whose root is too large to send with its condition (`expected`) in one 64 KiB door message, or one the door refuses as too large (413), is ended through its record layout instead, laid apart with its root last and checked by a second read of the root just before the write, and answers `laid_apart`. One whose laid-apart write the door still refuses as too large is left as it was and answers not ended with `too_large`, so the decisions beside it still end. A decided decision can be made safe to show strangers (`tool:share-a-decision`): the calling AI rewrites its redacted facts in general terms, the plain privacy pass finds nothing in the rewrite with the person's own private terms, and a second model's re-identification verdict is accepted for exactly those words. Ported from the old app's `src/engine.mjs` (DecisionEngine), `src/private-method.mjs`, `src/check-uses.mjs`, `src/check-judge.mjs` (the caller's verdicts) and the record layout of `src/decision-store.mjs`, so the Decisions screen reads what these tools write. The method is the person's own rows, which they see and edit: one tree in their one Checks list (`list:checks`, row type `check`): one branch row per method (`kind: "branch"`) and one row per check naming its step, every node `part_of` the one node above it (the link replaces a method's `extends` and a check's `method`); the same list holds the checks tool:check-against-a-persons-rules-and-verdicts judges, which are the rows with no step), never this folder's; Trillion asks no model. A call reads every method row (a few) but only the check rows of the step it asks or judges, through the records door's `where` (`{ step }`, and `{ id }` for each check a step names by id), so a step's few checks never cost the whole list. A question sends each check as its id and question; `tool:next-decision-question` with `explain: [ids]` sends the whole words of those checks (what a good answer does, what it refuses). An answered step keeps each check it asked as its id, question and the content identity of its row as asked; a decision's root keeps its method's id (`method_id`), so similar decisions are weighed without reading snapshots; a decision of any size fits under the records door's 64 KiB write cap, because everything in it that grows is a record of its own linked to its id (see Record layout); and a change too large for one door message is written in parts (`writeBatches` of `tools/records-door`), its root last.

## Record layout

`read-data/decision-records.mjs` lays a decision out; every name is in `records` of `read-data/decide-with-a-method.json`.

| Record | Holds |
|--------|-------|
| `decision` (id `source:<base64url>`) | The root: fields each set by one call (`source_id`, `input` with its `goal` and its `options`, bounded at start, `status`, the current `decision`, `shared`, `workflow_plan`, `decided_at`, `recheck_on`, ...), `method_id` and `method_identity` (where its snapshot is), `input_identity` (the input it was started with, so the same start is still that decision), `counts` (the length of each list below) and `call_count`. Nothing in it grows as the decision grows. |
| `decision-evidence:<id>:<nnnn>` | One evidence row: `ref`, `claim`, and `added_at`, `from`, `retracted_at` when it has them. |
| `decision-answered-step:<id>:<nnn>` | One answered step's summary: `step_id`, `answered_at`, `checks`, `graded`, `graded_by`, `version`, `needs_recheck` (`recheck_of`, `rechecked_at`). A flag is set here, so flagging later steps never rewrites their answers. |
| `decision-step:<id>:<nnn>` | One answered step whole: its answer, the checks it was asked (`{ checks }`) and the verdicts taken (`{ given }`); each superseded version beside it as `decision-step:<id>:<nnn>:v<vvv>`. |
| `decision-candidate:<id>:<nnn>` | One candidate a step left standing. |
| `decision-option:<id>:<nnn>` | Written only by 55179fc, which laid options apart too: such a root (`counts.options`) reads them back, and its next change folds them into the root's `input.options` and removes these records. |
| `decision-report:<id>:<nnnn>`, `decision-carried-out:<id>:<nnnn>` | One result the person reported; one receipt of what was done. |
| `decision-history:<id>:<nnn>` | One earlier decision (with its reopen mark and share, when it had them). |
| `decision-cited-pursuit:<id>:<nnnn>` | One cited pursuit as it stood: `{ ref, said }`. |
| `decision-call:<id>:<nnnnnn>` | One logged call of a decision that was once kept whole. |
| `decision-method:<identity>` | A method snapshot `{ method }`, kept once under its content identity and shared by every decision made with that same method. |
| `decision-part:<key>:part:<nnn>` | A piece of any record above larger than `record_bytes` (32000): that record keeps its short fields and `kept_in_parts`, and its whole value is the text of its parts, in order. A step with hundreds of checks and verdicts, or a long method, goes this way. |

A reader takes the first `counts` items of each list, so a record written in a write whose root never came is never read. A write keeps only the records that changed: the root, the step answered and its summary, the rows added. A root written the old way (evidence, options, results, history and cited pursuits inside it, the method snapshot inline, `answered_steps` on it, the original input kept whole, or the whole guidance in it) reads as it is, and its next change lays it apart: every list becomes its records, the snapshot goes to its identity, `original_input` becomes `input_identity`, all in parts with the root last when one write cannot carry it.

**Options on the root.** Options are set once at start and never grow, and readers outside this folder read them from the root (`input.options`), so they stay there, bounded: a start with more than `options.most` (32) options, or more than `options.most_bytes` (8000) bytes of their JSON, is refused (`words.options_too_large`: the limit, and to shorten or group them). The bound is checked only when a decision is opened, so an older decision with more options still replays. The arithmetic for the root at its largest: options at most 8,000 bytes; every other field the case adds to the root (`counts` with seven numbers, `method_identity` and `input_identity`, `method_id`, `call_count`, `change_count`, `outcome_revision`, `decision_generation`, status and times, the empty `scratchpad`, `actions` and `checks`) about 700 bytes and never more as the case grows; the one-call fields (goal, the current decision with its fields and refs, `shared`, `workflow_plan`, `decision_usage`) were about 450 bytes in the big-case test, whose largest root was 1,158 bytes with two options. With 8,000 bytes of options that root is about 9.2 KB, leaving about 56 KB of the 64 KiB (65,536 bytes) cap for the one-call words, which are bounded by their own calls, not by how large the case grows.

**Size guarantee.** Every record and write is measured as carried (`carriedBytes`: its JSON with every character past ASCII as a `\u` escape, quoted once more as a JSON string), the most a door can make of it on the way, so a part, whose text is JSON already escaped once, still fits when a door re-encodes it: a 67 KB chat message full of quotes, newlines and emoji once made a write of 46 KB plain that was 74 KB carried, and the door answered 413. Every record the tools write except the root is at most `record_bytes` carried; the root holds only one-call fields and counts; every door write is at most `writes` records and about `write_bytes` bytes, the root last when a change takes more than one. The test `a decision of any size fits` builds a made-up case of about 400 KB (500 evidence rows, 43 steps, a step with 300 checks and verdicts, three earlier decisions, twelve receipts, thirty cited pursuits, a 32 KB method) and checks every write against the 64 KiB cap of the in-memory door (`test/fixtures.mjs` refuses a larger write as the door does): its largest write is about 48 KB, its largest record 32 KB (a part), its largest root 1,158 bytes.

## Key Types / Functions

| Function | Signature | Role |
|----------|-----------|------|
| `startADecision` | `({ source_id, goal, evidence, options, method? }, { door }) -> reply` | One source opens one decision under the method's snapshot. |
| `answerADecisionQuestion` | `({ decision_id, step_id, answer? \| from?, revise?: { because, by? }, confirm?: true, verdicts?, usage? }, { door }) -> reply` | Validates the answer against the method, takes grounded refusals, refuses (`verdicts_missing`) an answer without a verdict for every check, keeps the step; a `revise` keeps the old version and flags every later step, and on a decided decision reopens it; `confirm` keeps a re-asked answer unchanged, or with `verdicts` adds them as a new version of the same answer; `from` copies another decision's step as it stood. |
| `addDecisionEvidence` | `({ decision_id, evidence: [{ ref, claim } \| { ref, from: { decision_id, ref } }] }, { door }) -> reply` | Adds evidence rows at any time, each kept with when it came in; the same rows again replay. |
| `makeTheDecision` | `({ decision_id, decision, verdicts?, usage?, expected_generation? }, { door }) -> reply` | The choice, its fields and evidence, refused (`ungraded_first`) while any answered step has fewer verdicts than checks; a new one only after a failed result or a revision that reopened the decision. |
| `reportADecisionResult` | `({ decision_id, result, summary, answered_by: "person", ... }, { door }) -> reply` | The person's result; a failed one opens the decision again. |
| `methodCatalogue` | `(methods, checks, { grader, link }) -> functions` | Every method function over the person's branch rows and check rows (one tree in `list:checks`, joined by `link`). |
| Check row | `{ id, method, step, check, good_answer, when?, skip?, ... }` (row type `check`, `list:checks`) | A question of one step of a method's lineage. The same list holds the rows `tool:check-against-a-persons-rules-and-verdicts` judges (rows with no `step`); a call reads only a step's rows, by `where`. |
| `similarDecisions` | `({ decision_id, limit? }, { door }) -> { similar_decisions }` | Earlier decisions like this one, each with its choice and how it turned out. |
| `shareADecision` | `({ decision_id, rewrite?, reidentification? }, { door }) -> { next: "rewrite" | "check" } or { shared, send }` | The redacted facts to rewrite; then the plain pass on the rewrite; then the review identity a verdict must carry; then the entry kept and the pool tool to send it to. |

## Not here yet

- Readers outside this folder that read a decision's evidence, results, history, cited pursuits, method snapshot or `answered_steps` from its root see a laid-apart decision as incomplete (pinned at trillion `42aff4e9` and trillion-rust `cf14230`; neither is changed here). No other Workshop tool reads decision records.
  - trillion `src/decision-store.mjs:123` (`apart` needs `answered_steps` on the root): a laid-apart root is taken as kept whole, so `assemble` (332-340) and `contentOf` (535-538) give it no guidance and no calls, and `:722` (`root.answered_steps.findIndex`) throws.
  - trillion `src/decision-store.mjs:457` method (null: reads `method.id`, not `method_id`), `:463` cited pursuit ids (empty), `:513` goals' method (null); results and receipts read from the root (`decisionStatus`, `carriedOut` at `:75`) are empty, so a decision with a report shows its root `status` only.
  - trillion `src/engine.mjs:91` and `:580` (`record.input.evidence.filter` throws), `:206` (the same start compares against a root input without its evidence, so it is refused as different), `:747`, `:808-822` (evidence added there throws), `:956-980` (starts from no reports).
  - trillion-rust `src/local_account/decision_screen_source/values.rs:312` cited pursuits (none), `:339-340` method (`universal`, from the missing snapshot), `:121-123` and `:237` results and receipts (none); `src/local_account/decision_screen_source.rs:742-760` (`complete_decision` rebuilds guidance only from `answered_steps`: no steps shown) and `:445` (no cited pursuits opened). `src/workspace_decision_screen.rs` reads no decision fields.

- A confirmation with verdicts takes only the verdicts a typed answer would take: a refusal that names no words of its check, or a verdict that rests on nothing of the answer or the evidence, is ignored, not refused. A verdict is never changed once kept.
- Adding evidence flags nothing: answers already given do not cite it, so a step that should weigh it has to be revised (with its reason) to do so.
- Revising the scope flags every answer after it. A step the old scope asked and the new one does not is kept and not asked, so its answer stays in the record unused.
- A reopened decision moves its share into the history, but a copy already sent to the pool stays there: nothing here can take it back out.
- A reopened decision's new decision waits until every answer is asked again (confirmed or revised), as before.
- A workflow run named by `run_id` cannot be read by these tools, so it is refused, and a plan whose decision needs a finished decision-phase run waits (`words.decision_phase_runs`).
- A report from a trusted person source (the signed-in host's basis) cannot be marked here: every report is kept as the caller's claim.
- The pool account's door admits other people through a share's act grant (trillion-rust `src/account_rights/share_grant.rs`). Sending a shared decision there is the calling AI's own call with the pool's share bearer: `tool:add-a-shared-situation` with `send.entry` and the meaning of its situation (the embedding the pool names), then `tool:add-a-pooled-result` with the bit `tool:randomize-a-result` drew. No tool here reaches another account's door.
- The re-identification verdict comes from `tool:ask-a-small-model-for-a-verdict`, whose rows run on the person's computer, not at the engine yet; this tool only checks that the verdict was accepted for exactly the rubric and words it names (`contentReviewIdentity`). A result's own words are not shared: the pool takes only its randomized bit.

## Port contract

`read-data/decisions.mjs` and `read-data/decision-records.mjs` have no contract in `ports/`, and the root test
`test/every-feature-file-has-a-port-contract.test.mjs` names them. The reason: they were written here, not first
committed as a byte copy of their older owner. `decisions.mjs` names that owner itself, the old app's `src/engine.mjs`
(DecisionEngine) and `src/decision-store.mjs`. Since the first commit here is not a byte copy, a SOURCE_FIRST_PORT
written now would be false, and so would NO_PRIOR_OWNER. Writing a contract after the fact is not the fix. The owner
decides what happens next: port `src/engine.mjs` and `src/decision-store.mjs` again, byte copy first, and adapt them
until they do what these files do now; or let this repository accept a rewrite of a named owner as a mode of its own
(`ports/feature-files.json`).
