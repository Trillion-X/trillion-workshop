# tools/check-against-a-persons-rules-and-verdicts/

Checks words, or anything else made for a person (a title, a script line, a plan as JSON), against that person's own rules and the verdicts they already gave, and says pass, fail or uncertain for each thing, with every finding and why. Nothing about any person is built in: their rule rows, their rule document and their stands are input, read at run time from their records or their files.

What decides, in order:

1. **Their exact stand on the thing** (from `tool:read-where-you-stand`): disagree fails it, partly holds it at review and fails it at final, agree passes it and clears the generic rules their document names in `agree_clears`, unless a row is newer than the stand. A stand on a part (`contains`) decides every thing holding that part. A reworded thing gets no verdict from a stand on the original.
2. **Their rows for the thing's kind**: a stated row fails; an inferred row (`at_most: "uncertain"`) only holds; a `required` inferred row that finds nothing holds at review and fails at final. A row whose `because` names stands takes its strength from the newest of them, and only holds once all of them are taken back. A `part` row gives a thing the stand on a part of it (a take gets its voice's).
3. **Reading rows and ask rows** (a question a model answers): a row's answer counts only once its calibration is `usable`; a capped row never fails. An ask is put once a sentence of each unit, or once of the whole unit when its `per` is `unit`. The tool never calls a model: it lists the questions by id, and the caller sends the answers back.
4. **Generic rule rows** (`rules`), judged by `tools/judge-words`. A row's `held_when` (over a unit's `facts`) makes its finding only hold on those units.

Nothing passes on silence: a thing no rule applies to is unqualified, and a thing nothing of the person's judges is novel (held at review, failed at final).

Two more things come from the person alone:

- **A waiver.** Their agree on one exact line that names one rule (a stand with `rule`) waives that rule on that line, and the result lists it in `waived`. Nothing else waives anything: not a stand by anyone else, not disagree or partly, not a stand with no rule, not another line however close. A stand that names a rule is never a verdict on the whole thing.
- **Their own words.** `do-work/spoken-origins.mjs` `withSpokenOrigins(units, spans, { fold })` marks a unit `own-words` (with its `span`) when every word is literally in one recording span the caller hands in, read through the person's fold; `unverified-speaker` when that span's speaker was never checked; else `added-words`. These go in the unit's `facts`, so a row's `held_when: { path: "origin", where: "own-words" }` holds, never fails, the person's own words. The literal match is `tools/pin-files-by-content` `literalPieces`.

## One check list, read by branch

Every check of a person is one row of their one Checks list (`list:checks`, row type `check`, records `record:check:<id>`), and names its branch in `method`. A branch is one of their method rows (`list:methods`, row type `method`), which `extends` another, up to a base: for example a base for any decision, a branch for anything people read or hear, a branch of that for a story, post, article or script, and a branch of that for one book. A branch's checks are its own and those of every branch it extends. Ported from the old app's `src/private-method.mjs:25` (`extends`) and the check rows of `methods/checks.json`; `tools/decide-with-a-method` reads the same lineage from `do-work/branch.mjs`.

Send `branch` in place of `rules` and `verdict_rules`, and the tool reads, through the person's records door, only what that branch needs:

- the method rows, and the lineage of the branch, nearest first (an unknown branch, an unknown `extends` or a cycle is refused);
- for each branch of the lineage, the check rows whose `method` is that branch (the door's `where { method }`, never the whole list), and the rows of every list the branch names in `check_lists` (a list whose rows are of a type `read-data/branch.json` does not allow is refused);
- a row with `step` is a question of a decision step, asked by the decision tools: its `check` is question text, so it never reaches the judge; a row with `on: "Off"` is not judged; a row id is judged once, the nearest branch's row winning;
- the nearest branch carrying `judge_settings` (a rule document's settings: `fold`, `stage`, `stance_rule`, `novel`, `agree_clears`, `kept_at`) makes the rule document: its rows and those of the branches extending it are the person's verdict rows; the rows inherited from above it are the generic `rules`.

- a row that states no test (none of `tools/judge-words` `SELECTOR_NAMES`, imported from there, no `ask`, no `part`) never reaches `makeJudge`, since one such row would refuse the whole branch. When it is not a piece of a source file (`kind: "piece"`) and has words in `says`, it is a **reading row**: an ask row whose `ask` is made from `read-data/branch.json` `reading` (`readingRow`): the question is its parts joined by new lines, filled from the row's `says` and, when `says` does not already hold them, the words it is about; `options`, `fail`, and `per: "unit"`, so it is asked once of each whole unit. Its `calibration`, `model`, `adapter` and `at_most` come from the nearest branch of the lineage whose method row holds `reading_settings` (the person's DATA, never code). It goes to the check like any ask row: a unit it reads is never passed while its answer is missing or its calibration is not `usable`. Reading rows are listed in `read_by_a_model` (`{ rows: [{ id, says, kind? }], more, settings_from }`, at most `read_by_a_model_at_most`). A piece, or a row that says nothing, is counted in `rows_used.skipped.no_test`; a branch with only such rows answers status `no-applicable-rule`, not a refusal.

Then the same check runs, and the answer adds `branch`, `lineage`, `rows_used` (`{ branches: { <method>: n }, lists: { <list>: n }, skipped: { step, off, no_test } }`) and `read_by_a_model`. The rules mode (`rules`, `verdict_rules`) is unchanged.

**How many questions.** A reading row is asked once a unit, so a branch with `n` reading rows asks `n` questions of each unit, whatever its length: per sentence, a 5-sentence paragraph against 400 reading rows would be 2,000 questions; per unit it is 400. Each question carries the unit's whole text, so the answer of a branch with hundreds of reading rows is larger than one door message and comes back in `byte_page` pages.

**Calibrating reading rows.** The reading rows are labelled cases: a row whose `says` quotes wording the person rejected is a bad line, a row holding a passage of theirs is a good line. Ask the model each reading question about each line (leaving out the rows that quote that same line), take a line's score as its highest answer (a unit fails on its worst row), and fit the pass and fail lines with `tool:fit-pass-and-fail-lines` (`tools/ask-a-small-model-for-a-verdict` `fit-lines`). Keep what it measures, usable or not, in the method row's `reading_settings.calibration`, with the `model` that answered; never write `usable` that was not measured.

## Every piece of every file, covered

A person's source files (a method, a book, a skill file) are held piece by piece in the same Checks list, never one row per file and never a byte slice. `tool:split-a-document-into-pieces` (`{ name | text, file?, file_identity? }`) breaks a document into its pieces: one paragraph, list item, table row or fenced block (``` or ~~~, fenced as CommonMark defines it) under its headings, keyed by its heading path and lead, identified by `1f:` and the BLAKE3 of its whitespace-folded text. A whole file is split and kept in one call: `name` is one of the person's files, read by reference through their files door page by page (a request body over 64 KiB is refused by the door, so a larger file is never sent as `text`), and every piece is kept as the row a person keeps (`record:check:piece-<24 hex>`, `kind: "piece"`). A piece already kept keeps its `checked_by`, `no_check`, tags and kinds and gains this file as a source; the same text in two files is one row with two sources. Every write is conditional on what was read and fits one door message; a piece too large for one write is named and not kept. The answer is counts (new, found again as a source, unchanged) and the first ids, never the pieces: answered as rows, a 31 KB file's pieces came to about 280 KB of JSON, and a door carries a run's answer twice in one 65,536-byte message, so the whole file ended with an unknown outcome while 3 KB chunks (about 29 KB of answer) did not. Time and memory were not the bound: that split took 146 ms and 58 MB. The person (or their AI) then names the checks written from each piece in `checked_by`, or records `no_check: { reason, covered_by? }`.

`tool:check-every-piece-is-covered` (`{ file?, after?, most_bytes? }`) reads the Checks list read only and only in bounded pages: the ids of every row (`fields: []`), then the piece rows (`where { kind: "piece" }`, narrowed to the fields it reads, never their text), each page folded into a running tally and let go. It answers totals and, per source file, pieces, with a check, with a reason and how many are uncovered, naming the first uncovered pieces; status `failed` while any piece is uncovered. The answer fits one door message (28,000 bytes of JSON): `next` is the `after` of the next page of files, and with `file` the page names that file's uncovered pieces by id after `after`. On a made-up list of 40,707 rows (39,088 pieces) it reads 324 pages in about 5 s and answers 27,742 bytes, where reading the list whole held every piece row, read 11,391 checks one by one and answered 9,146,520 bytes. Moved from old trillion's `scripts/method-sources.mjs` (`sweepAtoms` and its `--coverage` report); the pieces are its `scripts/method-atoms.mjs` `atomsOf`, read from its one home `tools/documents-as-list-rows/read-data/atoms.mjs`.

## Run it

```
jq -n --slurpfile rules <rule rows>.json --slurpfile doc <rule document>.json --slurpfile stands <stands>.json \
  --slurpfile units <units>.json '{rules: $rules[0], verdict_rules: $doc[0], stands: $stands[0], units: $units[0], stage: "review"}' \
  | node tools/check-against-a-persons-rules-and-verdicts/do-work/check-against-their-rules-and-verdicts.mjs
```

The last line is `{ "result": { status, passed, results, questions, lines } }`. To use a model's answers, send the same request again with `answers: { "<question id>": { "<option>": <probability> } }`.
