# screen-arrangement do-work

Package-owned request builders for screen-arrangement operations.

## Files

| Path | Purpose |
|---|---|
| `ask-screen-arrangement.ts` | Sends current layout state and an operation payload to `slot::screen-arrangement`. |
| `layout-operations.ts` | Builds UI-facing layout actions while leaving transition math in the Rust slot. The runtime's optional `settleReply(prev, next)` adjusts every reply before it is committed and recorded (the provider keeps rows the person placed side by side on a narrow stage side by side). Every request carries `paneSizes` from the runtime's optional `readDrawnPaneSizes`, so a new pane never takes room from the others. `resizeSplit(sizesPx, path)` records every pane of the split at `path` in layout pixels (`sizeUnit: 'px'`), so a dragged width is kept and drawn again after a reload (`test/pane-resize-keeps-its-size.test.mjs`). `resizeCross(path, index, lengthPx | null)` records one pane's own length across its split (its height in a row, its width in a stack; null fills again). `addPaneBeside(containerId, dir, initialTab?, position?)` opens a pane beside (`row`) or below (`column`) at the person's `added_pane_width_px` / `added_pane_height_px`, sending the target's drawn length so every pane keeps its size and the split keeps its lengths (`test/pane-height-and-add-beside.test.mjs`). All slot-backed and direct layout writes record arrangement history; `undoArrangement`, `redoArrangement`, and `restoreArrangementHistory` restore saved snapshots (`test/screen-arrangement-history.test.mjs`). |
| `save-layout-state.ts` | Persists the whole normalized `LayoutState` JSON to the canonical `screen-arrangement-layout-state` record at `["current-item", "published-record"]` through the same default label-addressed current-state family that the package input descriptor reads. A write may name `expected_identity` (what the page last read of the record): the store keeps it only while that is still what is kept, and `layoutStateWriteRefused(reply)` says when it kept nothing, so a drag made from an older copy never replaces a newer arrangement (test/arrangement-stale-drag.test.mjs). |
| `save-layout-preset.ts` | Writes saved layout preset owner actions. |
| `switch-saved-layout.ts` | The one switch between layouts (keeps the replaced arrangement as Previous layout and, when no layout matches it, as a self-kept layout named from its screens, before applying), `layoutChoices` (the one order the picker draws and the edge switch walks), `currentLayoutNeedsName`, `saveCurrentLayoutAs` (names the arrangement on screen; a self-kept copy or Previous layout becomes the person's own instead of a second copy; confirmed by read-back), `asOwnLayout`, `announceSavedLayoutsChanged`, `loadSavedLayoutGroups`, `savedLayoutSignature`, `keptLayoutsToLetGo`. Everything is kept in the account through `save-arrangement-as-group.ts`. |
| `save-arrangement-as-group.ts` | Saved layouts as GROUP records (W1): decompose LayoutState into `group.apply-mutation` ops (per-tab arrangement in member presentation + one structure member), fold back on read, index-group registration for listing. Applying goes through `save-layout-state` (SSOT). |
| `save-arrangement-as-group.test.ts` | Round-trip fold(decompose(state)) equality, field-presence gating, atomic batch/delete dispatch shapes. |
| `migrate-layout-presets-to-groups.ts` | One-shot additive migration of legacy `prop:layout_preset:*` rows to group-backed presets — readback-verified BEFORE archiving, idempotent, per-preset failure isolation. |
| `migrate-layout-presets-to-groups.test.ts` | Order-of-operations, idempotence, verify-blocks-archive tests. |
| `ask-discovered-addresses.ts` | Requests discovered address metadata for generic placeable surfaces. |
| `execute-open-intent.ts` | `executeOpenIntent`: opens a folder's or selection's screens by an open-intent row's strategy (tabs in one pane, split each, grid, floating, canvas). The first screen replaces the picker's empty tab in place; every placement goes to the arrangement as ONE `applySequence` request, so the finished arrangement appears at once. |
| `node-history-operations.ts` | Each pane's back/forward history (`recordVisits`: every pane whose shown tab changed between two layout states records that tab, called once at the layout-commit road in `layout-operations.ts`, so opens from anywhere land in it and a step back records nothing; a pane keeps its latest 100 visits; `recordNavigation`, `historyBack`, `historyForward`, `historyNavigateTo` to jump to a picked visit, `currentHistoryRef`) kept in `LayoutState.nodeHistory`, and `historyListItems`: the rows the back/forward list shows, each with the time it was opened and a closed tab disabled. |

## Boundary

The Rust slot owns transitions. This folder owns request construction and owner write invocation only. Layout-state persistence is one direct whole-payload JSON write through `engine.operation.label-addressed` at `valueAddressLabel: "screen-arrangement-layout-state"` using the package input descriptor's default address family; it does not keep the old `layout-state` RTBL feed active, does not write `layout-state/fact` rows, does not rebuild a table projection, and does not route through a package-local workflow wrapper.
