# Contributing a tool

Thank you for making a tool. Every merged tool is offered to every Trillion user's AI, so a tool here must do exactly what its row says, every time.

## The rules a tool follows

1. **One folder, everything in it.** Code, `tool-rows.json`, `README.md` and tests live in `tools/<your-tool>/`. A tool may import only from its own folder and from Node or Python's standard library, unless its row packs the module it needs. Code several tools share lives in a library folder (`part.json` and a README, no rows of its own); each row that needs it packs its files in `invoke.files.package_files`.
2. **One JSON request in, one JSON answer out.** The command reads the request on standard input (or in `argv`, if its row says so) and prints its answer as the last line. Nothing is kept between runs. The row's `result_selector` picks the answer from that last line itself: `"$"` when the program prints the answer, `"$.result"` only when it prints `{ "result": ... }` (`test/every-process-row-selector.test.mjs` checks it on the row's sample run).
3. **The job is in plain words.** `job` is what a person would ask for ("work out my unit economics"), never the tool's internal name. Trillion finds tools by their job.
4. **Say what it takes and gives back.** `input_schema` and `output_schema` are JSON Schemas; every answer is checked against `output_schema`.
5. **Prove it with a sample run.** A row that runs a program has an item in `verify` with `"kind": "sample-run"` and an `input` of made-up values. `test/every-process-row-selector.test.mjs` runs it the way the container runner does (`test-helpers/run-a-row.mjs`) and fails when the row's `result_selector` finds nothing in the last line the program prints, and fails, naming it, on every row no sample of its own proves. Only a row whose run truly needs a real computer (a Mac screen, a camera, an attached drive) may instead carry `{ "kind": "needs-a-machine", "requires": "<OS, permission, device>", "proved_on": null }` in `verify`, with `requires` naming exactly what; make the sample run here first, with the stand-ins below, wherever that is possible. A sample can seed the records the row reads (`records`), answer a row with `"internet": true` from replies it records (`replies`, each `{ "request": { "method", "url" }, "status", "body" }`, with `shape_read_at`, the date the reply shape was read from the service; after the days `test-helpers/stand-in-egress.json` allows, read it again), give made-up values for what the row mounts (`held`), answer the run's files door from made-up files (`door_files`; it finds, reads and keeps files sent in pieces), answer the files door's usage days from made-up engine day rows (`doorOptions: { "usageDays": [...] }`), lay made-up files in a granted folder (`files`, each `{ "grant", "path", "text" }`), replace a file the row packs for that run (`laid_files`), answer a row that asks a model for embeddings from a stand-in model server on loopback (`model_server`, `{ "vector": [...] }`, Ollama's embedding replies; any string names its address as `{model_endpoint}`), and put stand-in programs first by name (`stand_in_programs`), so a program that would send, print or read this computer answers from the sample instead. Any string may name a granted folder as `{grant:<capability>}`. Run one folder's rows with `WORKSHOP_UNIT_FOLDER=tools/<your-tool> node --test test/every-process-row-selector.test.mjs`. For example, a program whose last line is `{"domains": [], "count": 0}` needs the selector `"$"`; `"$.result"` finds nothing there.
6. **No secrets, no personal data.** Never put a key, token, password, email address or a real person's details in code, rows, tests or examples. A tool that needs an account takes it from the person at run time.
7. **Name its licence class.** `licence_class` is one of the ids in `licence-classes.json`, and `placements` must be places that class allows. A package the tool adds to `package-lock.json` must have a licence some class lists, in a class that allows every place this repository's tools run (`test/lockfile-licences.test.mjs`).
8. **No internet unless needed.** Set `"internet": true` in `invoke` only when the job is reading the web; such tools refuse private and local addresses.
9. **Refusals say what to do.** An error tells the caller what was wrong and how to fix the request.
10. **Ship it as a kit (L082).** A person should start running a tool or workflow, not read how to. Its kit is one file beside it, `<its folder>/kits/<its id without tool: or workflow:>.json` (a workflow's in `tools/workflows/kits/`), holding: `start_here` (what the person says first, with real values), `lists` (every list it reads or writes, with its fields, at least two filled-in example rows and the lists people already keep that do the same job), `workflows` and `tools` (everything it runs), `instructions` (from nothing to a finished run), `worked_examples` (what the person says, the MCP server, tool and exact input the AI calls, the workflow and the step, what comes back) and `pour` (how the example rows go into a list the person already has that does 80-100% of the same job, through `tool:pour-example-rows-into-my-list`). `tools/workflows/kit-template.json` shows every part filled in. `test/every-item-has-its-kit.test.mjs` and the push gate refuse an item with no kit or a kit missing a part; the items from before kits are on the dated list `test/items-without-a-kit.json`, which only shrinks (a push that adds an id to it is refused).

## Checks

`npm test` runs every tool's tests and `test/every-tool-row.test.mjs`, which reads the rows the way Trillion does. A pull request must pass it.

## Adding a repository from GitHub

To offer someone else's open-source project, add a row to `tools/tools-from-github/sources.json` and run `node tools/tools-from-github/index-github-tools.mjs`. It reads the licence from GitHub; a repository whose licence no class lists is refused.
